Overview & Mental Model

Definition

The Claude API is a stateless HTTP interface. The core endpoint, POST /v1/messages, takes the whole conversation (system prompt, alternating user/assistant turns, tool definitions) and returns one assistant message made of typed content blocks plus a stop_reason and token usage. Official SDKs (Python, TypeScript, Go, Java and others) wrap the same API and add retries, streaming helpers and types.

What your code owns

The API remembers nothing between calls and never runs your tools. Your application owns history (what to resend, prune or compact), tool execution (and authorization), branching on stop_reason, retries, validation of outputs, and cost/latency instrumentation. Almost every exam-style defect is one of these responsibilities done wrong.

Mental model

Treat every response as a state transition: read stop_reason first, then decide whether to show text, run tools, continue, compact, fall back or stop. Code that reads content[0].text without checking stop_reason is the root of most production bugs.

01

Build the request

Model ID, max_tokens, system, messages, tools, optional thinking/effort and output format.

02

Call (sync, stream or batch)

Pick the transport by who is waiting and how much work there is.

03

Branch on stop_reason

end_turn, tool_use, max_tokens, refusal, and the rest.

04

Append & loop

Append the assistant turn unchanged, add tool results, repeat until done.

1. Model Family, Effort & Choosing a Model

TierProfileTypical fitWatch out
HaikuFastest, lowest cost per tokenHigh-volume classification, routing, extraction, real-time triage, sub-agent workersValidate on your eval set before trusting it on nuanced steps
SonnetBalanced capability, speed and costDefault starting point for most apps and agents, coding, tool useDon't upgrade the whole pipeline when only one step fails
OpusMost capable, slowest, highest costHardest reasoning, long multi-step agent work, planning, review of critical outputPaying top-tier prices on steps a smaller tier passes

Two independent levers

  • Model tier sets the capability ceiling and the price per token.
  • Reasoning depth is a per-request setting: adaptive thinking plus output_config.effort (low, medium, high, xhigh, max; the accepted set varies by model).
  • Tune them separately. A smaller tier at higher effort can beat a larger tier at low effort on some tasks, and vice versa; only an eval tells you which.

Selection rule & Planner → Executor routing

  • Start on the balanced tier with the least reasoning that passes.
  • Move individual steps up or down only on eval evidence; route easy vs. hard inputs to different tiers.
  • Planner → Executor tier routing (Spec-Driven pattern): Use Opus for the read-only architectural specification and ambiguity-resolution pass, then start a fresh context window on Sonnet with only the finalized spec for implementation and tool-heavy execution (and Haiku for bounded read-only search workers).
  • Treat every model or effort swap as a release: pinned ID, baseline comparison, rollback target.
  • Turn thinking off or effort down on high-volume classifiers: thinking tokens are billed as output.

Sampling parameters on current models

On Claude 4.7 and later, setting temperature, top_p or top_k to any non-default value returns HTTP 400. Steer behavior with prompting, examples, structured outputs and effort instead. Even on older models where temperature: 0 is accepted, output was never fully deterministic: test properties, not exact strings.

Common trap

"Use the best model everywhere" is still a tier decision, just the most expensive one. And "set temperature to 0 for consistency" fails twice: it 400s on the newest models and never guaranteed identical text anyway.

import anthropic
client = anthropic.Anthropic()          # reads ANTHROPIC_API_KEY from the environment

resp = client.messages.create(
    model=PINNED_MODEL_ID,
    max_tokens=1024,
    system="You are a support assistant for Acme. Answer only from the provided policy.",
    messages=[
        {"role": "user", "content": "Can I return an opened item?"},
    ],
)
if resp.stop_reason == "end_turn":
    answer = next(b.text for b in resp.content if b.type == "text")

Common trap

Prefilling the final assistant turn to force a format is rejected with a 400 on Claude 4.6 and later. Use structured outputs (§6) instead. Also, content[0] is not always text: with thinking on, the first block is usually a thinking block. Select blocks by type.

3. The Tool-Use Loop

01

Define tools

name, description (what it does, when to use it and when not to), input_schema.

02

Claude requests

Response has tool_use blocks (each with an id) and stop_reason: "tool_use".

03

Your code executes

Authorize, validate inputs, run. Add a human gate before irreversible actions.

04

Return results

Append the assistant turn unchanged, then one user turn with a tool_result per call.

Pairing ruleWhat breaks if you ignore it
Every tool_use gets a tool_result whose tool_use_id equals the call's id400: result references an unknown ID, or a call is left unanswered
Results go in the very next user message; nothing in between400 on the next request
In that user message, tool_result blocks come first; any text goes after themValidation error, or the turn ends early
Parallel calls in one turn are all answered in one user messageOrphaned calls; splitting results across turns fails
Failures are returned as a tool_result with is_error: true and a short messageAn empty string reads as "no data", so Claude confidently reports a false result
 
messages.append({"role": "assistant", "content": resp.content})   # echo unchanged
results = []
for block in resp.content:
    if block.type == "tool_use":
        try:
            out = run_tool(block.name, block.input)                    # your authz + validation inside
            results.append({"type": "tool_result", "tool_use_id": block.id, "content": out})
        except ToolError as e:
            results.append({"type": "tool_result", "tool_use_id": block.id,
                            "content": f"lookup failed: {e.short}", "is_error": True})
messages.append({"role": "user", "content": results})                # all results, one turn, first
tool_choiceBehaviorNotes
{"type": "auto"} (default)Claude decides whether to call a toolAdd "disable_parallel_tool_use": true inside this object for at most one call per response
{"type": "any"}Must call some toolForced use: not allowed with manual extended thinking, and some of the newest models return 400
{"type": "tool", "name": "..."}Must call that toolSame restrictions as any; prefer auto + strict: true or structured outputs where forcing is rejected
{"type": "none"}No tool callsTools stay defined (keeps the cache prefix stable)

Tool design & multimodal tool_result

  • Description = purpose + when to use + an exclusion sentence ("not for refunds").
  • Small, well-named tool set; overlapping tools cause wrong picks.
  • Mark truly required fields in required; use enums for closed sets.
  • strict: true guarantees tool inputs match the schema.
  • Multimodal tool_result: content can be an array of text and image blocks (e.g. Playwright browser screenshots), enabling closed-loop visual UI verification.

Client vs. server tools

  • Client tools: you execute them and return tool_result.
  • Server tools (e.g. web search): Anthropic executes them inside the turn.
  • A long server-tool loop can stop with pause_turn: send the assistant content back as-is to continue.
ArchitectureHow tools & context are handledScaling limits & best fit
Workflow / Hybrid RAGFixed code path; static chunking + embeddings + reranking injected before calling ClaudePredictable latency; fails on multi-hop code navigation (under-retrieval, over-retrieval, and misaligned retrieval across imports)
Shallow ReAct Loop / Standard MCPSingle messages[] loop calling JSON tools one turn at a time4 scaling bottlenecks: (1) upfront tool-schema bloat, (2) K-turn sequential ping-pong latency & repeated prefix billing, (3) pretraining mismatch (LLMs are trained on millions of real TypeScript/Python repos vs. synthetic JSON tool_use traces), and (4) JSON schemas cannot express loops, conditionals, or error-handling chains

Common trap

"Unknown tool_use_id" is a wiring bug, not a schema or description bug. And disable_parallel_tool_use is not a top-level request field: it lives inside tool_choice.

4. stop_reason Values and Handling

stop_reasonMeaningCorrect handling
end_turnNatural finishUse the response
tool_useClaude is calling one or more toolsRun them, return paired tool_results, call again
max_tokensHit your max_tokens cap (or the model maximum)Raise the cap or continue the response; never parse truncated JSON as complete
model_context_window_exceededGeneration filled the context windowTreat as truncated; prune/compact history before the next turn
stop_sequenceOne of your stop_sequences firedRead stop_sequence to see which
pause_turnA long server-tool loop was pausedSend the assistant content back unchanged to continue
refusalClaude declined (safety classifiers)Returned as HTTP 200. Read stop_details; don't blind-retry the same request; reset or rephrase the refused turn, or retry on a fallback model where offered

Refusals in practice

  • stop_details can carry a policy category (may be null) and an explanation that isn't guaranteed stable.
  • Leaving the refused turn in history leads to continued refusals: remove or rephrase it, or clear history.
  • When streaming, the refusal arrives on the message_delta event; discard the partial turn.
  • An HTTP-status-only error check misses refusals entirely.

max_tokens vs. context window

  • Input alone larger than the window → 400 "prompt is too long", before any generation, on every model.
  • Input fits, but input + max_tokens exceeds the window → newer models accept it and stop with model_context_window_exceeded if they run out.
  • The API never silently drops old turns: history management is your job.

Common trap

A refusal is a content decision, not a transient error: exponential backoff on the same request just repeats it. And max_tokens limits output length only; raising it does nothing for an oversized prompt or a crowded context.

5. Streaming Events

Event (in order)CarriesHandler action
message_startMessage shell, initial usageOpen a buffer for the turn
content_block_startBlock index and type (text, tool_use, thinking)Start a per-index accumulator
content_block_deltatext_delta, input_json_delta (partial tool JSON), thinking deltasRender text; append JSON fragments, don't parse yet
content_block_stopBlock completeNow parse tool input JSON and validate
message_deltaTop-level changes: stop_reason, cumulative output usageBranch on stop_reason (refusal, tool_use, max_tokens…)
message_stopMessage completeOnly now commit the assistant turn to history
pingKeep-aliveIgnore

Why stream

  • Improves perceived latency (time to first token) for a waiting user.
  • Recommended for long requests: very long non-streamed calls risk timeouts, and the Python SDK requires streaming above roughly 21k max_tokens.
  • Does not reduce total tokens, cost or request count.

Interrupted streams

  • "The read loop ended" ≠ "the message is complete". Only message_stop means complete.
  • On a drop, discard the partial turn and retry from the last complete turn.
  • SDK helpers (e.g. a final-message accumulator) do the bookkeeping for you.

Common trap

Saving a half-streamed assistant turn leaves a malformed tool_use in history, and every later request fails validation, often surfacing only on retries. Parse tool input at content_block_stop; commit the turn at message_stop.

6. Structured Outputs

ApproachGuaranteeUse when
System-prompt output styles (format/persona instructions in system, e.g. YAML/HTML/tutor style)None: best effort (steers tone, verbosity, or non-JSON formats like YAML/Markdown)Human-facing presentation or custom personas; never rely on prompt prose for downstream JSON parsers
JSON outputs: output_config.format = {"type": "json_schema", "schema": {...}}The response text parses and matches the schema (constrained decoding)The answer itself must be machine-readable (extraction, classification, reports)

resp = client.messages.create(
    model=PINNED_MODEL_ID, max_tokens=1024,
    messages=[{"role": "user", "content": email_text}],
    output_config={"format": {"type": "json_schema", "schema": {
        "type": "object",
        "properties": {"name": {"type": "string"}, "demo_requested": {"type": "boolean"}},
        "required": ["name", "demo_requested"],
        "additionalProperties": False}}},
)
if resp.stop_reason == "end_turn":                      # check before parsing
    data = json.loads(next(b.text for b in resp.content if b.type == "text"))

Production constraints

  • Shape ≠ correctness. A schema-valid object can still hold a wrong date or a hallucinated value. Keep evals and business-rule validation.
  • Still check stop_reason. A refusal or max_tokens stop can leave output that doesn't conform.
  • First-call latency. A new schema is compiled on first use and then cached, so the first request is slower.
  • JSON outputs and strict tools can be used together in one request; both replace the old prefill trick, which newer models reject.

Common trap

When a parser breaks on "almost JSON", don't add a third paragraph of formatting instructions or a regex repair step. Move format enforcement into the API with output_config.format or strict: true.

7. Adaptive Thinking

What changed

The older extended thinking mode made you allocate a fixed token budget. Adaptive thinking lets the model judge how much to reason per request; you steer depth with effort.

  • API shape: thinking={"type": "adaptive"} plus output_config={"effort": "high"}.
  • Manual {"type": "enabled", "budget_tokens": N} is deprecated on Claude 4.6 and returns 400 on 4.7 and later.
  • Migration: drop budget_tokens, switch the type to adaptive, control depth with effort.

Display and billing

  • thinking.display: "summarized" returns readable summaries; "omitted" returns an empty thinking field.
  • You are billed for the full internal thinking as output tokens either way; display changes only what you see.
  • Higher effort is not always better: it adds latency and cost. Match effort to task difficulty.
Rule in tool-use loopsWhy
Echo the assistant message exactly, including thinking and redacted_thinking blocks, when you return tool resultsThinking blocks carry a cryptographic signature; editing, summarizing or filtering them gives a 400
Keep one thinking configuration per assistant turnA tool-use loop is one assistant turn; change settings only between turns
Manual extended thinking allows only tool_choice auto or noneForced tool use is incompatible with manual mode
To save context, prune or compact older completed turnsNever "save tokens" by stripping blocks from the active turn

Common trap

Changing thinking or effort between requests invalidates the messages prompt cache (and on some models the system and tool caches too). Pick a setting per workload and keep it stable.

8. Context Window, Compaction and Prompt Caching

Prune (Compress)Drop or truncate old tool results and stale turns in your codeTool outputs dominate the history

Sub-agent handoff (Isolate)Give a bounded sub-task its own fresh messages[] array; pass an explicit context contract and return only the synthesized answer + required raw artifactsExploration, deep search, or independent verification that would flood the main context
MeasureToken-counting endpoint before sending; watch usageAlways; production payloads are larger than test fixtures

Diagnosis rule: Turn 1 vs. Turn 5+

An agent that picks the wrong tool on Turn 1 has a schema/description collision or tool bloat problem (too many overlapping tools; fix with Select / progressive disclosure or sharper descriptions). An agent that picks the right tool on turns 1–4 and the wrong one from Turn 5+ does not have a schema problem: accumulated tool_result output is crowding out instructions (fix with Compress / prune / edit / compact, not by rewriting descriptions or raising max_tokens).

Context Rot Taxonomy & Recovery

  • Context poisoning: A hallucination or faulty premise in an early turn (or tool output) is referenced repeatedly by later turns. Warning: Summarization/compaction preserves poisoned premises in condensed form—you must truncate/reset history prior to the bad turn.
  • Context confusion: Unrelated documents, logs, or 50+ unused tool definitions dilute attention and degrade accuracy. Fix via tool scoping and progressive disclosure.
  • Context clash: Contradictory instructions or superseded requirements accumulate across turns. Fix by consolidating state into a single external spec or resetting with a clean handoff.

Multi-Agent Context Contracts & Builder–Reviewer

  • Self-contained handoff: A subagent starts with a blank messages[] array—never assume it inherits parent conversation history.
  • Raw artifact return: If a downstream step needs exact code, SQL, or JSON produced by a subagent, require the subagent to write it to a shared store/file or return it verbatim rather than returning a prose summary.
  • Bounded waves & when NOT to parallelize: Dispatch parallel subagents in bounded waves (e.g., 3–5 concurrent calls) to avoid workspace 429s. Never parallelize sequential data dependencies or overlapping writes to the same state/record.
  • Builder–Reviewer separation: Run verification/code review in a separate messages.create() call with a fresh messages[] array containing only the spec and candidate artifact—never ask the same context that generated the artifact to grade its own work.

Prompt caching mechanics

  • Mark the end of a reusable prefix with cache_control: {"type": "ephemeral"}; up to 4 breakpoints per request.
  • Prefix order is tools → system → messages. A change at one level invalidates that level and everything after it.
  • Cache hits need an identical prefix: static content first, dynamic content after the last breakpoint.
  • Default TTL is 5 minutes (refreshed on use); "ttl": "1h" is optional.
  • Track cache_creation_input_tokens vs. cache_read_input_tokens in usage.

Caching economics

  • Cache write: 1.25× base input (5-min TTL) or 2× (1-hour TTL).
  • Cache read: about 0.1× base input (lower on some newer models; check pricing).
  • Break-even: a 5-min entry pays off after 1 read; a 1-hour entry after 2 reads.
  • Also cuts time to first token on long prefixes.
  • Silent invalidators: editing tool definitions, changing tool_choice, toggling images, changing thinking/effort, or swapping system output styles mid-session (invalidates both system and downstream messages caches).

Common trap

A 0% hit rate with a timestamp, user ID or ticket text placed before the breakpoint. Each request writes a new entry and never reads one. A longer TTL only makes those writes cost more; move the dynamic text after the breakpoint.

9. Message Batches

What it is
An asynchronous endpoint that accepts many Messages requests in one submission and processes them in the background at 50% of standard price (input and output).
Limits
Capped at 256 MB total payload or 100,000 requests per batch (whichever threshold is reached first). Most batches finish within an hour; anything not done in 24 hours expires.
custom_id
Required, unique per request (1–64 chars, letters, digits, _, -). Results can come back in any order, so match on custom_id, never on position.
Lifecycle
Create → poll until processing_status is ended → fetch results (each succeeded, errored, canceled or expired). Results stay downloadable for 29 days.
WorkloadBest transportWhy
Nightly classification of 40k tickets, read next morningMessage BatchesHalf price, no rate-limit fight, latency doesn't matter
Chat UI with long answersStreamingA person is waiting; perceived latency
Backend fan-out of a few hundred calls per user actionAsync client with bounded concurrencyNeeds results in seconds
Same 5k-token instructions on every batched itemBatches + prompt cachingThe discounts can be combined

Common trap

Splitting a list into chunks and calling messages.create() per item is not batching: it is serial synchronous traffic that hits rate limits. Smaller chunks or more backoff don't change that; the Batches API does.

10. Errors and Retries

Status / typeClassAction
400 invalid_request_error (bad shape, prompt too long, unsupported param, spend limit you set)TerminalFix the request; retrying the same body fails identically
401 authentication · 403 permission · 404 not foundTerminalFix key, permissions or model ID; fail fast
402 billing_error · 413 request_too_largeTerminalFix billing; shrink the payload below the endpoint's size limit
429 rate_limit_errorRetriableWait retry-after, then backoff + jitter. A spend-cap 429 has no retry-after and keeps failing
500 api_error · 504 timeout_errorRetriableExponential backoff; for 504 on long requests, stream instead
529 overloaded_errorRetriableBackoff with jitter; consider a fallback model in the orchestration layer
HTTP 200 + stop_reason: "refusal"Not an HTTP errorContent decision: handle as in §4, don't backoff-retry

SDK defaults

  • Official SDKs retry connection errors, 408, 409, 429 and ≥500 2 times by default with short exponential backoff, honoring retry-after.
  • Configure with max_retries (client-wide or per request); 0 disables.
  • Log the request-id response header for support.

Reliability placement

  • Retry: next to the call, owned by one layer.
  • Circuit breaker: at the service boundary, on aggregate error rate.
  • Fallback (other tier, cached answer, human queue): in orchestration.
  • Budgets: max turns / tool calls per agent run.

Common trap

Wrapping SDK calls in your own 5-attempt loop with default SDK settings gives up to 15 attempts per request against a rate limit. One layer owns retries. And a bare except Exception: pass retries 400s pointlessly while hiding the real error.

Eval discipline

  • Define "done" first: success criteria, failure handling, cost and latency budgets.
  • Golden set = representative inputs + edge cases + adversarial cases; refresh it whenever prompt, model or retrieval changes.
  • Judge rules: reasoning before the score, anchored score bands, preferably a different model than the one graded, agreement checked against human labels.
  • Change one variable per run; read per-case diffs, not just the mean.
  • Assert properties, never exact strings: output varies even when correct.

Model-ID pinning

  • Claude 4.6 and later: the dateless ID (e.g. claude-sonnet-4-6) is a fixed snapshot; updates ship under new IDs.
  • Earlier models: dated IDs (claude-haiku-4-5-20251001); the short alias moves to the newest dated snapshot.
  • Platform formats differ: Bedrock anthropic.claude-… (dated models end in -v1:0; optionally global. / us. / eu. prefixed), Google Cloud …@YYYYMMDD for dated models and the API format from 4.6 on.
  • Every ID has its own deprecation and retirement date.

Release discipline

  • Pin the full model ID in config, not code.
  • Keep the previous pin as the rollback target.
  • Promote a new model only when evals meet or beat the pinned baseline.
  • Feature availability differs by platform: verify each beta or tool you depend on.
  • Measure latency from the customer's region with a real payload; compare total cost (fees, egress, integration), not just token price.

Common trap

"Inference must stay in the EU" cannot be met with first-party inference_geo (global or US only). Use Bedrock regional/EU routing or the Google Cloud eu multi-region, decided at scoping because residency is pass/fail. Encryption at rest does not change where inference runs.

Compliance scoping

  • Data retention, zero-data-retention and BAA eligibility vary by feature and by platform: confirm each feature you plan to use.
  • "No training on API data" is not the same as zero retention.
  • Audit-log every tool call and decision (request, response, context, outcome) with a shared trace ID.

Common trap

"All our users are trusted employees, so injection isn't a risk." The attacker is whoever wrote the web page, email or document the agent reads. Prompt rules and bigger models are probabilistic; capability removal and pre-action authorization are not.

Reveal the Fixes (Click)

Fixes. What must change, and why?

(a) Remove temperature: non-default sampling values return 400 on Claude 4.7+. Steer with the prompt instead. (b) Replace the manual budget with thinking={"type": "adaptive"} and output_config={"effort": "high"}; budget_tokens returns 400 on 4.7+. (c) Append resp.content unchanged: filtering thinking blocks breaks the signature check on the next call. (d) Return failures as a tool_result with is_error: true and a short message, never "". (e) Put tool_result blocks first; text after. Bonus: check resp.stop_reason == "tool_use" before looking for a call, and loop over all tool_use blocks in case of parallel calls.

Glossary, Practice Quiz & Related Guides

Content block
Typed unit of a message: text, image, document, tool_use, tool_result, thinking, redacted_thinking.
stop_reason
Why generation stopped: end_turn, tool_use, max_tokens, stop_sequence, pause_turn, refusal, model_context_window_exceeded.
tool_use_id
Field on a tool_result that must equal the id of the tool_use block it answers.
is_error
Flag on a tool_result telling Claude the tool failed, so it can retry, ask, or stop instead of trusting empty data.
tool_choice
auto (default), any, tool, none; holds disable_parallel_tool_use.
Strict tool use
strict: true on a tool: inputs are guaranteed to match its input_schema.
output_config.format
JSON outputs: constrains the response text to a JSON schema.
Adaptive thinking
thinking: {type: "adaptive"}; the model sizes its own reasoning, steered by output_config.effort.
Effort
Per-request reasoning depth: low → max (set varies by model). Higher = slower and costlier.
Signature
Cryptographic field on thinking blocks; any edit makes the next request fail.
message_stop
Final streaming event; the only safe point to commit a streamed turn.
input_json_delta
Streaming fragment of tool input JSON; parse only at content_block_stop.
Cache breakpoint
cache_control marker ending a reusable prefix; up to 4 per request; TTL 5m (default) or 1h.
Compaction
Server-side summarization of older context into a compaction block so long-running agents keep going.
4 Context Strategies
Write (persist outside context), Select (progressive disclosure/scoped tools), Compress (prune/edit/compact), and Isolate (subagents with clean messages[]).
Context Rot Taxonomy
Context poisoning (hallucinated premise survives compaction; requires reset), Context confusion (unrelated docs/tools dilute attention), and Context clash (contradictory turns).
Programmatic tool calling
CodeMode pattern where the model writes a typed script executed in a capability-restricted V8 isolate to chain multiple RPC calls in a single inference turn.
custom_id
Your unique key per batched request; the only reliable way to match out-of-order results.
inference_geo
First-party residency parameter: global or us (Claude 4.6+).
Pinned model ID
An ID whose underlying model never changes; the unit of release and rollback.
Indirect prompt injection
Instructions hidden in content the app reads (pages, emails, tool output) rather than typed by the user.

Self-Assessment Questions (Click to Reveal)

Q1. Claude returns two tool_use blocks in one response. How must the next request be structured?

Append the assistant message unchanged, then a single user message whose content starts with two tool_result blocks, each with the matching tool_use_id (any text goes after them). Failed calls use is_error: true.

Q2. How do max_tokens and model_context_window_exceeded differ, and what happens when the input alone is too large?

max_tokens means the output hit your cap; raise it or continue. model_context_window_exceeded means generation filled the context window; treat it as truncated and shrink history. An input that alone exceeds the window is rejected with a 400 before generation.

Q3. Why is a refusal not handled by your retry logic, and what should the app do?

It arrives as HTTP 200 with stop_reason: "refusal", so status-based retry never sees it, and resending the same request repeats it. Read stop_details, remove or rephrase the refused turn (or reset history), or retry on a fallback model where offered.

Q4. In a streaming handler, when is it safe to parse tool input and when is it safe to commit the turn?

Accumulate input_json_delta fragments and parse at that block's content_block_stop. Commit the assistant turn to history only after message_stop; on a dropped stream, discard the partial turn.

Q5. A team migrates to a Claude 4.7+ model and gets 400s. The request sets temperature: 0.2 and thinking: {type: "enabled", budget_tokens: 6000}. What changes?

Omit the sampling parameter and steer with prompting. Replace manual thinking with thinking: {type: "adaptive"} plus output_config: {effort: ...}.

Q6. A prompt with a 6k-token static system prompt shows 0% cache reads. The breakpoint is on a system block that begins with today's date. Fix?

Move the date (and any per-request text) after the last breakpoint so the cached prefix is byte-identical across requests; keep tool_choice, tools and effort stable too. A longer TTL would only raise write costs.

Q7. An EU insurer requires inference to stay in the EU. Which deployment choices satisfy it?

Not first-party inference_geo, which supports only global or us. Use Amazon Bedrock regional/EU routing or the Google Cloud eu multi-region (both carry a regional premium), pin the model ID, and verify feature availability on that platform.

Q8. Your code wraps each SDK call in its own five-attempt retry loop. What's wrong?

The SDK already retries retriable errors twice by default and honors retry-after, so attempts multiply against a rate limit. Let one layer own retries (or set max_retries), fail fast on 4xx terminal errors, and put fallbacks in orchestration.
