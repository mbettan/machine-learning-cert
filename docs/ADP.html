Overview & Mental Model

Definition

Agentic design patterns are reusable, framework-agnostic architectural blueprints that govern how an LLM-based system decomposes work, selects control flow, invokes tools, manages context memory, coordinates across specialized workers, and defers high-stakes decisions to deterministic code or human reviewers. They apply identically across Google ADK, the Claude Agent SDK, LangGraph, or direct model API loops.

What patterns solve for

A raw language model is a stateless, probabilistic token predictor—it can propose an action, but it cannot execute tools, enforce hard business invariants, persist session state, or halt a runaway loop. Architectural patterns define who owns the control flow (deterministic code vs. dynamic model reasoning), where authority sits (code gates vs. model judgment vs. human sign-off), and how context stays clean as tasks scale.

Rule 0 — The Simplicity Ladder

The model is the probabilistic reasoning engine; the architecture is the deterministic harness (nervous system, brakes, and safety interlocks). Start with the simplest architecture that passes your evaluation suite: climb from deterministic code → a single augmented LLM call → a predefined workflow → an autonomous agent only when empirical evaluations prove the simpler tier fails.

Augmented LLMCaller (1 turn + tools)Single model call equipped with Retrieval (RAG), Tools (MCP/functions), and Memory (read/write state). Handles most production features."LLM with a backpack"

Classic architectural trap: Workflow vs. Autonomous Agent

Calling an LLM five times in a Python script does not make the system an "autonomous agent." If application code dictates the sequence, branching, and retry count, it is a workflow. It becomes an agent only when the model itself decides the next step and action trajectory at runtime.

Preventing Deterministic Drift

Deterministic drift occurs when a team delegates exact, rule-bound logic—such as calculating pro-rated subscription refunds, enforcing role-based access control (RBAC), checking date eligibility windows, or redacting Social Security Numbers—to a system prompt instead of application code.

  • Why it is dangerous: Even when a frontier model follows a prompt rule on most test cases, probabilistic token sampling guarantees a non-zero tail-risk failure rate—especially under instruction crowding (long prompts with 20+ competing rules) or adversarial prompt injection.
  • The "Deterministic Handcuffs" rule: Let the LLM extract structured parameters or propose an action, but execute all math, eligibility comparisons, permission checks, and compliance gates in plain code (PreToolUse / before_tool_callback hooks, Pydantic validators, or SQL constraints).

HITL Checkpoints vs. Programmatic Guardrails

  • Guardrail callbacks (Bucket 1 — milliseconds): Deterministic pre/post hooks enforcing PII redaction, budget caps, allowlisted paths, and JSON schemas on every turn without human latency.
  • HITL approval (Bucket 3 — seconds to hours): Planned pause before an irreversible or regulated action commits. Persist session state so the workflow can pause indefinitely and resume cleanly.
  • Concrete argument inspection: Reviewers must inspect and approve concrete tool arguments (issue_refund(order_id="ORD-891", amount_usd=490.00)), never vague model prose.
  • Avoid approval fatigue: Gate by risk tier (e.g., auto-approve refunds <= $50 in code; require HITL for > $50) so human reviewers do not rubber-stamp alerts.

Four Behavioral Properties of Probabilistic Systems

1. Non-determinism
Identical prompts can yield different phrasings or tool trajectories across runs (and modern APIs reject non-default sampling knobs or still exhibit floating-point variance). Mitigation: Test structured properties and behavioral rubrics, never exact string equality; enforce JSON schemas at the token level.
2. Plausible-sounding errors (Hallucinations)
Models are trained to complete patterns helpfully. When fed garbled OCR text, an empty string "" from a timed-out tool, or a missing policy clause, an unguarded model invents confident facts or fabricated citations. Mitigation: Pre-LLM epistemic gates, explicit is_error: true tool results, and grounded citation verification.
3. Context sensitivity & instruction crowding
Packing 30 rules, 15 irrelevant documents, and 40 tool schemas into one call degrades mid-window recall and causes the model to silently skip late audit rules. Mitigation: Split generation from verification, keep tool catalogs <= 16 per agent, and isolate noisy exploration in subagents.
4. Compounding multi-step error rates
If a single autonomous step is 95% reliable, a 10-step unverified chain succeeds only 0.95^10 ≈ 60% of the time because an early misread file poisons every subsequent turn. Mitigation: Insert ground-truth environmental feedback (compilers, unit tests, schema validators, code gates) after every step to reset the error curve.

3. The 5 Canonical Workflow Patterns

When a single call falls short due to instruction crowding, multi-stage dependencies, or latency/cost trade-offs—but the control structure can be designed upfront—compose the five canonical workflow patterns. In all five, application code owns or bounds the control flow.

PatternControl Flow ShapePrimary OptimizationCanonical Use CaseMemory Hook
1. Prompt ChainingLLM 1 → [Code Gate] → LLM 2 → LLM 3Accuracy via focused sub-steps + early fail-fastDrafting an outline → verifying structure in code → generating localized report"Assembly line with quality inspectors"

5. Evaluator–OptimizerGenerator → Critic/Auditor → (Pass | Feedback Loop [max M])Iterative quality & compliance against a strict rubricLegal clause extraction + adversarial citation auditor; literary translation refinement"Writer + strict editor"

Pattern 1: Prompt Chaining & Code Gates

  • Mechanism: Decomposes a predictable multi-stage task into sequential LLM calls where each call handles one focused transformation.
  • The Deterministic Gate (gate_check): Plain application code between steps that checks schema validity, required fields, length bounds, or citation existence before spending tokens on Step 2.
  • When NOT to use: Do not chain independent subtasks sequentially (use Parallelization — Sectioning to avoid serial latency), and do not chain tasks that a single structured prompt already passes on evals.

Pattern 2: Routing & Tier Dispatch

  • Mechanism: Classifies intent or difficulty (via a fast small model, embeddings, or rules) and dispatches to a specialized downstream prompt, scoped toolset, or model tier.
  • Model-tier cost optimization: Route high-volume routine queries to a fast tier (Haiku / Gemini Flash-Lite) at low effort, reserving frontier models (Sonnet / Opus / Gemini Pro) for complex reasoning.
  • Preventing misrouting cascades: Define an explicit ambiguous / fallback route that asks a clarifying question, log classifier confidence, and allow specialist handlers to reject misrouted inputs back to triage.

Pattern 3: Parallelization (Sectioning vs. Voting)

  • Sectioning (Speed & Focus): Splits a task into independent subtasks executed concurrently via asyncio.gather / ParallelAgent (e.g., extracting financial metrics, legal risks, and timeline milestones in parallel, or running input/output guardrail screening concurrently with the main response). Each branch must write to a distinct output_key to avoid state overwrites.
  • Voting (Confidence & Consensus): Runs the same task multiple times—either sampling identical prompts at T > 0 (Self-Consistency CoT for math/logic) or running diverse critique prompts—and aggregates programmatically. Tune vote thresholds to risk: use 1-of-N (any flag) for high-recall vulnerability detection, or majority vote for high-precision labeling.

Pattern 4: Orchestrator–Workers

  • Mechanism: A central Orchestrator LLM analyzes the request, dynamically invents a structured list of subtasks at runtime, dispatches scoped Worker LLMs in parallel waves, and synthesizes their compact outputs.
  • Key distinction vs. Parallelization: Topological shape is similar (fan-out → fan-in), but in Parallelization the subtasks are hardcoded in advance, whereas in Orchestrator–Workers the subtasks are decided dynamically at runtime by the model based on the specific input (e.g., choosing which 5 files in a repository need edits).
  • Spec-Driven Planner → Executor split: Use a high-capability model for the read-only orchestrator planning pass, then dispatch balanced/fast-tier workers in fresh context windows for execution.

Pattern 5: Evaluator–Optimizer & Separation of Authority

Pairs a Generator LLM with an independent Evaluator / Critic LLM that grades the draft against an explicit rubric and returns actionable feedback in a loop.

  • When it fits: (1) Responses measurably improve when a human articulates feedback, and (2) an LLM + deterministic checks can reliably produce that feedback.
  • Separation of Authority: Never ask a generator prompt to grade its own output in the same context window (confirmation bias). Run the critic in a clean context window (include_contents='none') with an adversarial rubric and pair it with deterministic code verification (e.g., verifying cited sections exist in source text).
  • Bounded convergence: Cap loops with max_iterations (typically 2–3) and an explicit approval signal. If max_iterations trips without approval, fail closed to HITL escalation rather than shipping an unapproved draft.
def run_evaluator_optimizer(source_doc: str, max_iterations: int = 3) -> dict:
    feedback = None
    for attempt in range(1, max_iterations + 1):
        draft = call_generator_llm(source_doc, prior_feedback=feedback)

        # Deterministic gate first: verify every cited section heading exists in source_doc
        missing_refs = [c.section_heading for c in draft.citations if c.section_heading not in source_doc]
        if missing_refs:
            feedback = f"Cited sections missing from source text: {missing_refs}"
            continue

        # Cold-context adversarial critic (sees only source_doc, draft, and rubric)
        verdict = call_critic_llm(source_doc=source_doc, draft=draft)
        if verdict.approved:
            return {"status": "approved", "output": draft, "iterations": attempt}
        feedback = verdict.actionable_critique

    # Max iterations reached without passing rubric -> fail closed to HITL escalation
    return {"status": "escalation_required", "draft": draft, "reason": feedback}

4. Autonomous Agent Primitives & Reasoning Loops

When the number and sequence of steps cannot be predicted in advance—because step N+1 depends on what observation N uncovered—an Autonomous Agent drives its own execution loop using environmental ground truth.

Reasoning ParadigmExecution MechanicsStrengthsFailure Mode & When to Avoid
ReAct (Reason + Act)Interleaves Thought → Action (tool call) → Observation (ground-truth tool result) turn-by-turn.Maximum adaptability; each action is chosen from the immediate observation of the prior step.High sequential latency (O(N) LLM turns); context grows every turn; can drift into local rabbit holes without an externalized checklist.
Plan-and-Execute (ReWOO / LLMCompiler)Planner emits an upfront multi-step plan or dependency DAG of symbolic variables (#E1, $1); Executor/Dispatcher runs ready steps concurrently; Solver/Replanner synthesizes or replans on failure.Cuts sequential latency and token re-ingestion dramatically by executing independent tool calls in parallel without intermediate LLM turns.Brittle if early observations invalidate the upfront plan; requires a dynamic replanning trigger when unexpected environment state appears.
Reflection / Self-CorrectionAgent inspects deterministic feedback (compiler error, failing pytest trace, schema violation) and revises its action or draft before finishing.Automatically resolves syntax, schema, and localized logic bugs when grounded in objective test/validator output.Ungrounded reflection drift: Asking a model to "reflect and improve" without external ground truth (tests, linters, search) often degrades accuracy or amplifies hallucinations.

Stopping Conditions & Loop Hygiene

  • 1. Objective exit criteria: Define concrete completion conditions (tests pass, schema validates, or explicit finish_task / end_turn).
  • 2. Hard iteration caps (max_turns / max_llm_calls): Always bound total turns per invocation so a stuck agent halts deterministically (error_max_turns).
  • 3. Token & spend budgets (max_budget_usd): Track cumulative token cost per session and abort or escalate before runaway spend occurs.
  • 4. Duplicate tool-call detection: Hash (tool_name, canonical_json_args) across turns. If an agent repeats the exact same failing or no-op call 2–3 times, block execution in the harness and inject a loop-breaker error telling the model to change strategy or escalate.
  • 5. Structured error feedback (is_error: true): Never swallow exceptions as "" (which looks like "0 records found"). Return structured error details (error type, retryability, corrective hint) inside the tool result so the model can adapt.

ACI Design & Poka-Yoke (Mistake-Proofing)

Invest as much engineering rigor in your Agent-Computer Interface (ACI) as in human UX:

  • Junior-developer docstrings: State clearly what the tool does, when to use it, when not to use it (pointing to the right sibling tool), parameter formats, and output limits.
  • Poka-Yoke arguments: Shape tool schemas so invalid calls are impossible—e.g., require absolute file paths (/workspace/src/main.py) instead of relative paths that break after directory changes, and use strict Literal / enum types instead of free-text strings.
  • Keep tool catalogs small (<= 16 tools): Tool selection accuracy drops sharply when an agent must choose among dozens of overlapping tools; split by domain across subagents or use on-demand tool search.
def run_bounded_agent_loop(messages: list, max_turns: int = 12, max_usd: float = 0.50) -> dict:
    seen_calls: dict[tuple[str, str], int] = {}
    spent_usd = 0.0

    for turn in range(1, max_turns + 1):
        if spent_usd >= max_usd:
            return {"status": "stopped", "reason": "budget_ceiling_exceeded", "turns": turn - 1}

        resp = call_model(messages=messages, tools=TOOL_SCHEMAS)
        spent_usd += estimate_cost(resp.usage)
        messages.append({"role": "assistant", "content": resp.content})

        if resp.stop_reason == "end_turn":
            return {"status": "completed", "answer": extract_text(resp.content), "turns": turn}

        if resp.stop_reason == "tool_use":
            tool_results = []
            for block in [b for b in resp.content if b.type == "tool_use"]:
                sig = (block.name, json.dumps(block.input, sort_keys=True))
                seen_calls[sig] = seen_calls.get(sig, 0) + 1
                if seen_calls[sig] >= 3:
                    tool_results.append({
                        "type": "tool_result", "tool_use_id": block.id, "is_error": True,
                        "content": f"Loop breaker: {block.name} called 3x with identical args. Try another approach or escalate."
                    })
                    continue
                try:
                    out = execute_tool_safely(block.name, block.input)
                    tool_results.append({"type": "tool_result", "tool_use_id": block.id, "content": out})
                except Exception as exc:
                    tool_results.append({
                        "type": "tool_result", "tool_use_id": block.id, "is_error": True,
                        "content": f"{type(exc).__name__}: {exc}. Check parameter constraints or escalate."
                    })
            messages.append({"role": "user", "content": tool_results})

    return {"status": "stopped", "reason": "max_turns_exceeded", "turns": max_turns}

5. Memory Architecture & Context Budget Engineering

A large context window is not a substitute for memory architecture. Stuffing raw transcripts, 50 KB tool responses, and 80 tool schemas into every turn inflates cost and latency while causing Context Rot.

4. Context Rot Taxonomy: Poisoning vs. Confusion vs. Clash

  • Context Poisoning: An early hallucination, wrong file path, or refused turn enters messages[] and gets repeatedly referenced on later turns. Critical trap: Running summarization/compaction on a poisoned session preserves the poisoned assumption inside the summary block! Fix by rewinding prior to the bad turn or clearing/resetting into a fresh context window with only verified facts.
  • Context Confusion: Unrelated file dumps, bulky 50 KB JSON tool payloads, and dozens of unused tool schemas dilute model attention. Fix by paginating/pruning tool outputs, deferring tool schemas behind search, and delegating noisy exploration to subagents.
  • Context Clash: Contradictory rules across global prompts, path rules, and multi-turn instructions cause unpredictable behavior. Fix by scoping rules via path globs and resolving conflicts in an upfront spec.

The 4 Context Strategies & Compaction Mechanics

  • 1. Write (Externalize): Save plans, checklists, and large generated artifacts to typed state keys, disk files, or an ArtifactService outside messages[].
  • 2. Select (Just-in-Time): Retrieve narrow file line ranges (Grep → paginated Read), path-scoped rules, and on-demand skills only when needed.
  • 3. Compress (Compaction & Pruning): Strip verbose historical tool payloads once key fields are extracted, and trigger summarization checkpoints (Compaction) at 70–80% window capacity while retaining the last K turns verbatim (sliding window overlap). Keep the static prompt prefix byte-identical (no per-call timestamps at the top!) so prompt caching cuts input token cost by 75–90%.
  • 4. Isolate (Subagents): Offload high-volume exploration or independent verification to subagents with fresh messages[] arrays.

6. Multi-Agent Topologies & Handoff Contracts

The "Agent Theater" Litmus Test

Multi-agent orchestration is justified if and only if subagents have distinct tools or permissions, private data scopes, isolated context windows to contain noisy exploration, parallel I/O, or an independent verification role. Chaining three "persona" prompts that share the exact same tools and context is Agent Theater—multiplying token cost (~4×) and latency (1.5–2.5×) for zero architectural gain.

TopologyControl & Routing MechanicsStrengthsKey Risks & Required Safeguards
1. Hub-and-Spoke (Coordinator / Subagents)Central coordinator decomposes the request, invokes specialist subagents as tools (AgentTool / Task), collects compact results, and synthesizes the final response.Central visibility, strict context isolation per spoke, easy to enforce hub-level guardrails and wave limits (3–5 concurrent workers).Coordinator context overflows if spokes return raw 50 KB dumps instead of structured summaries. Block subagents from spawning recursive subagents unless explicitly needed.
2. Sequential PipelineFixed relay (Agent 1 → Gate → Agent 2 → Agent 3) passing state via explicit keys (output_key + output_schema).Zero routing overhead; deterministic transitions; ideal for Staged Extract → Redact → Analyze → Format pipelines.Rigid; if Step 1 misclassifies an input and no deterministic gate catches it, Steps 2 and 3 compound the error.
3. Mesh / Debate / SwarmPeer specialists transfer control directly to one another (transfer_to_agent) or critique each other's proposals without a central hub.Useful for adversarial red-teaming, multi-perspective design critique, or seamless specialist conversation handoffs.Highest risk of infinite ping-pong loops, state corruption, and diffusion of responsibility. Requires strict max_turns, explicit exit tools, and a deterministic tie-breaker/judge.
4. Hierarchical TeamsMulti-tier tree where a root orchestrator delegates to domain leads, which in turn manage narrow execution workers.Scales to large enterprise systems with dozens of tools by keeping each node's tool catalog <= 16.High cumulative latency and token spend; trace debugging requires correlation IDs across every parent-child boundary.

The Context Isolation Rule

  • Fresh, task-scoped context by default: When a coordinator delegates a task (codebase search, diff audit, SQL analysis) to a subagent, the subagent must execute in a fresh context window containing only its specialist system prompt and explicit task input—never inheriting the coordinator's noisy 80-turn history. (Use full-history context forking only when the child explicitly requires the exact prior transcript and shared prompt cache.)
  • No shared mutable scratchpads in parallel waves: When running 3–5 parallel workers, assign each worker a distinct output_key or isolated file/worktree path so concurrent writes never race or overwrite one another.
  • Artifact pointer pattern: Because only a subagent's final message returns to the parent, workers generating large diffs or tables must write the full payload to disk or an ArtifactService (artifact_uri) and return only a compact HandoffContract summary to the coordinator.

Vertical (MCP) vs. Horizontal (Subagents / A2A)

  • Vertical execution (Agent → Tool/Data via MCP): Equips an agent with deterministic tools, database queries, and resources. Enforce least privilege with tool_filter allowlists and scrub PII/injections in after_tool_callback.
  • Horizontal in-process (Coordinator → Subagent): Cognitive delegation inside the same runtime via AgentTool / Task with fresh context and typed output schemas.
  • Horizontal cross-boundary (Agent → Remote Agent via A2A): Delegates stateful tasks across organizational boundaries via an AgentCard (/.well-known/agent-card.json). Remote A2A agents are opaque black boxes (they never expose internal tools, prompts, or memory)—authenticate via card securitySchemes and validate all returned artifacts as untrusted input.

7. Anti-Patterns, Failure Modes & Architectural Checklist

Production Trust Architecture: Why Single-Prompt "Happy-Path" Prototypes Fail

While a single multimodal LLM call with a JSON schema can summarize a clean 1-page demo PDF in 2 seconds, unguarded single-prompt pipelines break on real enterprise workloads for five structural reasons:

  • 1. Token burn & hallucinations on corrupted inputs (Missing Epistemic Gate): Sending a 120-page blurry scan or wrong document type directly to a frontier model wastes tokens and invites hallucination. Fix: Run a $0 deterministic Pre-LLM Epistemic Gate checking file metadata and a composite extraction quality score (OCR token confidence, lexical dictionary ratio, character entropy, structural page completeness); if below threshold, escalate immediately without calling the LLM.
  • 2. Instruction crowding & self-grading bias: Packing 30 extraction rules and compliance checks into one prompt causes the model to focus on fluent generation and silently skip late verification rules. Even well-tuned prompts remain probabilistic, whereas a deterministic Python post-check paired with a cold-context critic enforces hard invariants reliably.
  • 3. Unverified citations: Format checks only verify that (Source: Section X) syntax appears, missing fabricated section numbers. Fix: Grounded citation verification deterministically checks that every cited heading/quote exists in the extracted source text.
  • 4. Cloud PII exposure: Sending raw unredacted documents directly to external APIs leaks sensitive PII before prompt rules run. Fix: Parse locally and scrub PII deterministically at the pre-LLM and after_tool_callback boundaries.
  • 5. Rule drift across repos: Copy-pasting compliance prompts across services guarantees drift. Fix: Centralize domain validators, prompts, and policy thresholds in a shared MCP server (Rules as Infrastructure).

8-Point Pre-Production Architectural Checklist

  • 1. 3-Bucket Triage Verified: Are all math, schema validation, RBAC, and hard compliance rules executed in deterministic code (Bucket 1), and all high-blast-radius irreversible actions gated by HITL (Bucket 3)?
  • 2. Complexity Ladder Justified: Have you proven with an evaluation baseline that a single Augmented LLM call or deterministic Workflow cannot meet the bar before deploying an Autonomous Agent?
  • 3. Pre-LLM Epistemic Gating Active: Does deterministic code validate file types, input completeness, and composite extraction quality before spending model tokens, with escalation_required = True as the safe default?
  • 4. Loop Hygiene Enforced: Does every agent and evaluator-optimizer loop enforce max_turns / max_iterations, token budget ceilings, duplicate tool-call detection, and explicit escalation when the cap trips?
  • 5. ACI & Poka-Yoke Hardened: Are tool catalogs <= 16 per agent, arguments constrained via strict schemas/enums/absolute paths, and failures returned as structured is_error: true signals?
  • 6. Context Budget & Cache Optimized: Are static instructions and tool definitions placed before dynamic per-request data for cache stability, and is noisy exploration isolated in subagents?
  • 7. Handoff Contracts Typed: Do subagents run in fresh, task-scoped context windows and return compact, schema-validated HandoffContract objects (with URIs for large artifacts)?
  • 8. Separation of Authority & Trajectory Evals: Are high-stakes outputs verified by an independent cold-context critic + deterministic code checks, and does CI evaluate both final answers and tool trajectories?

8. Glossary, Self-Assessment & Practice Quiz

3-Bucket Work Decomposition
Triage framework dividing logic into Bucket 1 (Deterministic Code) for math/validation/RBAC, Bucket 2 (Probabilistic LLM) for unstructured synthesis/planning, and Bucket 3 (HITL) for irreversible or accountability-bearing decisions.
4-Decision Sequence
Ordered architectural triage run before prompt writing: (1) Should an LLM be used at all? → (2) What work shape fits? → (3) How is it routed/hosted? → (4) What guardrails and verification wrap it?
5-Factor Pattern Matrix
Rubric comparing Single Call, Composable Workflow, and Autonomous Agent across path predictability, latency budget, error blast radius, token cost ceiling (~1× vs. 3–5× vs. ~15×), and auditability.
Deterministic Drift
Silent reliability failure caused by delegating exact arithmetic, schema validation, or policy enforcement to probabilistic prompt instructions instead of deterministic code.
Augmented LLM
The foundational building block of agentic systems: a single LLM call equipped with retrieval, tools (often via MCP), and memory.
Prompt Chaining & Gate
Sequential workflow decomposing a predictable task into fixed LLM steps separated by deterministic plain-code checks (gate_check) that fail fast on invalid intermediate outputs.
Routing
Workflow pattern that classifies an input's intent or complexity and dispatches it to a specialized prompt, scoped toolset, or cost-appropriate model tier.
Parallelization (Sectioning vs. Voting)
Running concurrent LLM calls either on independent subtasks for speed/focus (Sectioning) or repeating the same task for consensus/high-recall verification (Voting).
Orchestrator–Workers
Workflow pattern where a central LLM dynamically decomposes an unpredictable task at runtime, dispatches scoped workers, and synthesizes their results.
Evaluator–Optimizer
Workflow pattern pairing a generator LLM with an independent critic/auditor LLM (plus deterministic checks) in a rubric-driven loop bounded by max_iterations.
ReAct vs. Plan-and-Execute
ReAct interleaves Thought → Action → Observation sequentially for exploratory tasks; Plan-and-Execute (ReWOO / LLMCompiler) plans a step list or symbolic DAG upfront and runs independent tools concurrently.
ACI & Poka-Yoke
Agent-Computer Interface design and mistake-proofing: crafting junior-dev docstrings, strict enums, and unambiguous parameters (e.g., absolute file paths) so invalid tool calls cannot occur.
4-Tier Memory Model
Working (in-window scratchpad), Episodic (session transcripts/checkpoints), Semantic (consolidated RAG/Memory Bank facts), and Procedural (system instructions, rules, progressive-disclosure Skills).
Context Rot (Poisoning / Confusion / Clash)
Poisoning (hallucinated premise survives in history; requires rewind/clear, not compaction), Confusion (bulky tool dumps dilute attention), and Clash (contradictory instructions).
Context Isolation Rule & HandoffContract
Subagents execute in fresh, task-scoped context windows rather than inheriting the coordinator's noisy history, returning a compact schema-validated HandoffContract (with artifact_uri pointers for large outputs).
Epistemic Gating & Separation of Authority
Epistemic gating blocks corrupted/unreadable inputs in code before calling the LLM; Separation of Authority pairs generation with an independent cold-context critic and deterministic citation checks.

Self-Assessment Questions (Click to Reveal)

Q1. What is the 4-Decision Sequence, and why must it run before prompt engineering?

(1) Should an LLM be in the loop at all? (3-Bucket decomposition: Deterministic Code vs. Probabilistic LLM vs. HITL), (2) What work shape fits? (Single Call vs. Workflow vs. Autonomous Agent), (3) Where and how is it routed/hosted? (model tiers, effort, batch/stream, residency), and (4) What deterministic guardrails and verification wrap it? Running this sequence first prevents delegating exact math/RBAC to prompts (deterministic drift) or building a 15× token autonomous agent where a 2-step workflow suffices.

Q2. How do Parallelization (Sectioning), Parallelization (Voting), and Orchestrator–Workers differ?

In Parallelization (Sectioning), the task is split into predefined, independent subtasks (e.g., running a safety screen alongside answer generation) to cut wall-clock latency. In Parallelization (Voting), the same task runs multiple times (diverse prompts or multi-sample self-consistency) and aggregates via vote thresholds to boost confidence/recall. In Orchestrator–Workers, the subtasks are not known in advance—a central orchestrator LLM inspects the input at runtime, dynamically invents the worker task list, dispatches scoped workers, and synthesizes their outputs.

Q3. Why does asking a single prompt to both generate a 30-page contract summary and verify every citation fail at scale, and what pattern fixes it?

Packing generation and strict auditing into one prompt causes instruction crowding (attention dilution) and self-grading confirmation bias—the model prioritizes fluent generation and rationalizes or skips late audit rules. Fix it with Evaluator–Optimizer + Separation of Authority: pair the generator with a separate critic in a clean context window (include_contents='none') backed by a deterministic code gate that verifies every cited section header exists in the source text, bounded by max_iterations and HITL escalation on failure.

Q4. When should you choose Plan-and-Execute (or ReWOO / LLMCompiler) over a standard ReAct loop?

Use ReAct when the task is exploratory and step N+1 cannot be predicted until step N's observation returns (e.g., debugging an unknown production outage). Choose Plan-and-Execute / ReWOO / LLMCompiler when the required subtasks or dependency DAG can be planned upfront and executed concurrently—avoiding O(N) sequential LLM turns and repetitive prompt re-ingestion.

Q5. A coding session hallucinates a non-existent helper module in turn 3 and spends the next 6 turns failing to import it. Why is context compaction (/compact) the wrong fix, and what should you do instead?

This is context poisoning. Compaction summarizes the existing conversation history, which preserves the hallucinated premise inside the summary block so the agent continues acting on it. Instead, rewind to the checkpoint prior to turn 3 or clear/reset into a fresh context window carrying over only verified facts.

Q6. What is the Context Isolation Rule in multi-agent systems, and how should a worker return a 40 KB generated report to its coordinator?

A subagent must receive a fresh, task-scoped context window containing only its specialist instructions and explicit task inputs—never the coordinator's full noisy conversation transcript. Because only the subagent's final message returns to the parent, it should write the 40 KB report to disk or an ArtifactService and return a compact, schema-validated HandoffContract containing a short summary, status, verified citations, and the artifact_uri pointer.

Q7. During an evaluator–optimizer loop with max_iterations=3, the critic rejects the draft on all 3 attempts. What must happen next?

Many frameworks exit a loop silently when max_iterations trips. The exit tool must explicitly set an approval flag (approved = True) when the critic passes; a downstream deterministic gate checks that flag and, if False after iteration 3, halts automatic delivery and routes the draft + critic diagnostics to Human-in-the-Loop (HITL) escalation or a safe fallback.

Q8. What is the "Agent Theater" litmus test?

Multi-agent orchestration is justified if and only if subagents have distinct tools/permissions, private data scopes, isolated context windows to contain noisy exploration, parallel I/O, or an independent verification role. Wrapping multiple persona prompts in a sequential relay with identical tools and shared context is Agent Theater—multiplying token cost and latency without improving reliability.
