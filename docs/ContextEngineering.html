00

Overview

Definition

Context engineering is the per-call discipline of choosing which tokens enter a model's finite context window (instructions, tool definitions, working state, retrieved material, history and tool results), in what form and in what order, and what is moved outside the window so a long-running agent stays coherent after hundreds of turns.

What context engineering solves for

A model is stateless: at each step it sees only what the harness placed in the window for that call. Agents running in a loop keep producing tokens (tool payloads, reasoning, drafts) and most of them stop mattering a few turns later. Left alone, the window fills, recall of the details that still matter drops, and the agent either hits the hard limit or slowly drifts away from its instructions. Context engineering keeps the window small, current and high-signal for the whole run.

Mental model

treat the window like a kitchen counter during a long dinner service. Only the ingredients for the dish being plated stay on the counter; finished pans go to the sink (clearing), prep notes go on the whiteboard (scratchpad), the pantry is opened only when a recipe calls for something (just-in-time retrieval), and a second cook works a separate station (subagent).

Prompt vs. Context vs. Memory

Layer/approachTypeRole & behavior
Prompt engineeringAuthoringWording, structure and examples of one instruction; written once, reused on every call
Context engineeringPer-turn curationSelects, orders, compresses, offloads and isolates everything in the window on every call
StateExact working dataKey/value values the harness reads and writes deterministically (IDs, flags, step outputs)
ScratchpadAgent-written notesFiles the agent writes and re-reads during a task (plan, progress, open questions); outlives a context reset, usually not the task
MemoryLong-term recallFacts extracted across sessions and fetched by search or a memory tool; recall is probabilistic and can be stale
Retrieval (RAG)Shared knowledgeDocuments valid for every user (policies, manuals), fetched up front or on demand

Context levers

  • Trim drops the oldest turns once the window passes a size (a sliding window over history).
  • Summarize replaces a span of older turns with a digest that sits in front of the recent turns (summary prefix, compaction).
  • Clear removes stale tool results or thinking blocks while leaving the rest of the conversation intact (context editing).
  • Offload writes information to a file, state or memory and keeps only a handle (path, key, query) in the window.
  • Fetch late keeps references instead of payloads and loads data with a tool when a step needs it (just-in-time retrieval).
  • Isolate gives a noisy subtask its own window (subagent or agent-as-tool) and brings back a short digest.
  • Mapping to the common framing: offload corresponds to write, fetch late to select, trim, summarize and clear to compress, and isolate to isolate (the four strategies in the Agentic design patterns guide).

Key rule

every token draws on the same attention budget. A bigger window raises the ceiling, but irrelevant tokens still lower recall of the relevant ones, so the goal is the smallest set of high-signal tokens for the current step.

Per-turn assembly workflow

  1. Load: read session events, the working state for this task and, if the task uses one, the current scratchpad.
  2. Reduce: apply the history policy (sliding window, summary prefix or compaction) and clear tool results that can be re-fetched.
  3. Fetch: pull in only the documents or memories the next step needs, or expose search tools and let the agent decide.
  4. Place: stable prefix first, then working state and the summary prefix, then recent turns, then the current input.
  5. Call: count tokens when close to the limit and reserve room for the output.
  6. Offload: after the call, write new decisions to state or the scratchpad and replace bulky results with handles.

When not to engineer context

  • Short, single-turn tasks: one well-written prompt with the needed document is enough; compaction, notes and memory add cost with no benefit.
  • Everything fits and stays relevant: a 20-turn chat with small tool results needs no trimming; measure before adding machinery.
  • Shared reference knowledge: put it in retrieval or the stable prefix, not in per-user memory.
02

Context budget and placement

Budget arithmetic

  • The window holds input and output: system prompt, tool definitions, history, tool results and the reply all count; reserve output headroom (max_tokens on Claude, max_output_tokens on Gemini) before filling the rest.
  • Window sizes differ by model: current Claude models default to a 1M-token window with up to 128k output tokens, while legacy models keep 200k; check the model page rather than assuming.
  • Count, don't guess: Claude exposes a token counting endpoint (POST /v1/messages/count_tokens, returning input_tokens) and Gemini exposes count_tokens; character heuristics (about four characters per token in English) are only rough planning numbers.
  • Recount when you switch models: tokenizers change between model generations (Anthropic documents roughly 30% more tokens for the same text with the tokenizer introduced in Opus 4.7), so a prompt that fit before can overflow or cost more after an upgrade.
  • Let the agent see its budget: recent Claude models receive a context-awareness note after tool calls with tokens used and remaining, which helps them wrap up or write notes before the limit.
  • Tool definitions are a fixed tax: every tool schema is sent on every call. A bloated tool set also creates ambiguous choices; if an engineer cannot say which tool fits a situation, the model cannot either. Keep a minimal set per agent.
  • Context rot: recall of a specific detail degrades gradually as total tokens grow, well before the hard limit. Treat the usable window as smaller than the advertised one.

Placement

  • Position effect: models use information at the start and end of a long input more reliably than material buried in the middle (Liu et al.). Keep the instruction that governs the step near an edge.
  • Long documents first, question last: for large inputs, place documents above the instructions and the question at the end; Anthropic's long-context guidance reports better answers with this order.
  • Label what you place: wrap documents and notes in named sections or XML-style tags (<notes>, <document source="..." date="...">) so the model can refer to them precisely.
  • Prompt altitude: write instructions specific enough to steer behavior but general enough to act as heuristics. Hard-coded if-else rules are brittle; vague guidance assumes context the model does not have.
  • Examples over rule lists: a few diverse, canonical examples steer more reliably per token than a long list of edge-case rules.

Note

Directional figures: the "about four characters per token" heuristic and vendor-reported quality gains from document placement are rules of thumb. Measure on your own prompts with the token counting APIs and an evaluation set.

03

Long sessions: sliding windows, summary prefixes and compaction

Symptoms of an overloaded session

  • Generic answers: the agent talks about "the usual approach" instead of the specific file, ticket or decision it found earlier.
  • Instruction drift: a rule stated early stops being applied after many large tool calls.
  • Repeated work: the agent re-runs searches whose results it already has, because those results are buried or were dropped without a trace.

History policies

PolicyHow it worksKeepsLosesFits
Sliding window (trimming)Send only the last N turns or last K tokens; drop older turnsRecent detail, verbatimEverything older, abruptlyChat where old turns rarely matter
Summary prefixA rolling digest of older turns is placed before the recent window and refreshed as turns age outGist of older turns plus recent detailExact wording of summarized turnsAssistants with long back-and-forth

  • Sliding windows are cheap but blunt: they need no extra model call, yet a constraint stated in turn 3 disappears at turn 3 + N. Anything that must survive belongs in the system prompt, state or a notes file, never only in early turns.
  • Summary prefixes trade fidelity for continuity: the digest is generated by a model, so it paraphrases. Keep values that must stay exact (amounts, IDs, deadlines) in state or a scratchpad that the summarizer never rewrites.
  • Compaction is the usual first lever for long agent runs: Anthropic describes Claude Code compaction as summarizing the history while keeping architectural decisions, unresolved bugs and implementation details, discarding redundant tool output, and continuing with the summary plus the five most recently accessed files.

Tuning a compaction prompt

  1. Collect real traces: pick long, messy runs where a later step depended on an early detail.
  2. Maximize recall first: write the summary instructions so nothing that a later step used is dropped.
  3. Then raise precision: remove categories of content the agent never needed again (raw tool payloads, superseded drafts).
  4. Re-test on new traces: overly aggressive summaries lose details whose importance appears only later.

Common trap

relying on early turns to carry a rule once a sliding window or compaction is enabled. Restate durable rules in the system prompt or a re-read file such as CLAUDE.md, so trimming can never remove them.

04

Tool-result clearing and context editing

  • Lightest-touch compaction: once a tool result has been read and acted on, the agent rarely needs the raw payload again. Clearing it frees space without asking a model to rewrite anything, which is why Anthropic describes tool-result clearing as one of the safest forms of compaction.
  • Calls stay visible: by default Claude clears only the tool results and keeps the original tool calls, so the agent still knows what it asked for and can call the tool again if it needs the data.
  • Token-efficient tools reduce the need to clear: tools that paginate, filter on the server and return handles to large objects put fewer tokens in the window to begin with.

  • Protect tools whose results stay relevant: list them in exclude_tools (a memory tool, a configuration lookup that the whole task depends on).
  • Pair clearing with notes: when the memory tool is enabled and the context approaches the clearing threshold, Claude receives an automatic warning so it can save important information to memory files first, then look it up later instead of keeping it in the window.
  • Mind the cache: clearing tool results invalidates the cached prefix from the cleared point. Use clear_at_least so each clearing event frees enough tokens to justify the cache write.
  • ADK equivalent: there is no built-in clearing strategy; prune or rewrite history in a before_model_callback, or store bulky outputs as artifacts and keep a reference in the event.

Scenario: shipment tracing at Larchmont Freight

A tracing agent calls a carrier API about 40 times per investigation; each response is a large JSON document.

  • Before: after 25 calls the window is mostly raw carrier responses and the agent stops applying the customer's "ground only" constraint.
  • After: tool-result clearing triggers at 60k input tokens and keeps the last four results; the shipment_policy lookup is excluded from clearing; the agent writes each confirmed scan event to a trace.md notes file as it goes.
  • Outcome: the window stays under the trigger for the rest of the run, the constraint stays visible and earlier findings remain one file read away.

Common trap

clearing with no breadcrumb. If an agent sees neither the result nor a placeholder or note, it assumes the lookup never happened and repeats it.

05

Scratchpads and structured note-taking

  • Definition: the agent periodically writes notes to storage outside the window (a NOTES.md, a to-do list, a progress file) and reads them back when it needs them, typically after a compaction, a context reset or a new session.
  • Why it works: notes give persistence with little overhead. A short progress file carries goals, completed steps and dependencies across dozens of tool calls that would otherwise be trimmed or summarized away.
  • Agent-written, agent-read: unlike state, which the harness owns, the scratchpad is curated by the agent itself, which decides what is worth remembering.
# trace.md (agent scratchpad)
Goal: locate pallet LF-88213; customer requires ground transport only
Done: origin scan Reno 11-02 06:10; hub scan Denver 11-03 21:44
Open: no scan since Denver; carrier ticket CT-5512 pending
Next: query Denver hub scan log; re-check ticket at 14:00

Vendor mechanisms

  • Claude memory tool (memory_20250818) is client-side: Claude issues view, create, str_replace, insert, delete and rename commands against a /memories directory that your application stores. With the tool enabled, Claude is instructed to check the directory before starting and to record progress as it works.
  • Claude Code keeps durable project guidance in the CLAUDE.md hierarchy and auto memory (MEMORY.md); a plain notes file in the repository works as a task scratchpad.
  • ADK offers temp: state for values that live only within one invocation, session state for task progress, and artifacts (ArtifactService) for larger, versioned notes files.

Note-taking workflow

  1. Seed: at task start, create the notes file with the goal and constraints.
  2. Append at milestones: after each confirmed finding or decision, write one line; avoid logging every tool call.
  3. Re-read at boundaries: after compaction, clearing or a new session, read the file before acting.
  4. Prune: collapse completed sections so the file itself stays small.
  5. Close out: delete the ephemeral parts and promote only durable lessons to long-term memory.
  • Anti-pattern (notes as a transcript): copying raw tool output into the scratchpad recreates the bloat the file was meant to avoid.
  • Anti-pattern (ephemeral notes promoted wholesale): turning a task's working notes into permanent memory fills future sessions with stale hypotheses.
06

Just-in-time retrieval

  • Up-front retrieval embeds and searches a corpus before inference and pastes the top results into the window. It is fast at run time, but the agent receives whatever the retriever ranked highly, relevant or not, and the index can be stale.
  • Just-in-time retrieval keeps lightweight identifiers (file paths, stored queries, URLs, record IDs) and loads the data with a tool only when a step needs it. Anthropic describes agents writing targeted queries and using commands like head and tail on large data instead of loading whole objects into the window.
  • Metadata is signal: folder names, file sizes, naming conventions and timestamps tell the agent what a reference is for before it opens it.
  • Progressive disclosure: each lookup informs the next, so the agent assembles understanding layer by layer and keeps only what the current step needs in the window.

Up-front vs. Just-in-time vs. Hybrid

ApproachLatencyFreshnessRiskFits
Up-frontLowest at run timeAs fresh as the indexWindow filled with loosely relevant chunksStable corpora, single-shot Q&A
Just-in-timeHigher (extra tool calls)Reads the source directlyWasted calls and dead ends without good tools and heuristicsCodebases, large datasets, fast-changing sources
HybridMediumMixedTwo systems to maintainSome essentials preloaded, the rest explored on demand
  • Hybrid in practice: Claude Code drops CLAUDE.md files into the window at start, then uses glob and grep style tools to find and open files just in time, which avoids stale indexes.
  • Give the agent good handles: list or search tools that return names, sizes and short previews, plus read tools with ranges or pagination, keep exploration cheap.
  • Cap exploration: set a tool-call budget or ask for a plan before broad searches, so the agent does not burn context on dead ends.

Scenario: policy lookups at Fernhill Insurance

An underwriting assistant answers questions over 3,000 policy documents that change weekly.

  • Before: each question preloads the top 20 chunks from a nightly vector index; answers sometimes quote last week's wording and the window carries about 30k tokens of loosely related text.
  • After: the assistant starts with a short catalog (product line, document ID, effective date) and opens only the two or three documents it selects, reading the relevant section by heading.
  • Outcome: answers cite the current version, and the per-question context shrinks to the sections actually read.

Memory write policy

  • Extract at boundaries: generate memories at session end or at task milestones (ADK: add_session_to_memory on a Memory Bank service, which calls GenerateMemories in the background), not on every turn.
  • Consolidate, don't append: a new fact that contradicts an old one updates it ("moved to Lyon" replaces "lives in Paris"); Memory Bank consolidates extracted facts against existing memories in the same scope, while append-only stores accumulate contradictions.
  • Direct writes for explicit facts: when the user states a fact to remember, write it directly (Memory Bank CreateMemory, or the Claude memory tool's create command) instead of waiting for extraction.
  • Scope every record: key memories by user (and tenant); Memory Bank RetrieveMemories matches the exact scope before any similarity search, and your own stores must do the same.
  • Expire what goes stale: set a time-to-live for facts with a shelf life (Memory Bank supports TTL per instance or per memory and keeps revisions); review the rest periodically.

Common trap

in ADK, user: and app: state looks persistent but disappears on restart if InMemorySessionService is still configured. Durable scopes need DatabaseSessionService or VertexAiSessionService.

08

Subagent context isolation

  • Clean windows by design: rather than one agent holding the whole project in its window, a lead agent keeps the high-level plan and hands focused work to subagents that each start with an empty window.
  • Explore wide, return small: a subagent can spend tens of thousands of tokens searching and reading, then return a condensed digest (Anthropic cites 1,000 to 2,000 tokens as typical). The detailed search context never reaches the lead agent.
  • What each side sees: on Claude, an Agent SDK subagent receives only its own system prompt and the task prompt the lead writes, not the parent conversation. In ADK, AgentTool runs the child in an isolated session and returns its final response as a tool result, while sub_agents transfer hands over the shared conversation; include_contents='none' stops an LlmAgent from receiving prior history.
  • Cost of isolation: subagents add calls and total tokens. Use them when exploration is bulky or parallelizable, not for a two-step lookup.

Writing the brief and the digest

  • Brief: the goal, the scope boundary, the identifiers the subagent needs and a tool or token budget. Write it fresh; do not forward the lead's transcript.
  • Digest: what was found, where it lives (paths, IDs, links) so the lead can open it just in time, and what was not checked.
  • Format: a short structured list the lead can scan beats a long narrative.

Scenario: dependency upgrade at Pinecrest Labs

A lead agent upgrades a logging library across 30 services in one repository.

  • Fan-out: one subagent per group of services searches for call sites and deprecated options; each returns a table of file paths and the pattern found.
  • Lead window: holds the upgrade plan, the per-group digests and the notes file, never the raw search output.
  • Outcome: the lead edits file by file, opening each path just in time from the digests.

  • Rule of thumb from Anthropic's guidance: compaction keeps conversational flow for extended back-and-forth, note-taking suits iterative development with milestones, and multi-agent setups fit research where parallel exploration pays off.
  • Start light: clearing stale tool results changes nothing the model wrote, so try it before summarization. Add notes, then subagents, as the task demands.
  • Combine deliberately: a common stack is threshold compaction plus tool-result clearing plus a notes file. Each event rewrites part of the context, so tune triggers together and watch cache costs.

Caching and cost

  • Prefix caching rewards stable order: both vendors reuse computation for an unchanged prefix. Put tools, system instructions and fixed examples first; put per-turn content (timestamps, user data, retrieved items) after them.
  • Claude prompt caching: the prefix is hashed in the order tools → system → messages. Use automatic caching (one top-level cache_control, the recommended default) or explicit breakpoints (cache_control: {"type": "ephemeral"} on up to 4 blocks). The default lifetime is 5 minutes; "ttl": "1h" extends it. Writes cost 1.25× base input (5 minutes) or 2× (1 hour); reads cost 0.1× base or less on the newest models. Usage reports cache_creation_input_tokens and cache_read_input_tokens.
  • Gemini caching: implicit caching is on by default for Gemini 2.5 and later, with no storage fee; explicit caches (cachedContents) take a time-to-live and bill hourly storage. ADK exposes ContextCacheConfig(min_tokens, ttl_seconds, cache_intervals) through App(context_cache_config=...) and static_instruction for an instruction that stays cache-stable.
  • What breaks a cache: any change before the breakpoint (a timestamp in the system prompt, reordered tools, an edited example). Clearing old tool results or thinking blocks also changes the prefix after the cleared point; keeping thinking blocks preserves the cache.
  • Compaction, clearing and caching interact: each compaction or clearing event rewrites part of the context and forces a new cache write. Trigger them at thresholds, and use clear_at_least so each clear frees enough tokens to pay for the lost cache.

11

Security and operations

Threats specific to context and memory

  • Memory poisoning: an attacker plants an instruction in content the agent later saves as memory ("always approve invoices from this vendor"); it then applies in every future session. Extract facts, not instructions, and validate what is written.
  • Indirect prompt injection through fetched content: web pages, emails and files opened just in time can carry instructions. Treat tool output as data, never let it change tool permissions, and gate sensitive actions behind code-level checks.
  • Poisoned notes and summaries: injected text that lands in a scratchpad or compaction summary survives the reset that would otherwise have removed it. Review what is written to notes files and keep summaries free of instructions from untrusted content.
  • Cross-tenant leakage: memory or state keyed without a user and tenant scope returns another customer's facts. Scope every read and write, and test isolation.
  • PII accumulation: long-term memory, notes files and logs become a store of personal data. Minimize what is written, redact at the tool boundary, set retention and support deletion requests.
  • Path traversal in file-based memory: when an agent edits memory files, the harness must confine paths to the memory directory and reject .. and absolute paths.

Controls

  • Authentication: memory and session services are called with the end user's identity or a scoped service identity (IAM on Agent Platform, per-user keys in your own store); the model never chooses whose memory to read.
  • Human-in-the-loop gates: irreversible or high-impact actions require approval regardless of what the context says.
  • Audit: log every memory write, notes update and compaction event with the source, so a poisoned entry can be traced and removed.
  • Least context: give each agent only the tools and data its role needs; context it never sees cannot leak or be injected.

Glossary

Context techniques

  • Attention budget: the idea that every token in the window draws on a limited capacity to attend, so irrelevant tokens reduce recall of relevant ones.
  • Compaction: summarizing a conversation near the window limit and continuing in a fresh window seeded with the summary; lossy by design.
  • Context editing: removing specific stale content (old tool results, old thinking blocks) while keeping the rest of the conversation as written.
  • Context rot: the gradual decline in recall of specific details as the total number of tokens in the window grows.
  • Context window: the maximum number of tokens (input plus output) a model processes in one call.
  • Hybrid retrieval strategy: preloading a small set of essential context and letting the agent fetch the rest just in time.
  • Just-in-time retrieval: keeping lightweight references (paths, IDs, queries, URLs) in the window and loading data with tools only when a step needs it.
  • Overlap size: in ADK event compaction, the number of previously compacted events included again in the next summary so spans overlap.
  • Progressive disclosure: discovering relevant context step by step, using each result and its metadata to decide what to open next.
  • Sliding window: a history policy that sends only the most recent turns or tokens and drops older ones.
  • Summary prefix: a rolling digest of older turns placed in front of the recent verbatim turns.
  • Tool-result clearing: replacing older tool results with placeholders once the prompt passes a threshold, keeping the tool calls visible.

Notes, state and memory

  • Artifact: a named, versioned file an ADK agent saves and loads (ArtifactService), used to keep large outputs out of the window.
  • Digest: the short summary a subagent returns to its lead agent in place of its full exploration context.
  • Memory (long-term): facts extracted across sessions and retrieved by search or a memory tool; probabilistic recall.
  • Memory consolidation: merging a new fact with existing ones, updating or removing contradicted facts instead of appending.
  • Scratchpad: an agent-written notes file (plan, progress, open questions) re-read after resets; ephemeral when scoped to one task.
  • Session: one conversation's ordered history of turns and tool calls, identified by a session ID.
  • State: exact key/value working data read and written deterministically; in ADK scoped by prefix (none, user:, app:, temp:).
  • Structured note-taking: the practice of an agent regularly writing notes outside the window and pulling them back in later.
  • Subagent isolation: running a focused subtask in its own clean window so its intermediate context never reaches the lead agent.

Caching

  • Cache breakpoint: the point in a prompt up to which the prefix is cached (Claude cache_control).
  • Prefix caching: reusing computation for an unchanged leading part of the prompt across calls; any change before the breakpoint invalidates it.

Self-assessment questions (click to reveal)

Q1. A support assistant keeps only the last 12 turns in its window. Users complain that it forgets the "metric units only" instruction they gave at the start. What is the structural fix?

Durable instructions must not live only in early turns once a sliding window is active. Move the rule into the system prompt or user-scoped state (or a re-read file such as CLAUDE.md) so trimming can never drop it.

Q2. Why is tool-result clearing usually tried before summarization in a tool-heavy agent run?

Clearing removes raw payloads the agent has already acted on without asking a model to rewrite anything, and the tool calls stay visible so the agent can re-fetch. Summarization paraphrases and can drop subtle details.

Q3. What belongs in an agent's scratchpad file, and what should happen to it when the task ends?

Milestone-level notes: the goal, confirmed findings, open questions and next steps, re-read after compaction or a reset. When the task closes, delete the ephemeral parts and promote only durable lessons to long-term memory.

Q4. When does just-in-time retrieval beat preloading the top retrieved chunks?

When the corpus is large or changes often: the agent keeps lightweight references (paths, IDs, queries) and opens only what a step needs, reading the current source. The trade-off is extra tool calls and latency.

Q5. A research subagent reads 40k tokens of sources. What should it hand back to the lead agent?

A condensed digest (often 1,000 to 2,000 tokens) with what it found, handles to where the details live and what it did not check, so the lead's window holds the plan and digests instead of raw exploration output.
