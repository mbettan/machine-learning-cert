Overview & Mental Model

Google Antigravity

Google Antigravity is Google's agent-first development platform. You hand an agent a task, review the artifacts it produces (plans, diffs, walkthroughs, browser recordings), and approve key milestones. You no longer have to watch every keystroke.

Agents CLI

Agents CLI (agents-cli, package google-agents-cli) is a separate, open-source tool. It gives any coding agent (Antigravity, Claude Code, Codex, Gemini CLI) a machine-readable way to scaffold, evaluate, deploy and publish ADK agents on Google Cloud.

LayerToolRole
Developer harnessAntigravity (App, CLI agy, IDE, SDK)The coding agent you work with
Agent-building expertiseAgents CLI skills + agents-cli commandsTeach the coding agent ADK, evals and deployment
Agent frameworkADK (open source)The code of the agent you ship
Production runtimeAgent Runtime, Cloud Run, GKE → Gemini EnterpriseWhere the shipped agent runs and is distributed
Secure dev environmentCloud Workstations, Agent Sandbox on GKE, Antigravity terminal sandboxWhere agent-run code is isolated

Rule 0: harness ≠ runtime

Antigravity is the developer's harness, not the production runtime of the agent you build. The agent you ship runs on Agent Runtime, Cloud Run or GKE.

Agent-First Workflow: Plans, Artifacts & Verification

Planning mode

The agent researches the codebase, groups its work and produces an implementation plan artifact before it edits anything. Use it for multi-file changes, new features, migrations and security-sensitive work.

Fast mode

The agent acts right away. Use it for renames, one-off commands and small local fixes.

Review → execute

You review and approve, then the agent executes.

Artifacts are structured deliverables: implementation plans, code diffs, diagrams, images and browser recordings. A walkthrough artifact is produced at the end. It summarizes the changes and often includes screenshots or recordings of browser tasks.

Steering: comment inline on a plan (like a doc). Then click Proceed, or click Review to send your comments as feedback.

Exam trap: plans vs. file edits

The artifact review policy covers plans. File edits are controlled separately, by the agent mode (see section 07).

Multi-file refactoring & runtime optimization

Use Planning mode (/plan) to inventory call sites across the repository, establish a baseline (existing test suite or latency/memory benchmark), apply incremental diffs, and run verification gates after each step before producing the final walkthrough artifact. The full playbook follows below.

Automated vulnerability patching

Pair security scanner findings (SAST or dependency audit) with a security implementation plan and a Proof-of-Concept (PoC) reproduction test in an isolated sandbox (the Antigravity terminal sandbox: Seatbelt profiles on macOS, kernel namespaces on Linux). The agent confirms the PoC reproduces the flaw before the fix, patches the root cause (e.g., parameterized queries, output encoding, path canonicalization, upgraded dependency), verifies that the PoC and regression tests pass, and records a security audit report artifact. Use PreToolUse / PostToolUse hooks to run linters or security scanners automatically on every edit.

Refactoring and runtime optimization playbook

Refactoring and runtime optimization are judged by different proofs than a security patch, so they need their own gates.

AspectMulti-file refactoringRuntime optimizationVulnerability patching (CodeMender-style)
GoalChange structure, keep external behavior identicalCut latency, cost or resource use against a measured baselineRemove one verified flaw at its root cause
ScopeWide: many modules and call sitesHot paths found in traces or profilesNarrow: the code path behind one finding
Proof of successUnchanged test results plus a clean interface diffBetter benchmark or trace numbers and no eval regressionThe exploit or PoC stops reproducing and regression tests pass
Typical toolingRules, skills, research subagents, branch worktrees, hooksCloud Trace, benchmarks, agents-cli eval compare, revision traffic splitCodeMender (cm fix on Agent Platform, Preview) or the security plan flow above

Key point

CodeMender and the PoC flow above start from a finding and end with a small, reviewed diff. A refactor starts from a target design and can touch hundreds of files, so the safety net is the test suite and isolation, not an exploit reproducer.

Walkthrough: rename a module boundary across a monorepo

  1. Pin the contract: add an always_on rule that names the new package path and bans imports of the old one; run the full suite and save the result as the baseline.
  2. Map the blast radius: in /plan, have the agent delegate discovery to research subagents that list every importer and public symbol; the plan groups them into slices with no shared files.
  3. Fan out safely: the main agent launches one subagent per slice, each in its own branch workspace so writers never share a working tree.
  4. Let hooks enforce quality: the formatter runs after each edit and the Stop hook re-enters the loop with the failing test output until the slice is green.
  5. Review and merge: a custom reviewer subagent whose tools list has only read tools audits each worktree diff; the walkthrough artifact summarizes the result before you merge.

Walkthrough: cut response latency of a deployed ADK agent

  1. Measure first: open the agent's Cloud Trace spans and separate model time from tool and I/O time; save agents-cli eval run results as the quality baseline.
  2. Fix orchestration: independent lookups that run one after another become a ParallelAgent fan-out.
  3. Fix tokens: enable ADK context caching (ContextCacheConfig) for long, stable instructions on Gemini, or rely on prompt caching for Claude models; move simple classification steps to a smaller model.
  4. Prove both speed and quality: rerun the benchmark, then agents-cli eval compare on the old and new result files.
  5. Canary: on Agent Runtime, switch to a manual traffic split that keeps the current revision at 100% before you deploy, then move a small share to the new revision (revisions and traffic splitting are in Preview). The default is always-latest routing, which sends all traffic to a new revision as soon as it exists.

Hook setup used above (.agents/hooks.json; top-level keys are hook names, and Stop handlers sit directly under the event with no matcher):

JSON: .agents/hooks.json 
{
  "format-on-edit": {
    "PostToolUse": [
      { "matcher": "write_to_file|replace_file_content|multi_replace_file_content",
        "hooks": [{ "type": "command", "command": "./scripts/format_changed.sh", "timeout": 20 }] }
    ]
  },
  "tests-before-stop": {
    "Stop": [
      { "type": "command", "command": "./scripts/stop_unless_green.sh", "timeout": 120 }
    ]
  }
}

Why the Stop hook carries the test gate

  • A PostToolUse hook returns an empty object, so it cannot steer the agent. A Stop hook can print {"decision": "continue", "reason": "..."} and the reason is injected into the conversation, which sends the agent back to fix the failure.
  • Cost: hooks run synchronously and block the loop (default timeout 30 seconds), so keep the PostToolUse script to changed files and run only the affected tests in the Stop script.

Anti-patterns

  • Refactor and feature in one change: behavior changes hide inside structural moves; ship the pure refactor first, gated by unchanged test results.
  • Optimizing by feel: tuning prompts or swapping models without a saved baseline and an eval comparison trades latency for silent quality loss.
  • Shared working tree: parallel writer subagents in inherit mode overwrite each other; use branch and non-overlapping slices.
  • Self-grading: asking the authoring agent to review its own diff reuses the same blind spots; use a separate reviewer subagent with a clean context.
  • Sandbox off for builds: benchmarks and build scripts written by the agent run with full host privileges outside the sandbox.
  • Deploy equals rollout: with always-latest routing, every Agent Runtime deploy is a 100% rollout; pin traffic with a manual split before deploying.

Rules, Skills & Workflows

Rules are persistent constraints and invariants, such as "always use zod" or "never import internal/".

FileFrontmatterActivation
AGENTS.md / GEMINI.md (any directory)NoneAlways on for that directory and below
.agents/rules/*.mdRequired: triggeralways_on · model_decision (needs description) · glob (needs globs) · manual
Global: ~/.gemini/AGENTS.md, ~/.gemini/GEMINI.md, ~/.gemini/config/rules/*.mdModular rules need frontmatterAll projects on the machine

Rule mechanics

  • Rules add up. When they conflict, the more specific directory rule wins. Each rule file is injected only once.
  • A missing or invalid trigger (for example camelCase alwaysOn) means the rule is silently discarded.
  • .agents/rules/ is scanned one level deep. Files in nested folders are ignored unless you register them in .agents/rules.json.
  • Budgets: each rule file is capped at 24 KB. Always-on and global rules share a 20,000-token budget. Rules over budget are reduced to a file-path pointer.

Skills: on-demand procedures and runbooks

  • Layout: skills/<name>/SKILL.md with name and description in the frontmatter. Optional folders: scripts/, references/, examples/, resources/.
  • Progressive disclosure: only the name and description go into the context. The full body loads when the task matches. The description decides whether the skill ever activates.
  • Keep SKILL.md short. Move bulky docs into references/. Wrap long command sequences in scripts/. Include steps to validate the work.
  • Rule or skill? A rule is a constraint. A skill is a workflow ("how to run DB migrations").

Workflows (legacy, IDE)

Markdown prompt sequences you run as /workflow-name. The docs say current workflows stop working on October 19, 2026. Migrate them to skills with /migrate-workflows.

04

MCP, Hooks & Plugins

MCP servers: mcp_config.json (mcpServers map)

  • Locations: global ~/.gemini/config/mcp_config.json, workspace .agents/mcp_config.json, plugin plugins/<name>/mcp_config.json.
  • stdio (local): command, args, env. Streamable HTTP (remote): url (serverUrl is also accepted).
  • The legacy HTTP+SSE transport is not supported. For an SSE-only server, run a stdio bridge such as mcp-remote.
  • Discovered tools are added to the agent's toolset. Plugin tools get a namespace prefix when needed to avoid name clashes.

Hooks: hooks.json (named hooks → event handlers)

EventFiresTypical use
SessionStartOnce per new sessionInject startup context
PreToolUse (needs matcher)Before a tool runsGate, block, audit, or rewrite arguments
PostToolUse (needs matcher)After a tool runsLint, format, analyze
PreInvocationBefore each model callInject reminders
PostInvocationImmediately after each model invocation completesInject follow-up steps; force the loop to continue or terminate
StopWhen the loop endsBlock stopping until the goal is met

Hook outputs & limits

  • PreToolUse returns decision: allow · deny · ask · force_ask (ignores cached approvals). It can also return overwrite (a shallow merge into the tool arguments).
  • Stop can return decision: "continue" to re-enter the loop.
  • Only type: "command" is supported. Hooks run synchronously and block the loop, so keep them fast. Set "enabled": false to turn a hook off.

Plugins: namespaced bundles

  • plugins/<name>/plugin.json, plus optional skills/, rules/ (a consolidated AGENTS.md is recommended), hooks.json at the plugin root, mcp_config.json and agents/.
  • Discovered plugins are on by default. Your on/off choice is stored in config.json, never inside the plugin.
  • Install: agy plugin install <name>@antigravity-plugins-official, a GitHub URL or a local directory. Or use /plugin in the TUI.

06

Subagents, Browser Agent & Parallel Work

How subagents work

  • The main agent calls invoke_subagent with a role and a prompt. Each subagent starts with a clean context window and does not see the parent's history. Subagents run in parallel, in the background.
  • Workspace modes: inherit (same folder), branch (an isolated Git worktree), share (shared repo storage).
  • Built-in subagents: research (codebase exploration), browser (only through /browser), self (a clone of the caller).
  • Custom subagents: .agents/agents/<name>.md (workspace), ~/.gemini/config/agents/ (global) or plugins/<name>/agents/. YAML frontmatter: name, description, tools, model (inherit/flash/pro), commandExecutionPolicy (default sandbox), mcpServers, skills, mainAgent, subagent. Known issue: a misspelled tool name in tools can make the subagent hang.
  • Lifecycle: Running → Idle (sent its result; wakes up with full context when it gets a message) → Killed (permanent; temporary worktrees are cleaned up).

CLI & SDK

  • CLI: the /agents panel (Agent Manager) shows ID, role, state and current step. Alt+J jumps to the next pending approval. Ctrl+K approves in place.
  • SDK: dynamic self-cloning (CapabilitiesConfig(enable_subagents=True)) or static SubagentConfig. A custom tool given to a subagent must also be in the parent's tools.

Browser subagent & Automations

  • /browser drives Google Chrome through the Chrome DevTools MCP server. Its context is isolated, every session is recorded as a WebM artifact, and it is hidden from the normal subagent list. It is not available in the IDE, and admins can turn it off.
  • Automations (App) run prompts on a schedule. /schedule sets a timer or recurring check inside a conversation.

Permissions, Execution Modes & Terminal Sandbox

Permission rules: allow / ask / deny lists with typed matchers: command(npm test), read_file(path), write_file(src/), read_url, execute_url, mcp. Deny > Ask > Allow.

Defaults when no rule matches: reading and writing inside the workspace is allowed. Web actions (read_url, execute_url) default to Ask. Everything else (commands, MCP, files outside the workspace) defaults to Ask.

CLI agentMode (cycle with Shift+Tab)

ModeBehavior
defaultAsks you to review a diff before every file write
accept-editsAuto-approves file edits in the workspace. Commands still follow toolPermission
auto (Preview)Auto-approves edits and runs commands in the sandbox. Commands that need to run outside the sandbox are auto-evaluated: safe, reversible ones run, risky ones pause
planPlans before editing (adds /plan to the prompt)

CLI toolPermission: request-review (default) · proceed-in-sandbox · strict (asks before every tool call, even reads) · always-proceed (also turned on by --dangerously-skip-permissions). strict and always-proceed override auto.

Terminal sandbox (enableTerminalSandbox / --sandbox; off by default, turned on automatically in auto mode)

  • Project folders are mounted read-write. read_file paths are mounted read-only and write_file paths read-write. Everything else is invisible (macOS/Linux). Files such as .env are blocked.
  • Network: in the CLI, sandboxed commands get no network by default. Domains allowed under read_url are added to the outbound allowlist.
  • A command that runs outside the sandbox runs on the host with full privileges. Business and enterprise accounts use unsandboxed(...) rules for this.
  • App security presets (Default, Full machine, Turbo) never turn the sandbox on. You must enable sandbox mode yourself. A common combo is sandbox + Proceed in Sandbox.

Other settings: non-workspace file access (off by default), internet access policy, command allow/deny lists, browser domain allowlist. Project settings override global settings.

08

Secure Dev Environments: Cloud Workstations & GKE

Cloud Workstations: managed dev environments on Google Cloud

  • Cluster: region + VPC (not related to GKE clusters). Configuration: the template (VM type, persistent disk, container image, IDE, idle and running timeouts; access through IAM). Workstation: an instance started or stopped on demand.
  • Access through a browser IDE, local VS Code or JetBrains IDEs, or SSH. You can bring your own Linux container image, as long as its entrypoint runs a blocking process.
  • Lock it down: put it inside a VPC Service Controls perimeter, use a private cluster (clients connect through Private Service Connect), turn off public IPs (org policy constraints/compute.vmExternalIpAccess), and also restrict the Compute Engine API.
  • Agent-optimized development: set idleAction=SUSPEND with an idleTimeout (for example 1800s). Add keep-alive lifecycle hooks: start /google/scripts/keep_alive.sh when the agent starts working and kill it when the agent waits for input. Samples for Claude Code and Antigravity CLI ship in /google/samples/agents/keepalive/. A suspended workstation keeps RAM, processes and agent context, and stops vCPU and memory charges.

Agent Sandbox on GKE

A managed add-on that gives kernel-level isolation (gVisor) to untrusted, LLM-generated code. Pieces: SandboxTemplate (the blueprint) and SandboxWarmPool (pre-warmed pods). A core security policy that you cannot override requires gVisor and blocks hostNetwork and hostPath.

NeedPick
Stop a local coding agent from running wild on a laptopAntigravity terminal sandbox + deny rules
Corporate, exfiltration-safe dev box for humans and their coding agentsCloud Workstations (private cluster, VPC-SC, no public IP)
Run agent-generated code at scale inside a productAgent Sandbox on GKE
09

Agents CLI: Build → Evaluate → Deploy → Publish

What it is: a single, machine-readable interface that coding agents use to drive ADK projects end to end. It packages expert knowledge of ADK, evaluation and Google Cloud deployment as skills. Source: github.com/google/agents-cli.

Install. This is the only command you run yourself:

Bash — install Agents CLI 
uvx google-agents-cli setup        # installs agents-cli, ADK packages and skills into the coding agents on this machine
# alternatives: pipx/pip install google-agents-cli && agents-cli setup
# skills only:  npx skills add google/agents-cli

Prerequisites: Python 3.11+, uv, Node.js (for the skills), a coding agent. For deployment you also need the gcloud CLI and Terraform.

Positioning: Agents CLI vs. ADK CLI vs. gcloud vs. Antigravity

ToolTypeRole & behavior
Agents CLI (agents-cli)Lifecycle toolchain plus a skill bundleScaffolds, evaluates, deploys, publishes and provisions infra for ADK projects. Built for coding agents, but every command also runs standalone in a terminal
ADK CLI (adk)Framework CLI shipped with ADKInner-loop work on the framework itself (adk create for a single-file learning agent, adk run to chat with an agent in the terminal). No production scaffolding, eval synthesis or Gemini registration
gcloudGeneral Google Cloud CLIManages individual APIs, IAM and network resources one at a time. Agents CLI drives Cloud tooling for you and suppresses gcloud prompts (CLOUDSDK_CORE_DISABLE_PROMPTS=1) unless you pass -i
AntigravityCoding agent (the harness)Reads the Agents CLI skills and runs agents-cli commands on your behalf. Agents CLI is a tool for a coding agent, not a coding agent itself

Rule of thumb

Use adk to learn the framework, agents-cli to ship a project, and gcloud for one-off resource changes outside the agent stack.

Extensions (experimental)

  • agents-cli extension add <ref> adds third-party skills and command overrides. Project scope (default) records the pin in agents-cli-extensions.yaml and copies skills to <project>/.agents/skills/; --global uses ~/.agents/skills/. When both scopes define the same command, project scope wins.

Cloud Trace is on by default. Asking the agent to "set up observability" provisions a service account, a Cloud Storage bucket and a BigQuery dataset.
Templates
--agent adk_python (alias adk, the -y default) or --agent adk_go; --agent also accepts a template repository (org/repo, optionally with --ref) or local@<path>; confirm the exact syntax with agents-cli create --help. RAG is no longer a built-in template (it is now a clone-and-study recipe). For a single-file learning agent, use adk create instead.

Agent vs. human mode

Agents CLI serves two callers with the same commands and syntax. There is no documented --mode agent or --mode human flag. The difference is how prompts and output are handled.

DimensionAgent mode (coding agent or CI)Human mode (developer at a terminal)
CallerAntigravity or another coding agent following the google-agents-cli-* skills; CI runnersYou, typing commands directly
Prompts-y / --yes (alias --auto-approve) skips prompts and fills missing values with defaults; gcloud prompts stay suppressed-i / --interactive shows menus and prompts (for example create -i, or publish gemini -i, which lists your Gemini apps)
InputsExplicit flags or env vars (publish gemini reads GEMINI_APP_ID and AGENT_RUNTIME_ID)Interactive answers, plus the playground browser UI
OutputSingle-shot commands (run "<prompt>") and info --json for parsingConsole output and local URLs meant for reading
Best forBuild-eval-deploy loops, CI/CD, repeatable releasesFirst login, exploration, debugging in playground

Exam trap: run --mode is not agent vs. human

agents-cli run --mode exists, but it selects the protocol used to talk to the agent (adk, a2a, adk_live). It has nothing to do with agent vs. human mode. Anti-pattern: passing -i from a coding agent or CI job leaves the command waiting on a prompt nobody answers.

Example: build and ship a new agent with Antigravity

  1. Brief: ask Antigravity to "use agents-cli to build a support agent for order lookups". The workflow and scaffold skills activate, and Antigravity asks about tools, inputs, outputs and success criteria.
  2. Scaffold: Antigravity runs agents-cli create support-agent --prototype -y, then writes app/agent.py with the adk-code skill.
  3. Check locally: agents-cli run "<prompt>" and agents-cli lint; you open agents-cli playground to try it yourself.
  4. Gate: agents-cli eval run must pass before any cloud step.
  5. Ship: agents-cli deploy to Agent Runtime, then agents-cli publish gemini to register the agent in your Gemini Enterprise app.

Example: fix a quality regression on a deployed agent

  1. Widen coverage: agents-cli eval dataset synthesize adds scenarios around the reported failure.
  2. Measure: agents-cli eval run, then agents-cli eval analyze to cluster the failures by cause.
  3. Repair: agents-cli eval optimize, or patch the instructions by hand.
  4. Prove it: re-run eval run and use agents-cli eval compare on the old and new result files to confirm nothing regressed.
  5. Roll out: agents-cli deploy --update-only updates the existing Agent Runtime deployment instead of creating a duplicate.

Example: harden a prototype for production

  1. Add a target and pipeline: agents-cli scaffold enhance -d cloud_run --cicd-runner github_actions (preview with --dry-run).
  2. Provision: agents-cli infra single-project to plan, then rerun with --apply; or agents-cli infra cicd for a staging and prod split.
  3. Observe: ask Antigravity to "set up observability"; the observability skill covers Cloud Trace, prompt-response logging and BigQuery Agent Analytics.
  4. Verify: agents-cli info confirms the project config and CLI version before the first pipeline run.

Endpoint and model settings

  • CMEK: Cloud KMS keys cannot live in the global location, so any customer-managed key requirement already rules out the global endpoint. Check the Agent Platform CMEK page for partner-model coverage before promising key control over prompts.
  • Per-model overrides: with CLOUD_ML_REGION=global, a model that lacks global support can be routed elsewhere through its VERTEX_REGION_CLAUDE_* variable. A malformed region value is ignored and Claude Code falls back to us-east5.
  • Pin models: set ANTHROPIC_DEFAULT_OPUS_MODEL, ANTHROPIC_DEFAULT_SONNET_MODEL and ANTHROPIC_DEFAULT_HAIKU_MODEL to IDs enabled in your project. Unpinned aliases follow Claude Code's built-in defaults, which may not be enabled for you and default to Opus pricing.

Claude Code on Agent Platform: cost and capacity

  • Prompt caching is on by default in Claude Code. A coding session resends the same system prompt, tool schemas and repo context on every turn, so cached prefixes cut both latency and input cost. Caches are scoped to one Google Cloud project.
  • Default TTL: 5 minutes. Extended TTL: 1 hour, requested with ENABLE_PROMPT_CACHING_1H=1.
  • Billing shape: writing to the cache costs more than a normal input token (more again for the 1-hour TTL); reading from it costs far less.
  • Provisioned Throughput reserves capacity for some partner models for a fixed fee, in the regions you choose, and is bought through sales. Reserved requests are served ahead of pay-as-you-go traffic when the system is busy. It works only on regional endpoints, not global or multi-region.
  • Quota errors (429): on regional endpoints, check that both the primary and the background model are offered in that region, or move to global. Rate-limit increases go through Google Cloud quotas, not Anthropic.

Note

The cache multipliers on the Agent Platform pricing page at writing time: 5-minute writes cost 1.25x base input, 1-hour writes 2x, and cache reads 0.1x. Treat these as directional and recheck the pricing page before quoting them.

Credentials

  • No API keys: none of these paths needs ANTHROPIC_API_KEY. Avoid service account key files too; use ADC from a user login or an attached identity.
  • Workstation tip: Cloud Workstations ships keep-alive samples for Claude Code so a suspended workstation keeps the agent's session (see section 08).
  • Expiring user credentials: Claude Code's gcpAuthRefresh setting runs a command (typically the ADC login) when it detects expired credentials, instead of failing mid-session.
  • Anti-pattern (keys in the repo): a service account key in .env or GOOGLE_APPLICATION_CREDENTIALS on a laptop is a long-lived secret the agent can read and leak.

Governing MCP traffic

  • Google remote MCP servers: enable a Model Armor floor setting with MCP sanitization (integrated service GOOGLE_MCP_SERVER) in the project. Every tool call and response to a supported Google MCP server is screened for prompt injection and sensitive data, whatever harness made the call.
  • Custom MCP servers: host them on Cloud Run or GKE behind Agent Gateway, which applies access policies and Model Armor templates to agent egress traffic.
  • Residency: some Google MCP servers route Model Armor calls across jurisdictions, so check the supported-products list if residency matters.

Allowlist semantics and limits

A custom allow list implicitly denies every model not listed; with no policy set or inherited, every model is allowed. An explicit deny at the folder wins over an allow at the project, unless the project policy is set to override its parents. List each model individually (there is no "all third-party models" value) and stay under 500 allowed plus denied values per policy. The policy applies to every principal in the resource, not per user, and only to Model Garden models (not Model Registry). Anti-pattern: allowing the Claude model but not count-tokens, so token-count requests stay blocked.

Claude Code on Agent Platform: Developer Knowledge MCP server

The Developer Knowledge MCP server (https://developerknowledge.googleapis.com/mcp, remote HTTP transport) lets Claude Code ground its answers in current Google developer documentation through three tools: search_documents, get_documents and answer_query.

Auth pathHow Claude Code sends itWatch out for
API key (the path Google documents for Claude Code)X-Goog-Api-Key headerRestrict the key to the Developer Knowledge API; keep it out of committed files
ADC bearer tokenAuthorization: Bearer plus X-Goog-User-ProjectTokens from print-access-token last one hour; the quota project header needs serviceusage.services.use (for example roles/serviceusage.serviceUsageConsumer)
Bash: add the server (local scope) 
gcloud services enable developerknowledge.googleapis.com
claude mcp add google-developer-knowledge --transport http \
  https://developerknowledge.googleapis.com/mcp --header "X-Goog-Api-Key: $DK_KEY"

That command writes to local scope. For a team-shared, keyless setup, commit a project-scoped .mcp.json whose headersHelper script prints a fresh ADC token on every connection:

JSON: .mcp.json 
{
  "mcpServers": {
    "google-developer-knowledge": {
      "type": "http",
      "url": "https://developerknowledge.googleapis.com/mcp",
      "headersHelper": "/usr/local/bin/dk-headers"
    }
  }
}

Helper contract, approval and errors

  • Helper contract: the command must print a JSON object of string headers (here Authorization and X-Goog-User-Project); Claude Code reruns it on reconnect, so expiring tokens do not break the session.
  • Approval: project-scoped servers stay pending until each developer trusts the workspace and approves them; a cloned repo cannot pre-approve its own servers.
  • Errors: a 403 asking for a quota project means the X-Goog-User-Project header is missing; a 404 or 403 on /mcp usually means the API is not enabled.

Workstation access notes

  • Local IDE access: the tunnel forwards a local port to the workstation's SSH port; it authenticates with your gcloud credentials and is authorized by the workstation's IAM policy, so nothing listens publicly. gcloud workstations ssh does the same in one command.
  • Private cluster caveat: the laptop must sit on a network that reaches the PSC endpoint (for example over VPN or Interconnect), or the tunnel cannot connect.

Self-Assessment Questions (Click to Reveal)

Q1. Your new file in .agents/rules/ has trigger: alwaysOn and the agent ignores it. Why?

The trigger value is invalid (camelCase), so the rule is silently discarded. Use always_on, and keep the file directly in .agents/rules/ (nested folders need rules.json).

Q2. When should a piece of guidance be a rule and when a skill?

A rule is a persistent constraint ("never import internal/"). A skill is an on-demand procedure ("how to run DB migrations"). Skills load through progressive disclosure: only the name and description sit in context until the task matches.

Q3. A remote MCP server only exposes the legacy HTTP+SSE transport. How do you connect it?

Antigravity does not support legacy SSE. Point to a Streamable HTTP endpoint (url) if one exists, or run a stdio bridge such as mcp-remote (command/args).

Q4. Two parallel subagents edit the same files and overwrite each other. What do you change?

Use the branch workspace mode so each subagent works in its own Git worktree, and give them non-overlapping scopes.

Q5. You picked the App's "Full machine" preset. Are agent commands sandboxed?

No. App security presets never turn the terminal sandbox on. Enable sandbox mode yourself, typically with Proceed in Sandbox. Commands that run outside the sandbox have full host privileges.

Q6. A coding agent on a Cloud Workstation loses its in-memory state after lunch. What is the fix?

Set idleAction=SUSPEND with an idleTimeout and add keep-alive lifecycle hooks (start keep_alive.sh while the agent works, kill it when it waits for input). Suspension keeps RAM, processes and agent context.

Q7. List the Agents CLI path from an empty folder to Gemini Enterprise.

uvx google-agents-cli setup → agents-cli create + install → run / playground → eval run (release gate) → scaffold enhance --deployment-target if needed → deploy → register with Gemini Enterprise in one Agents CLI command (agents-cli publish gemini; publish gemini-enterprise is the older hidden alias).

Q8. Is Antigravity where your shipped ADK agent runs in production?

No. Antigravity is the developer's harness. The ADK agent you ship runs on Agent Runtime, Cloud Run or GKE, and can be distributed through Gemini Enterprise.
