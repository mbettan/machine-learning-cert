Overview & Mental Model

Google Antigravity

Google Antigravity is Google's agent-first development platform. You hand an agent a task, review the artifacts it produces (plans, diffs, walkthroughs, browser recordings), and approve key milestones. You no longer have to watch every keystroke.

Agents CLI

Agents CLI (agents-cli, package google-agents-cli) is a separate, open-source tool. It gives any coding agent (Antigravity, Claude Code, Codex, Gemini CLI) a machine-readable way to scaffold, evaluate, deploy and publish ADK agents on Google Cloud.

LayerToolRole
Developer harnessAntigravity (App, CLI agy, IDE, SDK)The coding agent you work with
Agent-building expertiseAgents CLI skills + agents-cli commandsTeach the coding agent ADK, evals and deployment
Agent frameworkADK (open source)The code of the agent you ship
Production runtimeAgent Runtime, Cloud Run, GKE → Gemini EnterpriseWhere the shipped agent runs and is distributed
Secure dev environmentCloud Workstations, Agent Sandbox on GKE, Antigravity terminal sandboxWhere agent-run code is isolated

Rule 0: harness ≠ runtime

Antigravity is the developer's harness, not the production runtime of the agent you build. The agent you ship runs on Agent Runtime, Cloud Run or GKE.

Facts to remember

  • Sign-in is shared: signing in on one local surface signs you in on the others.
  • The SDK agent is read-only by default. Pass capabilities=CapabilitiesConfig() to enable write tools.
  • Remote Control lets you drive App and CLI sessions from a browser. In the CLI, use /remote-control, --remote-control or agy remote-control start.
  • Gemini CLI migration: on first launch, agy detects old Gemini CLI configs. agy plugin import gemini converts Gemini CLI extensions into Antigravity plugins.

Agent-First Workflow: Plans, Artifacts & Verification

Planning mode

The agent researches the codebase, groups its work and produces an implementation plan artifact before it edits anything. Use it for multi-file changes, new features, migrations and security-sensitive work.

Fast mode

The agent acts right away. Use it for renames, one-off commands and small local fixes.

01

Analysis & discovery

/plan starts by exploring the codebase and the task.

02

Clarifying interview

Runs only if the requirements are unclear.

03

Implementation plan

Step-by-step tasks, verification gates and risks.

04

Review → execute

You review and approve, then the agent executes.

/grill-me interviews you one question at a time before work starts. Combine them with /plan /grill-me <task>.

Artifacts are structured deliverables: implementation plans, code diffs, diagrams, images and browser recordings. A walkthrough artifact is produced at the end. It summarizes the changes and often includes screenshots or recordings of browser tasks.

Steering: comment inline on a plan (like a doc). Then click Proceed, or click Review to send your comments as feedback.

SurfaceArtifact review policy optionsDefault / guidance
AppRequest review · Always proceedRequest review is recommended
CLI (artifactReviewPolicy)asks-for-review · agent-decides · always-proceedasks-for-review is the default. agent-decides currently behaves the same way

Exam trap: plans vs. file edits

The artifact review policy covers plans. File edits are controlled separately, by the agent mode (see section 07).

Multi-file refactoring & runtime optimization

Use Planning mode (/plan) to inventory call sites across the repository, establish a baseline (existing test suite or latency/memory benchmark), apply incremental diffs, and run verification gates after each step before producing the final walkthrough artifact.

Automated vulnerability patching

Pair security scanner findings (SAST or dependency audit) with a security implementation plan and a Proof-of-Concept (PoC) reproduction test in an isolated sandbox (workspaceWrite / Seatbelt). The agent confirms the PoC reproduces the flaw before the fix, patches the root cause (e.g., parameterized queries, output encoding, path canonicalization, upgraded dependency), verifies that the PoC and regression tests pass, and records a security audit report artifact. Use PreToolUse / PostToolUse hooks to run linters or security scanners automatically on every edit.

03

Rules, Skills & Workflows

Rules are persistent constraints and invariants, such as "always use zod" or "never import internal/".

FileFrontmatterActivation
AGENTS.md / GEMINI.md (any directory)NoneAlways on for that directory and below
.agents/rules/*.mdRequired: triggeralways_on · model_decision (needs description) · glob (needs globs) · manual
Global: ~/.gemini/AGENTS.md, ~/.gemini/GEMINI.md, ~/.gemini/config/rules/*.mdModular rules need frontmatterAll projects on the machine

Rule mechanics

  • Rules add up. When they conflict, the more specific directory rule wins. Each rule file is injected only once.
  • A missing or invalid trigger (for example camelCase alwaysOn) means the rule is silently discarded.
  • .agents/rules/ is scanned one level deep. Files in nested folders are ignored unless you register them in .agents/rules.json.
  • Budgets: each rule file is capped at 24 KB. Always-on and global rules share a 20,000-token budget. Rules over budget are reduced to a file-path pointer.

Skills: on-demand procedures and runbooks

  • Layout: skills/<name>/SKILL.md with name and description in the frontmatter. Optional folders: scripts/, references/, examples/, resources/.
  • Progressive disclosure: only the name and description go into the context. The full body loads when the task matches. The description decides whether the skill ever activates.
  • Keep SKILL.md short. Move bulky docs into references/. Wrap long command sequences in scripts/. Include steps to validate the work.
  • Rule or skill? A rule is a constraint. A skill is a workflow ("how to run DB migrations").

Workflows (legacy, IDE)

Markdown prompt sequences you run as /workflow-name. The docs say current workflows stop working on October 19, 2026. Migrate them to skills with /migrate-workflows.

04

MCP, Hooks & Plugins

MCP servers: mcp_config.json (mcpServers map)

  • Locations: global ~/.gemini/config/mcp_config.json, workspace .agents/mcp_config.json, plugin plugins/<name>/mcp_config.json.
  • stdio (local): command, args, env. Streamable HTTP (remote): url (serverUrl is also accepted).
  • The legacy HTTP+SSE transport is not supported. For an SSE-only server, run a stdio bridge such as mcp-remote.
  • Discovered tools are added to the agent's toolset. Plugin tools get a namespace prefix when needed to avoid name clashes.

Hooks: hooks.json (named hooks → event handlers)

EventFiresTypical use
SessionStartOnce per new sessionInject startup context
PreToolUse (needs matcher)Before a tool runsGate, block, audit, or rewrite arguments
PostToolUse (needs matcher)After a tool runsLint, format, analyze
PreInvocationBefore each model callInject reminders
PostInvocationImmediately after each model invocation completesInject follow-up steps; force the loop to continue or terminate
StopWhen the loop endsBlock stopping until the goal is met

Hook outputs & limits

  • PreToolUse returns decision: allow · deny · ask · force_ask (ignores cached approvals). It can also return overwrite (a shallow merge into the tool arguments).
  • Stop can return decision: "continue" to re-enter the loop.
  • Only type: "command" is supported. Hooks run synchronously and block the loop, so keep them fast. Set "enabled": false to turn a hook off.

Plugins: namespaced bundles

  • plugins/<name>/plugin.json, plus optional skills/, rules/ (a consolidated AGENTS.md is recommended), hooks.json at the plugin root, mcp_config.json and agents/.
  • Discovered plugins are on by default. Your on/off choice is stored in config.json, never inside the plugin.
  • Install: agy plugin install <name>@antigravity-plugins-official, a GitHub URL or a local directory. Or use /plugin in the TUI.

Discovery & Precedence

01

Workspace

.agents/ (also .agent/, _agents/, _agent/). The agent walks from the CWD up to the repo root. Commit this folder to share with the team.

02

Directory rules

AGENTS.md, GEMINI.md and .agents/rules/*.md, found by walking up from each file the agent reads or edits.

03

Global

~/.gemini/config/ (applies only on this machine).

Priority (highest → lowest). When two customizations have the same name, the higher one wins.

#Source
1Workspace project (walking up from the CWD)
2Declared configs: workspace skills.json / plugins.json
3Global discovery: ~/.gemini/config/
4Built-in customizations (mounted by name)
5Global declared configs

skills.json / plugins.json: entries (paths scanned one level deep, with include_only / exclude) and inherits (other config files). Paths can be absolute, ~/-relative, or relative to the workspace/repo root.

Team pattern

Commit shared skills to tools/agents/skills/. Then commit .agents/skills.json with {"entries":[{"path":"tools/agents/skills"}]}. Anyone who clones the repo gets the skills automatically.

06

Subagents, Browser Agent & Parallel Work

How subagents work

  • The main agent calls invoke_subagent with a role and a prompt. Each subagent starts with a clean context window and does not see the parent's history. Subagents run in parallel, in the background.
  • Workspace modes: inherit (same folder), branch (an isolated Git worktree), share (shared repo storage).
  • Built-in subagents: research (codebase exploration), browser (only through /browser), self (a clone of the caller).
  • Custom subagents: .agents/agents/<name>.md (workspace), ~/.gemini/config/agents/ (global) or plugins/<name>/agents/. YAML frontmatter: name, description, tools, model (inherit/flash/pro), commandExecutionPolicy (default sandbox), mcpServers, skills, mainAgent, subagent. Known issue: a misspelled tool name in tools can make the subagent hang.
  • Lifecycle: Running → Idle (sent its result; wakes up with full context when it gets a message) → Killed (permanent; temporary worktrees are cleaned up).

CLI & SDK

  • CLI: the /agents panel (Agent Manager) shows ID, role, state and current step. Alt+J jumps to the next pending approval. Ctrl+K approves in place.
  • SDK: dynamic self-cloning (CapabilitiesConfig(enable_subagents=True)) or static SubagentConfig. A custom tool given to a subagent must also be in the parent's tools.

Browser subagent & Automations

  • /browser drives Google Chrome through the Chrome DevTools MCP server. Its context is isolated, every session is recorded as a WebM artifact, and it is hidden from the normal subagent list. It is not available in the IDE, and admins can turn it off.
  • Automations (App) run prompts on a schedule. /schedule sets a timer or recurring check inside a conversation.
07

Permissions, Execution Modes & Terminal Sandbox

Permission rules: allow / ask / deny lists with typed matchers: command(npm test), read_file(path), write_file(src/), read_url, execute_url, mcp. Deny > Ask > Allow.

Defaults when no rule matches: reading and writing inside the workspace is allowed. Web actions (read_url, execute_url) default to Ask. Everything else (commands, MCP, files outside the workspace) defaults to Ask.

CLI agentMode (cycle with Shift+Tab)

ModeBehavior
defaultAsks you to review a diff before every file write
accept-editsAuto-approves file edits in the workspace. Commands still follow toolPermission
auto (Preview)Auto-approves edits and runs commands in the sandbox. Commands that need to run outside the sandbox are auto-evaluated: safe, reversible ones run, risky ones pause
planPlans before editing (adds /plan to the prompt)

CLI toolPermission: request-review (default) · proceed-in-sandbox · strict (asks before every tool call, even reads) · always-proceed (also turned on by --dangerously-skip-permissions). strict and always-proceed override auto.

Terminal sandbox (enableTerminalSandbox / --sandbox; off by default, turned on automatically in auto mode)

  • Project folders are mounted read-write. read_file paths are mounted read-only and write_file paths read-write. Everything else is invisible (macOS/Linux). Files such as .env are blocked.
  • Network: in the CLI, sandboxed commands get no network by default. Domains allowed under read_url are added to the outbound allowlist.
  • A command that runs outside the sandbox runs on the host with full privileges. Business and enterprise accounts use unsandboxed(...) rules for this.
  • App security presets (Default, Full machine, Turbo) never turn the sandbox on. You must enable sandbox mode yourself. A common combo is sandbox + Proceed in Sandbox.

Other settings: non-workspace file access (off by default), internet access policy, command allow/deny lists, browser domain allowlist. Project settings override global settings.

08

Secure Dev Environments: Cloud Workstations & GKE

Cloud Workstations: managed dev environments on Google Cloud

  • Cluster: region + VPC (not related to GKE clusters). Configuration: the template (VM type, persistent disk, container image, IDE, idle and running timeouts; access through IAM). Workstation: an instance started or stopped on demand.
  • Access through a browser IDE, local VS Code or JetBrains IDEs, or SSH. You can bring your own Linux container image, as long as its entrypoint runs a blocking process.
  • Lock it down: put it inside a VPC Service Controls perimeter, use a private cluster (clients connect through Private Service Connect), turn off public IPs (org policy constraints/compute.vmExternalIpAccess), and also restrict the Compute Engine API.
  • Agent-optimized development: set idleAction=SUSPEND with an idleTimeout (for example 1800s). Add keep-alive lifecycle hooks: start /google/scripts/keep_alive.sh when the agent starts working and kill it when the agent waits for input. Samples for Claude Code and Antigravity CLI ship in /google/samples/agents/keepalive/. A suspended workstation keeps RAM, processes and agent context, and stops vCPU and memory charges.

Agent Sandbox on GKE

A managed add-on that gives kernel-level isolation (gVisor) to untrusted, LLM-generated code. Pieces: SandboxTemplate (the blueprint) and SandboxWarmPool (pre-warmed pods). A core security policy that you cannot override requires gVisor and blocks hostNetwork and hostPath.

NeedPick
Stop a local coding agent from running wild on a laptopAntigravity terminal sandbox + deny rules
Corporate, exfiltration-safe dev box for humans and their coding agentsCloud Workstations (private cluster, VPC-SC, no public IP)
Run agent-generated code at scale inside a productAgent Sandbox on GKE

Agents CLI: Build → Evaluate → Deploy → Publish

What it is: a single, machine-readable interface that coding agents use to drive ADK projects end to end. It packages expert knowledge of ADK, evaluation and Google Cloud deployment as skills. Source: github.com/google/agents-cli.

Install. This is the only command you run yourself:

Bash — install Agents CLI 
uvx google-agents-cli setup        # installs agents-cli, ADK packages and skills into the coding agents on this machine
# alternatives: pipx/pip install google-agents-cli && agents-cli setup
# skills only:  npx skills add google/agents-cli

Prerequisites: Python 3.11+, uv, Node.js (for the skills), a coding agent. For deployment you also need the gcloud CLI and Terraform.

Skills that activate (seen in the quickstarts): google-agents-cli-workflow, -scaffold, -adk-code, -eval, -deploy, -publish, -observability.

Lifecycle commands (the coding agent usually runs them for you)

StageCommand
Scaffoldagents-cli create <name> --prototype --yes then agents-cli install
Smoke testagents-cli run "<prompt>"
Local UIagents-cli playground (ADK web UI, hot reload, localhost:8080)
Evaluateagents-cli eval run (evalsets in tests/eval/evalsets/*.evalset.json, LLM-as-judge criteria in tests/eval/eval_config.json)
Add deploy targetagents-cli scaffold enhance --deployment-target cloud_run
Deployagents-cli deploy (Agent Runtime, Cloud Run or GKE)
PublishRegister an Agent Runtime agent with Gemini Enterprise in one Agents CLI command (agents-cli publish gemini-enterprise, e.g. --agent-runtime-id)
Project layout
app/agent.py, app/fast_api_app.py, tests/{eval,integration,unit}, agents-cli-manifest.yaml, Dockerfile, GEMINI.md (guidance for coding agents) and .env.
Auth
A Gemini API key in .env (comment out the GOOGLE_CLOUD_* lines), or Application Default Credentials (gcloud auth application-default login) with the GOOGLE_CLOUD_* lines set.
Observability
Cloud Trace is on by default. Asking the agent to "set up observability" provisions a service account, a Cloud Storage bucket and a BigQuery dataset.
Templates
adk_a2a (multi-agent over A2A) and agentic_rag. For a single-file learning agent, use adk create instead.

Agent vs. human mode

Agents CLI is built for two callers. In agent mode, your coding agent uses the installed Agents CLI skills and runs the commands for you, so it needs non-interactive flags (for example --yes). In human mode, you run the same commands yourself with the same syntax. Plugin options (verify): check the current Agents CLI docs.

Self-Assessment Questions (Click to Reveal)

Q1. Your new file in .agents/rules/ has trigger: alwaysOn and the agent ignores it. Why?

The trigger value is invalid (camelCase), so the rule is silently discarded. Use always_on, and keep the file directly in .agents/rules/ (nested folders need rules.json).

Q2. When should a piece of guidance be a rule and when a skill?

A rule is a persistent constraint ("never import internal/"). A skill is an on-demand procedure ("how to run DB migrations"). Skills load through progressive disclosure: only the name and description sit in context until the task matches.

Q3. A remote MCP server only exposes the legacy HTTP+SSE transport. How do you connect it?

Antigravity does not support legacy SSE. Point to a Streamable HTTP endpoint (url) if one exists, or run a stdio bridge such as mcp-remote (command/args).

Q4. Two parallel subagents edit the same files and overwrite each other. What do you change?

Use the branch workspace mode so each subagent works in its own Git worktree, and give them non-overlapping scopes.

Q5. You picked the App's "Full machine" preset. Are agent commands sandboxed?

No. App security presets never turn the terminal sandbox on. Enable sandbox mode yourself, typically with Proceed in Sandbox. Commands that run outside the sandbox have full host privileges.

Q6. A coding agent on a Cloud Workstation loses its in-memory state after lunch. What is the fix?

Set idleAction=SUSPEND with an idleTimeout and add keep-alive lifecycle hooks (start keep_alive.sh while the agent works, kill it when it waits for input). Suspension keeps RAM, processes and agent context.

Q7. List the Agents CLI path from an empty folder to Gemini Enterprise.

uvx google-agents-cli setup → agents-cli create + install → run / playground → eval run (release gate) → scaffold enhance --deployment-target if needed → deploy → register with Gemini Enterprise in one Agents CLI command (agents-cli publish gemini-enterprise).

Q8. Is Antigravity where your shipped ADK agent runs in production?

No. Antigravity is the developer's harness. The ADK agent you ship runs on Agent Runtime, Cloud Run or GKE, and can be distributed through Gemini Enterprise.
