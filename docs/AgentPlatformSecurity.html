Agent Platform: Identity, Security & Governance

How to secure and govern agents on Gemini Enterprise Agent Platform. Topics: who the agent is (Agent Identity), how it authenticates to tools (auth manager, Secret Manager), what it may reach (IAM, Principal Access Boundary), where its traffic is enforced (Agent Gateway + Agent Registry), what content it may see or emit (Model Armor, Sensitive Data Protection, Gemini safety filters), how its network and data are isolated (VPC-SC, PSC, CMEK, residency), how it's audited (Cloud Audit Logs, SCC AI Protection), and when a human must approve (HITL).

Author: Michaël Bettan
Track: Google Cloud / Professional Agentic Architect

Agent Identity is supported on Agent Runtime, Gemini Enterprise, and Cloud Run.

Principal formats

  • SPIFFE ID: spiffe://agents.global.org-ORG_ID.system.id.goog/resources/aiplatform/projects/PROJECT_NUMBER/locations/LOCATION/reasoningEngines/AGENT_ID
  • Single agent (IAM): principal://agents.global.org-ORG_ID.system.id.goog/resources/aiplatform/projects/PROJECT_NUMBER/locations/LOCATION/reasoningEngines/AGENT_ID
  • All agents in a project: principalSet://agents.global.org-ORG_ID.system.id.goog/attribute.platformContainer/aiplatform/projects/PROJECT_NUMBER
  • All agents in the org: principalSet://…/attribute.platform/aiplatform

Enabling it

  • SDK (api_version="v1beta1"): client.runtimes.create(config={"identity_type": types.IdentityType.AGENT_IDENTITY, ...}). You can create the identity before deploying code so you can set up IAM first, then add code with client.runtimes.update(...).
  • CLI: agents-cli deploy --agent-identity; for adk deploy, set it in .agent_engine_config.json.
  • If the setting is absent, the agent runs as a service account.
  • Default roles granted to the identity: roles/aiplatform.agentContextEditor, roles/aiplatform.agentDefaultAccess.
  • Typical extra roles: roles/aiplatform.expressUser, roles/serviceusage.serviceUsageConsumer, roles/browser, roles/secretmanager.secretAccessor.

Tool Authentication & Secrets

Two authorities

ModelAgent acts as…MechanismUse when
User-delegatedthe end user (with consent)3-legged OAuth via the auth managerPer-user data in SaaS (Jira, GitHub, Salesforce, ServiceNow, Workspace)
Agent's own authorityitselfAgent Identity → Google Cloud APIs; OIDC ID tokens → external services (federation); 2-legged OAuth (machine-to-machine); API key; HTTP basic (not recommended)Shared back-end services, batch jobs, service-to-service calls

Audit logs record both the agent and the user when the agent acts on a user's behalf, and only the agent when it acts on its own authority.

Identities in one agent call

IdentityWhat it representsWhere it comes fromTypical use
End userThe person typing the promptCloud Identity or an external IdP through Workforce Identity FederationCarries the user's own data entitlements (document sharing, row-level rules)
Agent IdentityOne deployed agentProvisioned by Agent Runtime, Gemini Enterprise or Cloud Run; SPIFFE ID with a certificate-bound credentialCalls Google Cloud APIs and the gateway as the agent; is granted roles/agentidentity.user on the auth providers it may use

  • As itself: the data or action is not tied to who is asking (reference data, shared queues, batch jobs, service-to-service calls). Use Agent Identity for Google Cloud APIs, or a 2LO/API-key auth provider for a third party.
  • On behalf of the user: the result must differ per user, or the action must be attributable to that user (their mailbox, their tickets, CRM records filtered by owner). Use a 3LO auth provider so the downstream service applies the user's own permissions.
  • Anti-pattern (shared super-credential): one 2LO token or broad service account answers every user's request. The agent then decides who sees what, which sets up a confused deputy (see Access boundaries).

Agent Identity auth manager

  • A centralized credential vault and auth broker. "Auth providers" hold API keys, OAuth client IDs/secrets and delegated user tokens.
  • Automates the OAuth dance: consent, code exchange, token refresh.
  • ADK integration injects Authorization / X-Goog-Api-Key headers into tool and MCP calls, so the credentials never live in agent code.
  • Access to auth providers is governed by IAM using the agent's SPIFFE identity. User grants can be viewed and revoked.
  • With Agent Gateway + Gemini Enterprise, end-user credentials are encrypted by the auth manager and decrypted at the gateway, so the agent never sees the raw credential.
  • Constraint: some providers (e.g., GitHub, Microsoft) support only a single scope.
  • API migration: auth providers were first exposed through the IAM Connectors API (iamconnectors.googleapis.com, Preview), which will not reach GA. Use the Agent Identity API (agentidentity.googleapis.com; credential calls on agentidentitycredentials.googleapis.com), where resources are named authProviders/ instead of connectors/. Both run side by side during migration.

Secret Manager

  • Agent Runtime secret env vars: env_vars={"API_KEY": {"secret": "SECRET_ID", "version": "latest"}}. Only same-project secrets can be referenced.
  • Grant roles/secretmanager.secretAccessor to the agent identity. When secrets are injected as env vars at deploy time, also grant it to the Agent Platform service agent.
  • ADK SecretManagerClient fetches secrets at runtime, so a rotated secret takes effect without a redeploy or restart.

Decision rule

Per-user consent → 3LO through the auth manager. Static third-party key → Secret Manager (or an auth-manager API-key provider). Google Cloud API → the agent's own identity with least-privilege IAM. Never put secrets in code, prompts or plaintext env vars.

Identity propagation, hop by hop

Each hop checks a different credential against a different policy. Access to the data succeeds only when every hop allows it.

01

User → front end

User sign-in session (Cloud Identity or federated IdP), checked by Gemini Enterprise or the front end: may this user use the app and agent?

02

Front end → agent

Caller identity plus the user's context, checked by Agent Runtime: IAM permission to query the agent (e.g., roles/aiplatform.user) and ingress gateway policies if Client-to-Agent is enabled.

03

Agent → Agent Gateway

Agent Identity credential (mTLS + DPoP) plus the injected tool credential. REQUEST_AUTHZ (IAP: UAP, PAB) runs first, then CONTENT_AUTHZ (Model Armor, Semantic Governance).

04

Gateway → tool or MCP server

The destination's credential (3LO token, 2LO token, API key or the agent's Google token), checked by destination IAM, e.g., roles/iap.httpsResourceAccessor for an IAP-protected Cloud Run server or roles/mcp.toolUser for Google remote MCP, plus OAuth scopes.

05

Tool → data source

The user's delegated token, the agent's identity, or the MCP server's own service account, checked by source IAM and ACLs (row/column rules, document sharing) and the VPC-SC perimeter.

Example: on first use the auth manager redirects the user to Jira for consent and vaults the token; the agent then sends tools/call with its Agent Identity and that token through the gateway, the MCP server forwards the user token, and Jira returns only that user's records, which Model Armor screens on the way back.

Exam trap

If the MCP server queries the data source with its own broad service account, the user's identity stops at the server and the source can no longer filter by user. Propagate the user token (3LO) to the last hop when results must be user-specific.

Access Boundaries: IAM, Deny & PAB

Policy types compared

PolicyEffectGranularityAnswers
IAM allow policyGrants rolesResource + role (+ condition)"What may this principal do?"
IAM deny policyDenies specific permissions; overrides allowPermission-level"What must it never do, whatever its roles?"
Principal Access Boundary (PAB)Limits which resources a principal is eligible to accessOrg/folder/project (up to 500 resources per policy, effect ALLOW only)"Where can it ever operate?"
Unified Access Policy (gateway)Allow/deny on agent traffic through Agent GatewayMCP tool, agent, endpoint, unregistered host/path/method"Which tools and destinations?"

Least privilege for agents

01

Own identity

Give each agent its own identity (Agent Identity), not the shared default service agent.

02

Narrow roles

Grant specific predefined roles on specific resources. Avoid Owner/Editor. Put baseline roles on the project principalSet; per-agent extras on the agent's principal://.

03

Deny + boundary

Add deny policies for permissions that must never be used (e.g., IAM admin). Bind a PAB policy to the agents' principal set so they can't reach resources outside approved projects, even if someone over-grants.

04

Tool-level at gateway

Govern tool-level access at the gateway (UAP) because Google Cloud IAM can't see MCP tool names.

PAB specifics

  • Rules list Resource Manager resources. PAB has an enforcementVersion and blocks only the permissions supported by that version.
  • Binding example: gcloud iam principal-access-boundary-policies bindings create … --target-principal-set=… (bound to a principal set, e.g., the agents in a project or org).
  • For agents, PAB can also be enforced on egress through Agent Gateway (via IAP).

Effective access and CEL conditions

  • Effective access = (resources granted by allow policies ∩ resources eligible under PAB) minus permissions blocked by deny policies.
  • Worked case: someone grants roles/bigquery.admin at the org level to the agents' principalSet. A PAB bound to that set that lists only the analytics-prod project keeps the agents out of every other project's datasets.
  • IAM conditions add CEL to an allow binding so the grant applies only in context, e.g., resource.name.startsWith("projects/_/buckets/agent-reports") or request.time < timestamp("2027-01-01T00:00:00Z") for a time-boxed grant.
  • Gateway CEL (in UAPs, see Gateway policies) works on tool and destination attributes that IAM conditions can't see, e.g., allow only when destination.agent_registry.mcp_server.tool.annotations.read_only_hint == true.

Exam trap

PAB doesn't grant anything. A principal needs an allow-policy role and must be inside its boundary and must not be denied.

04

Agent Registry, Skill Registry & Agent Gateway

Agent Registry

  • A central catalog for agents, MCP servers and tools, endpoints, and standalone skills (skills: Preview).
  • Automatic registration covers supported workloads in the governance project, including Google Cloud remote MCP servers (https://<service>.googleapis.com/mcp, enabled with the service API and requiring roles/mcp.toolUser / mcp.tools.call plus service IAM roles). Manual registration uses Service resources for remote, custom (e.g., MCP Toolbox for Databases or third-party SaaS connectors on Cloud Run/GKE), or cross-project components (gcloud agent-registry mcp-servers list).
  • Governance-project model: single-project or cross-project.
  • Agent Gateway queries the registry before routing, and policies reference registry identifiers (urn:agent: identifiers are for inventory, not for IAM bindings).
  • Limit: up to 5,000 Agent Registry resources per gateway.
  • Purpose: fight agent sprawl, fragmented tool access and redundant integrations.

Skill Registry (Preview)

  • A secure, private, low-latency repository of skills (instructions + code + docs) that agents discover and load on demand.
  • Includes a built-in gcp-skill-registry skill. Semantic Governance can constrain which skills an agent loads.

Agent Gateway

PathDirectionTypical controls
Client-to-AgentIngress (users/apps → agent)mTLS termination, IAP access policy, Model Armor screening of ADK streamQuery
Agent-to-AnywhereEgress (agent → tools, agents, LLMs, APIs)UAPs, PAB, Semantic Governance, Model Armor on MCP tools/call, A2A messages and OpenAI-compatible payloads
  • Mediates MCP, A2A, REST, gRPC, and inspects MCP JSON-RPC to extract tool names for policy.
  • Emits OpenTelemetry traces and access logs to Cloud Logging/Trace.
  • Works with the auth manager for OAuth and WIF.
  • Deployment models: Google-managed for Agent Runtime + Gemini Enterprise. GKE, Cloud Run and cross-cloud (self-managed Envoy + WIF) are coming soon / early preview.
  • Org governance: custom org policy constraints can restrict which gateways may be associated with agents.

Limitations

Gemini Enterprise supports only Agent-to-Anywhere (egress); Client-to-Agent is for Agent Runtime. Ingress governs query/streamQuery only. All agents in the same project + region bind to the same egress/ingress gateway. SCC Agent Engine Threat Detection isn't available while a gateway is enabled. VPC-SC works with Agent Gateway when the agent uses VPC connectivity (route all egress through your VPC, restricted VIP).

05

Gateway Policies: UAP & Semantic Governance

Unified Access Policies (IAM v3)

  • Bound to the project that holds the gateway; enforced by IAP. The permission involved is iap.googleapis.com/resources.egressViaIAP.
  • Default-deny: nothing passes unless an allow rule matches. Rules can mix allow and deny effects; deny overrides allow.
  • CEL conditions on attributes such as destination.agent_registry.mcp_server.tool.name, …tool.annotations.read_only_hint / destructive_hint, and destination.unregistered.host, .path, .method.
  • Rollout: set iamEnforcementMode: "DRY_RUN" in the IAP authorization extension metadata so IAP logs would-be denials to Cloud Audit Logs without blocking. Remove the field to start enforcing (see Audit and detection).
  • Best practices: dry-run first; name specific tools (no wildcards); use deny rules as guardrails (e.g., deny destructive_hint == true); audit regularly.

Semantic Governance (Preview)

  • Natural-language constraints evaluated by an LLM policy engine running in your VPC.
  • Intercepts each proposed tool call and runs two checks: (1) alignment with user intent (on by default): does this call serve what the user asked? (2) business-constraint compliance: e.g., "refunds may not exceed $75".
  • Verdict: ALLOW or DENY with a rationale. A custom denial message (≤1,000 chars) can replace the rationale.
  • Mitigates context poisoning / indirect prompt injection and rogue actions. Can also govern which skills load.
  • Complements IAM and UAP; doesn't replace them. Verdicts are probabilistic and can be wrong, so keep deterministic controls for hard limits.
  • Enforcement order: gateway policies run as Service Extensions authorization extensions. REQUEST_AUTHZ extensions see only headers (IAP evaluates identity and UAPs). CONTENT_AUTHZ extensions see full request and response bodies (Model Armor, Semantic Governance). A custom engine can use either profile.
NeedUse
Hard allow/deny by tool name, host, methodUAP (deterministic)

  • Built-in limits: each prompt or response is screened as a single turn with no conversation memory; Base64, hex, URL-encoded or encrypted text is not decoded; audio and video are not supported. Multi-turn or encoded attacks need other layers (Semantic Governance, HITL).
  • Templates hold filter configs. Enforcement is Inspect only or Inspect and block.
  • Floor settings set a minimum baseline at org, folder or project level that every template must meet.
  • Best practice: separate input and output templates; start at High/Medium; run inspect-only to tune; then block.
  • Model-agnostic and cloud-agnostic; findings appear in Security Command Center.
  • Regional endpoints from a VPC need a PSC endpoint. Document (PDF) screening is via the API, not the gateway integration.

Model Armor on Agent Gateway

  • Templates must be in the same region as the gateway.
  • Ingress roles roles/modelarmor.calloutUser + roles/modelarmor.user for the Reasoning Engine service agent. Egress: the same roles for the Service Extensions service agent.
  • Redaction requires an advanced SDP de-identify template and INSPECT_AND_BLOCK. If multiple detectors fire, the whole payload is blocked. Logs are redacted either way.
  • Ingress screens ADK streamQuery. Egress screens A2A SendMessage/AgentCard, MCP tools/call, prompts/get, tool-execution errors, and OpenAI-compatible LLM payloads. It does not screen tools/list, resources/*, notifications or MCP Streamable HTTP/SSE streams.

01

Enable logging first

INSPECT_ONLY produces nothing useful without Cloud Logging.

02

Start conservative

Separate input and output templates; RAI at HIGH; prompt injection at HIGH or MEDIUM_AND_ABOVE (HIGH for Gemini Enterprise to avoid false positives).

03

Replay known traffic

Run known-good and known-bad prompts and record the false-positive baseline.

04

Read the verdicts in logs

Check SanitizeOperationLogEntry records; a model refusal in the response body is not a Model Armor block.

05

Switch to block

Move to INSPECT_AND_BLOCK; lower a threshold only for the one category that is under-protected.

Anti-pattern

Turning on LOW_AND_ABOVE across all RAI categories on day one. The docs flag it as high false-positive risk for general content; reserve it for categories where a miss costs more than a wrong block.

Sensitive Data Protection (formerly DLP)

  • infoType detection, inspection and de-identification (masking, tokenization) via templates.
  • Use it inside Model Armor (advanced mode) for agent traffic, or directly to scan and de-identify data before it reaches a corpus or memory.

Gemini safety filters (model level)

  • Non-configurable filters (e.g., CSAM, PII) always apply.
  • Configurable harm categories: harassment, hate speech, sexually explicit, dangerous content.
  • Thresholds: BLOCK_LOW_AND_ABOVE, BLOCK_MEDIUM_AND_ABOVE, BLOCK_ONLY_HIGH, BLOCK_NONE, OFF. Method: SEVERITY (default) or PROBABILITY.
  • Per the docs, newer Gemini models default to OFF for configurable filters (verify for your model version).

Network & Data Protection

VPC Service Controls

  • Inside a perimeter, Agent Runtime keeps access to Google APIs, but public internet is blocked. For internet egress, use a PSC interface + RFC 1918 proxy VM + Cloud NAT.
  • Without VPC-SC the Google-managed tenant keeps default internet access, but it can't reach your private VPC or on-prem; plan a PSC-I (plus proxy if needed).
  • Deploys may need ingress rules for the Reasoning Engine service agent: pickle deploys need Cloud Storage + Artifact Registry; source deploys need Artifact Registry; bring-your-own-container needs none.
  • Agent Identity APIs (agentidentity.googleapis.com, agentidentitycredentials.googleapis.com) can be added to a perimeter (restricted VIP), and agent identities can appear in ingress/egress rules.
  • Violations are recorded as Policy Denied audit logs.

Private Service Connect

  • PSC interface (PSC-I): private egress from the agent to your VPC, on-prem or multicloud via a network attachment (subnet minimum /28). DNS peering resolves private names. Shared VPC is supported. Can't be changed without recreating the agent.
  • PSC endpoint: private ingress to Google APIs or regional endpoints (e.g., Model Armor, a sandbox).

CMEK

  • Set encryption_spec at creation, using a single-region key in the same region. Can't be changed after deploy.
  • Grant roles/cloudkms.cryptoKeyEncrypterDecrypter to the gcp-sa-aiplatform-re service agent.
  • Not covered by your key: metadata such as display names, descriptions, service-account emails, method names and env vars, so don't put secrets there.
  • Security controls such as CMEK aren't supported for preview models.

HITL & Governance at Scale

Human-in-the-loop approvals

  • ADK tool confirmation (Experimental): FunctionTool(fn, require_confirmation=True), or pass a function returning a bool (e.g., confirm only when amount > 1000).
  • Advanced confirmation returns a structured payload (approve/modify). Remote approvals can arrive via the REST API, which suits async approval UIs.
  • ADK graph workflows can pause on a request-input node until a human responds.
  • Use HITL for irreversible, high-blast-radius, regulated, or novel actions. Use deterministic code for hard limits, and Semantic Governance/Model Armor for scalable screening. See Responsible AI: stakes & HITL and ADK: HITL & resilience.

Glossary, Self-Assessment & Resources

Agent Identity
A per-agent SPIFFE-based principal with certificate-bound, auto-rotated credentials.
Auth manager
Credential vault and OAuth broker for agent-to-tool auth.
PAB
Principal Access Boundary, which caps the resources a principal is eligible to access.
UAP
Unified Access Policy, an IAM v3 allow/deny policy enforced by IAP on Agent Gateway traffic.
Semantic Governance
LLM-evaluated natural-language constraints on proposed tool calls (Preview).
Floor settings
The Model Armor minimum baseline across templates.
PSC-I
Private Service Connect interface for private agent egress.
Auth provider
An auth manager resource holding one integration's credentials (3LO, 2LO or API key); agents need roles/agentidentity.user on it.
Confused deputy
A privileged component tricked into using its authority for a caller who lacks it.
REQUEST_AUTHZ / CONTENT_AUTHZ
Gateway authorization profiles that inspect headers only (IAP) or full payloads (Model Armor, Semantic Governance).
Token exchange (RFC 8693)
Swapping one security token for another, as Workload Identity Federation's Security Token Service does.
Template conformance
The floor settings check that rejects any Model Armor template weaker than the effective floor at create or update time.
Inline enforcement
Project floor settings applied directly to Gemini generateContent and Google Cloud MCP traffic, with no template reference in code.
INSPECT_ONLY / INSPECT_AND_BLOCK
Model Armor enforcement types that log detections only, or log and return a block verdict.
Fail-open
A control that lets traffic through unscreened when it is unavailable, as the Gemini integration does if Model Armor can't be reached.
Referential integrity (SDP)
The same input always maps to the same output under one key and context, so joins and entity tracking survive de-identification.
Format-preserving encryption (FPE)
Reversible tokenization (CryptoReplaceFfxFpeConfig) that keeps the input's length and alphabet.
Surrogate infoType
A label prefixed to a deterministic token so content.reidentify can find and reverse it.
SDP content policy
A Sensitive Data Protection resource that Gemini Enterprise applies to connectors and uploads to block sensitive content.
iamEnforcementMode / sgpEnforcementMode
Authorization extension metadata keys that put IAP or Semantic Governance in DRY_RUN (log only); removing the key enforces.
Telemetry policy
The telemetryPolicies resource that turns on Cloud Trace sampling for an Agent Gateway.

Self-Assessment Questions (Click to Reveal)

Q1. Why do bindings break after a redeploy, and how do you prevent it?

A redeploy creates a new resource ID and therefore a new principal. Read spec.effectiveIdentity in CI/CD and put baseline roles on the project principalSet.

Q2. IAM deny vs PAB?

Deny blocks specific permissions; PAB limits which resources are reachable at all. Neither grants access.

Q3. Why can't IAM alone stop a destructive MCP tool call?

Google Cloud IAM doesn't see MCP tool names; a gateway UAP on tool.name/destructive_hint does.

Q4. When does Semantic Governance help where UAP can't?

When the tool is allowed but the specific call doesn't match user intent (indirect injection) or breaks a business rule.

Q5. What's needed to redact PII through Model Armor on the gateway?

An advanced SDP de-identify template plus INSPECT_AND_BLOCK.

Q6. Which audit logs must you enable to see model usage?

Data Access logs. Viewing them requires Private Logs Viewer (roles/logging.privateLogViewer).
