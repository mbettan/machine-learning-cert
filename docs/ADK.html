Overview & Core Mechanics

Definition

ADK is Google's open-source, code-first framework (Python, TypeScript, Java, Go, Kotlin) for building, evaluating and deploying AI agents. It supplies the agent loop as infrastructure: an execution engine, tool runtime, scoped state and memory, multi-agent delegation, guardrail hooks, evaluation and one-command deployment.

Why ADK? (Raw model API limits)

a model API is stateless (remembers nothing between calls), cannot act (it can only request a tool call), has no control flow (no durable loop, branching, checkpointing or stop condition) and no governance (no audit trail, approval gate or isolation between users). ADK supplies all four, so you build the agent instead of the plumbing.

Mental model

The model is the brain. ADK is the body and nervous system: hands (tools), memory (sessions), reflexes (callbacks) and a spine (the Runner) that decides when the brain thinks and when the hands move.

Workflow

1. Define (Agent + tools + instruction) → 2. Run (Runner loads the session, calls the model, executes tools, commits every step as an Event) → 3. Evaluate (adk eval grades answers and tool trajectories) → 4. Deploy (Agent Runtime, Cloud Run or GKE).

Workflows vs. agents

a workflow orchestrates LLMs and tools through predefined code paths (railway tracks). An agent directs its own process (a taxi). Both are "agentic systems".

The "agent theater" litmus test

multi-agent is justified **only if sub-agents have independent tools, private data, an independent verifier role (include_contents='none' + external check) or human-gated steps.** Splitting one prompt into three persona agents plus a synthesizer costs ~4× the tokens and 1.5–2.5× the latency for marginal quality gains.

Common trap

"SDK" ≠ "ADK". The Gen AI SDK (google-genai) is a model API client: it can run a short in-process function-calling helper (10 calls default) and keep in-memory chat history, but has no persistent sessions, event ledger, multi-agent delegation, callbacks/plugins, evals or deployment. ADK is the agent framework built on top of it.

Context objects

InvocationContext (one per turn: session, agent, run config), ReadonlyContext (InstructionProvider: read-only ctx.state), CallbackContext (agent/model callbacks: state, artifacts), ToolContext (tools and tool callbacks: state, artifacts, auth, search_memory, confirmation, actions).

Event ledger

every step is appended to session.events as an Event with author, invocation_id, content (text or function call/response parts) and actions (state_delta, artifact_delta, transfer_to_agent, escalate, skip_summarization). One ledger feeds debugging (adk web), audit trails, evaluation (tool trajectories) and memory extraction.

Common trap

putting memory inside the agent object (Agent(memory=Buffer())). Under concurrent requests users' data bleeds together. State belongs to the SessionService, partitioned by the 3-tier isolation keys app_name → user_id → session_id.

3. Agent Types and Deterministic Control Flow

All agents derive from BaseAgent. Only LlmAgent uses a model to decide; workflow agents never call a model to route. (In ADK 2.0, SequentialAgent, ParallelAgent, LoopAgent and custom BaseAgent workflows are **deprecated in favor of graph Workflow** in §5, though both appear on exams.)

AgentControl flowUse forKey parameter
**LlmAgent** (alias Agent)Model-driven (ReAct)Reasoning, tool use, dynamic routingoutput_key, output_schema, sub_agents, tools, planner
**SequentialAgent**Fixed order 1 → 2 → 3Pipelines where each step feeds the nextsub_agents
**ParallelAgent**Concurrent fan-out (isolated branch tag, shared session.state)Independent retrievals or checksDistinct output_key per branch
**LoopAgent**Repeat until exitRefinement, polling, critic loopsmax_iterations + escalate

from google.adk.agents import LlmAgent, SequentialAgent, ParallelAgent, LoopAgent
from google.adk.tools import ToolContext

def exit_loop(tool_context: ToolContext) -> dict:
    """Call ONLY when the critique says the draft needs no further changes."""
    tool_context.actions.escalate = True           # stops the enclosing LoopAgent
    tool_context.actions.skip_summarization = True # skip extra LLM call after exit tool
    tool_context.state["temp:approved"] = True     # distinguish approval from max_iterations
    return {"status": "approved"}

research = ParallelAgent(name="research", sub_agents=[
    LlmAgent(name="market", instruction="Find market data.", tools=[search], output_key="market"),
    LlmAgent(name="pricing", instruction="Find competitor pricing.", tools=[search], output_key="pricing"),
])
refine = LoopAgent(name="refine", max_iterations=3, sub_agents=[
    LlmAgent(name="writer", instruction="Write or revise using {market}, {pricing}, {critique?}.", output_key="draft"),
    LlmAgent(name="critic", instruction="Critique {draft}. If no issues remain, call exit_loop.",
             tools=[exit_loop], output_key="critique"),
])
root_agent = SequentialAgent(name="report", sub_agents=[research, refine])
  • Data passing: output_key="x" saves the agent's final response to state["x"]; downstream instructions read it as {x} ({x?} if it may be missing; {artifact.name} injects a text artifact).
  • **Dynamic instructions (InstructionProvider):** if an instruction contains literal curly braces (JSON examples, regexes, format strings) or needs branching logic, pass a callable def build_prompt(ctx: ReadonlyContext) -> str:: ADK skips {var} auto-templating when instruction is a function.
  • Loop termination: a LoopAgent stops when a sub-agent or tool sets escalate=True, or when max_iterations trips. **When max_iterations trips, LoopAgent exits silently** (no exception), and the next step in an outer SequentialAgent still runs: record temp:approved = True in the exit tool and gate the downstream step via before_agent_callback.
  • Reflection cost: every critic cycle adds model calls and grows history. To prevent self-grading bias, use a separate verifier (temperature=0, include_contents='none', its own verification tools, explicit pass rubric).

Common trap

a SequentialAgent does not route; it runs every sub-agent in order. A LoopAgent(max_iterations=3) around "write code → run tests" runs all 3 iterations even when the tests pass, unless something sets escalate.

5. Graph Workflows (ADK 2.0), Planners and Custom Agents

ADK 2.0 replaces SequentialAgent / ParallelAgent / LoopAgent with a unified graph engine: Workflow(edges=[...]) wires LlmAgents, plain Python functions (FunctionNode) and nested Workflows into a directed graph. Function return values flow to the next node as typed input (node_input); parameters matching state keys are injected automatically.

from google.adk import Workflow
from google.adk.workflow import START, END, JoinNode
from google.adk.events import Event

def route_ticket(node_input: str) -> Event:        # conditional edge via Event(route=...)
    target = "urgent_agent" if "outage" in node_input.lower() else "standard_agent"
    return Event(output=node_input, route=target)

root_agent = Workflow(name="triage", edges=[
    (START, route_ticket, ("urgent_agent", "standard_agent")),
    (("urgent_agent", "standard_agent"), END),
])

def file_read(path: str) -> dict:
    """Read a UTF-8 text file inside the project sandbox (read-only, max 1 MB).

    Args:
        path: Path relative to the project root.
    """
    target = (BASE_DIR / path).resolve()
    if not target.is_relative_to(BASE_DIR):
        return {"status": "error", "error_message": "Path outside sandbox."}
    return {"status": "success", "content": target.read_text()[:1_000_000]}
  • Tool families: FunctionTool (async def functions run concurrently when the model emits parallel tool calls), AgentTool, LongRunningFunctionTool, Gemini built-ins (google_search, VertexAiSearchTool, BuiltInCodeExecutor), Google Cloud toolsets (BigQueryToolset with BigQueryToolConfig(write_mode=WriteMode.BLOCKED), SpannerToolset, ApiHubToolset, ApplicationIntegrationToolset, ToolboxToolset), OpenAPIToolset, McpToolset, SkillToolset.
  • Gemini built-in tool constraint: built-in tools (google_search, VertexAiSearchTool, BuiltInCodeExecutor) execute inside the Gemini API call and cannot be freely mixed with custom function tools or placed inside sub_agents transfer targets on all models. Either set bypass_multi_tools_limit=True on Python search tools (GoogleSearchTool(bypass_multi_tools_limit=True), VertexAiSearchTool(..., bypass_multi_tools_limit=True)) or isolate each built-in on its own specialist wrapped in AgentTool(agent=...).
  • Structured output: output_schema=<Pydantic model> forces the agent's final answer into a schema; combine with output_key to pass typed data to the next agent. For high-stakes pipelines add epistemic fields (confidence, citations, escalation_required: bool = True by default, so the pipeline must earn auto-approval).

Common trap

on models/SDK versions where output_schema disables tool calling (or forces an extra schema-conversion step), let a tool-using agent gather data and add a separate formatter agent (output_schema=MySchema, include_contents='none') at the end of a SequentialAgent.

9. Skills and Progressive Disclosure

A tool is a function; a skill is packaged expertise (instructions + resources + scripts) loaded only when needed, so the prompt doesn't inflate as capabilities grow.

TierContentLoaded by
L1 metadataYAML frontmatter name (kebab-case matching directory) + description (~60 tokens)list_skills (or injected eagerly into system prompt)
L2 instructionsFull SKILL.md body (< 500 lines)load_skill
L3 resourcesreferences/, assets/, scripts/load_skill_resource, run_skill_script (requires a code_executor on the agent/toolset)
  • ADK wiring: load_skill_from_dir(Path("./skills/my-skill")) or inline models.Skill(frontmatter=..., instructions=...) passed to SkillToolset(skills=[...], code_executor=...); with a SkillRegistry (e.g. GCPSkillRegistry) the agent also gets search_skills.
  • Authoring & bundled scripts: the frontmatter description is the routing index, so write it the way users phrase requests. Scripts must be (1) non-interactive (CLI flags/env vars only; stdin hangs in headless containers), (2) self-documenting (--help), and (3) emit structured JSON on stdout with actionable errors on stderr + non-zero exit codes.
  • Toolset ≠ skill: a group of related tools sharing config (e.g. McpToolset, any BaseToolset) is a toolset, not a SKILL.md skill.

Common trap

a malicious SKILL.md or script is prompt injection through the filesystem. Load skills only from allowlisted roots, review them like code and provide a sandboxed code_executor when enabling run_skill_script.

def block_injection(callback_context, llm_request):
    last = llm_request.contents[-1] if llm_request.contents else None
    text = (last.parts[0].text or "") if last and last.parts else ""
    if INJECTION_PATTERN.search(text):
        return LlmResponse(content=types.Content(role="model",
                           parts=[types.Part(text="I can't help with that request.")]))
    return None                                   # proceed to the model

agent = LlmAgent(name="assistant", model="gemini-3.8-flash", before_model_callback=block_injection)
  • **Plugins (BasePlugin):** register once on App(name=..., root_agent=..., plugins=[...]) (Runner(plugins=...) is deprecated) to apply hooks across every agent, model and tool call in the hierarchy. Execution order: plugin callbacks run before agent-level callbacks, and the first non-None return short-circuits remaining hooks in that phase.
  • Escalation thresholds: map a composite quality score to deterministic actions, e.g. ≥ 0.85 proceed, 0.70–0.85 flag for verification, < 0.70 hard stop and human escalation.

Common trap

redacting PII only in after_model_callback is too late: raw tool outputs have already been sent to the LLM and persisted in session.events. Scrub PII at the tool boundary (after_tool_callback and before_tool_callback), and keep after_model_callback as the final output backstop.

11. Human-in-the-Loop, Resilience and Durability

Rule of thumb

if a step can change user data, send something externally or spend money, pause for approval before it runs.

Exception handling ladder across ADK's 3 recovery layers

  • Transport (HTTP 429/503): configure HttpRetryOptions(attempts=3, initial_delay=1.0, exp_base=2.0) on the Gemini model's retry_options.
  • Tool self-correction: ReflectAndRetryToolPlugin(max_retries=3, throw_exception_if_retry_exceeded=False) feeds tool errors back to the LLM so it can fix malformed arguments. Caveat: by default it only intercepts raised tool exceptions; if your tools return {"status": "error", ...} dicts, override extract_error_from_result on the plugin.
  • Model failover & human escalation: catch persistent model/quota errors in on_model_error_callback (Python) or RoutedLlm (TypeScript, experimental) to switch models, and escalate to a human after N consecutive tool failures tracked in state.
  • Idempotency: retries and resumption can re-execute a completed tool call if the process crashed before the event commit, so side-effecting tools need check-before-create or idempotency keys.
  • Goal monitoring: store explicit success criteria in state and let a checker agent or callback compare progress to them; escalate, don't loop, when the goal is unreachable.

14. Evaluation and Observability

Grade the path, not just the answer. An agent that answers correctly after 15 erratic tool calls (where 3 would do) is still failing in production.

  • Built-in efficiency metrics vs. custom thresholds: ADK automatically emits tool_call_count_v1, inference_call_count_v1, token_usage_v1 and invocation_duration_v1 as **INFORMATIONAL** metrics (setting a pass/fail threshold on them in test_config.json raises an error). To fail a test on call budgets or forbidden tools, register a Python function under custom_metrics (code_config: {"name": "pkg.mod.metric_fn"}).
  • LLM-as-judge rules: grade against reference facts, require reasoning before the score, return JSON; a 3-judge majority vote stabilizes borderline cases. Keep red-team cases (jailbreaks, indirect injection, empty/huge inputs) in the evalset permanently.
  • Observability: native OpenTelemetry spans (invoke_agent, call_llm, execute_tool); --otel_to_cloud exports to Cloud Trace (--trace_to_cloud is deprecated); set ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false in production so raw prompts, tool args and PII are omitted from traces.

Common trap

response_match_score is lexical (ROUGE-1), so a correct paraphrase can fail. Use final_response_match_v2 or a rubric when wording legitimately varies. And EXACT trajectory matching fails agents that make harmless extra calls; use IN_ORDER or ANY_ORDER when order or extras don't matter.

import asyncio
from google.genai import types
from google.adk.agents import Agent
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService

agent = Agent(name="assistant", model="gemini-3.8-flash", instruction="You are a helpful assistant.")

async def main(query: str) -> str:
    session_service = InMemorySessionService()            # swap for Database/VertexAi in prod
    session = await session_service.create_session(app_name="demo", user_id="u1")
    runner = Runner(agent=agent, app_name="demo", session_service=session_service)
    msg = types.Content(role="user", parts=[types.Part(text=query)])
    final_text = ""
    async for event in runner.run_async(user_id="u1", session_id=session.id, new_message=msg):
        if event.is_final_response() and event.content and event.content.parts:
            # In multi-agent workflows EVERY sub-agent emits is_final_response(); drain the stream
            # and skip thinking parts (p.thought == True) so you keep the last agent's answer.
            final_text = "".join(p.text or "" for p in event.content.parts if not getattr(p, "thought", False))
    return final_text

print(asyncio.run(main("Hello!")))

In Python ADK, setting StreamingMode.BIDI on run_async() is a silent no-op: only run_live() opens a Gemini Live session (StreamingMode.SSE on run_async() streams text tokens).

Self-Assessment Questions (Click to Reveal)

Q1. Why does storing conversation state on an Agent instance cause cross-user data leaks under concurrent traffic, and how does ADK solve this?

An Agent instance is a stateless specification shared across requests. Conversation history and working state belong in the SessionService, isolated by the 3-tier key hierarchy app_name → user_id → session_id and mutated exclusively via committed Event deltas.

Q2. What happens when a LoopAgent(max_iterations=3) reaches its iteration ceiling without any tool setting escalate = True, and how do you prevent an unapproved draft from reaching the next step in an outer SequentialAgent?

LoopAgent exits silently when max_iterations trips—it does not raise an exception—so the next agent in an outer SequentialAgent still runs. Have the exit tool set tool_context.state["temp:approved"] = True alongside tool_context.actions.escalate = True, and verify temp:approved in the downstream agent's before_agent_callback.

Q3. When delegating to a specialist, how does sub_agents=[specialist] differ from wrapping the specialist in AgentTool(agent=specialist)?

With sub_agents (LLM transfer via transfer_to_agent), the child takes over the conversation and answers the user directly on the shared session history. With AgentTool, the parent calls the child like a function in an isolated child session, forwards the child's state/artifact deltas back, and retains control of the conversation.

Q4. Why is scrubbing PII only inside after_model_callback insufficient when an agent queries external customer APIs or support tickets?

By the time after_model_callback runs, raw tool outputs containing PII have already been sent to the model context and recorded in session.events. Scrub PII at the tool boundary (after_tool_callback and before_tool_callback) and keep after_model_callback as the final output backstop.

Q5. An agent uses ReflectAndRetryToolPlugin(max_retries=3) and returns {"status": "error", "error_message": "..."} dictionaries from its tools, yet the plugin never triggers a retry. Why?

By default, ReflectAndRetryToolPlugin only intercepts raised Python exceptions. When tools return structured error dictionaries instead of raising, you must override extract_error_from_result on the plugin so it recognizes the error dictionary and triggers reflection.

Q6. Why does returning on the first if event.is_final_response(): inside a runner.run_async(...) loop return an incomplete answer in a multi-agent pipeline?

In multi-agent workflows (SequentialAgent, LoopAgent, sub_agents), every sub-agent emits its own is_final_response() event when its turn completes. Always drain the entire run_async generator (filtering out thinking parts where p.thought == True) so you capture the final step's response.
