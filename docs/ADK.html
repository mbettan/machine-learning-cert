Overview & Core Mechanics

Definition

Agent Development Kit (ADK) is Google's open-source, code-first framework (Python, TypeScript, Go, Java, and Kotlin) for building, evaluating, governing, and deploying production AI agents. Rather than leaving teams to hand-roll conversation state, tool dispatch, retries, and trace instrumentation around a raw model endpoint, ADK provides the agent harness as modular infrastructure: an event-sourced execution runtime, typed tool and protocol connectors, multi-tier state and memory, multi-agent orchestration, deterministic callback/plugin guardrails, trajectory evaluation, and one-command cloud deployment.

Why ADK? (What a raw model API lacks)

A bare model endpoint is stateless (retains zero memory across HTTP requests unless using server-side interaction handles), passive (emits tool-call intents as JSON text without executing anything), unstructured in control flow (no durable loops, fan-out joins, checkpoints, or hard iteration caps), and ungoverned (no tenant isolation, approval gates, or tool-boundary PII scrubbing). ADK supplies all four layers cleanly decoupled from model weights.

Mental model

Treat the foundation model (Gemini 4 Argon, Gemini 3.8 Flash, Claude, or Gemma 4) as the brain, and ADK as the nervous system and skeleton: hands (FunctionTool, McpToolset), short- and long-term memory (SessionService, MemoryService), spinal reflexes (before_tool_callback, BasePlugin), and the motor loop (Runner / Workflow) that coordinates when the brain reasons and when tools act.

End-to-end lifecycle

1. Define (LlmAgent / Workflow / ManagedAgent + tools + instructions) → 2. Run (Runner loads session state, invokes the model or Interactions API, executes tools, and commits each step as an immutable Event) → 3. Evaluate (adk conformance + adk eval in CI, paired with Agent Platform Gen AI Evaluation Service in cloud) → 4. Deploy (Agent Runtime, Cloud Run, or GKE).

The "agent theater" litmus test

Splitting a system into multiple agents is justified **only when specialists require distinct tool permissions, isolated data scopes, an independent auditor (include_contents='none' + verification tools), or explicit human sign-off boundaries.** Breaking a single prompt into four chatty persona agents sharing identical context and zero tools burns ~4× the tokens and ~2× the latency without improving accuracy.

`LlmAgent` (`GenerateContent`) vs. `ManagedAgent` (`Interactions API`)

  • **Standard LlmAgent:** Your ADK Runner owns the orchestration loop, re-sending compacted conversation history (and cryptographic Thought Signatures) over GenerateContent while executing custom Python FunctionTools and McpToolset connections inside your runtime environment.
  • **ManagedAgent (Preview):** Invokes a pre-existing hosted agent (agent_id, such as antigravity-preview-... or a custom agent provisioned via the Agents API control plane) over the Interactions API (stream=True) with environment={'type': 'remote'}. Reasoning, built-in tools (google_search, ToolCodeExecution), and sandbox execution happen inside Google's managed cloud infrastructure while partial and final events stream into your ADK workflow.
  • **State split in ManagedAgent:** ADK never re-transmits prior conversation turns to a ManagedAgent. Instead, the local Session records only two lightweight pointers on emitted events—**previous_interaction_id and environment_id**—and reuses them on subsequent turns so the server-side Interaction and remote container sandbox continue seamlessly.
  • **Direct Interactions API (client.interactions.create) for long-horizon tasks:** When calling gemini-4-argon or Deep Research directly via google-genai, setting background=True runs multi-minute tasks asynchronously on the server (preventing ~60s HTTP gateway timeouts and unlocking long decodes up to the unified 1,048,576-token window). Chaining a follow-up request via previous_interaction_id while the prior interaction is still in_progress returns **400 Bad Request**—poll until completed first.
# ManagedAgent runs server-side via Interactions API; coordinator wraps it as AgentTool
web_researcher = ManagedAgent(
    name="managed_web_researcher",
    description="Grounded web synthesis in Google's remote managed environment.",
    agent_id=os.environ.get("MANAGED_AGENT_ID", "antigravity-preview-09-2026"),
    environment={"type": "remote"},
    tools=[google_search],  # Server-side tools only; local tools raise NotImplementedError
)
coordinator = LlmAgent(
    name="portfolio_coordinator",
    model="gemini-4-argon",
    instruction="Combine internal CRM lookups with external web research.",
    tools=[AgentTool(agent=web_researcher)],
)

Context hierarchy & Event ledger

InvocationContext (full per-turn runtime handle), ReadonlyContext (passed to InstructionProvider callables for read-only ctx.state), CallbackContext (agent/model hooks: mutable state + artifacts), and ToolContext (tools + tool hooks: state, artifacts, credentials, search_memory, confirmation, and actions). Every state change, tool call, transfer, or escalation is recorded as an Event (author, invocation_id, content, actions.state_delta, actions.artifact_delta), creating a single source of truth for adk web time-travel inspection, Cloud Audit trails, and trajectory grading.

Common trap

Passing client-executed Python functions or an McpToolset into ManagedAgent(tools=[...]) raises **NotImplementedError**, and pointing ManagedAgent at a regional Agent Platform endpoint fails because the Managed Agents API is served exclusively from **global**. Keep custom/MCP tools on an LlmAgent and compose ManagedAgent beside it.

3. Agent Types and Deterministic Control Flow

Every ADK agent inherits from BaseAgent. Only LlmAgent (and ManagedAgent) consult a model to decide next steps; workflow agents route deterministically in code with zero LLM routing overhead. *(In ADK 2.0 for Python, TypeScript, and Go, SequentialAgent, ParallelAgent, LoopAgent, and custom BaseAgent orchestrators are superseded by unified graph Workflows in §5, though both patterns remain active in Java/Kotlin and exam scenarios.)*

**SequentialAgent**Strict linear order A → B → CStaged pipelines where step N consumes step N-1's output_keysub_agents=[...]
**ParallelAgent**Concurrent execution (branch isolated, shared session.state)Multi-source retrieval, independent compliance checksUnique output_key per parallel branch
**LoopAgent**Iterative cycle until exit signal or capDraft → critique → revise loops, pollingmax_iterations + tool setting actions.escalate = True

def approve_patch(tool_context: ToolContext) -> dict:
    tool_context.actions.escalate = True            # Halts enclosing LoopAgent immediately
    tool_context.actions.skip_summarization = True  # Suppresses redundant post-tool LLM turn
    tool_context.state["temp:verified"] = True      # Proves convergence vs max_iterations cap
    return {"status": "verified"}

patch_loop = LoopAgent(name="patch_and_verify", max_iterations=3, sub_agents=[
    LlmAgent(name="patcher", model="gemini-3.8-flash", instruction="Write patch for {cve}.", output_key="diff"),
    LlmAgent(name="auditor", model="gemini-4-argon", include_contents="none",
             instruction="Verify {diff}. Call approve_patch only if tests pass.",
             tools=[run_tests, approve_patch], output_key="audit"),
])
root_agent = SequentialAgent(name="pipeline", sub_agents=[gather_agent, patch_loop])
  • **State templating & InstructionProvider:** Setting output_key="cve" writes the agent's final text to state["cve"], which downstream instructions reference via {cve} (use {audit?} when optional so turn 1 doesn't raise KeyError, or {artifact.report} to inline text artifacts). Whenever an instruction includes literal curly braces—such as JSON schemas {"status": "ok"} or regex quantifiers—supply a callable def build_instruction(ctx: ReadonlyContext) -> str: so ADK bypasses {var} placeholder parsing.
  • **Silent LoopAgent exhaustion:** Reaching max_iterations exits LoopAgent silently without raising an exception, allowing any subsequent agent in an outer SequentialAgent to run on unapproved output. Always write an explicit convergence flag (state["temp:verified"] = True) inside your exit tool and check it in the downstream step's before_agent_callback.
  • Independent verification: Prevent self-grading bias in critic loops by isolating the verifier (include_contents="none", dedicated deterministic test/linter tools, and explicit pass/fail criteria).

Common trap

Expecting SequentialAgent to skip irrelevant steps dynamically or expecting LoopAgent(max_iterations=3) to stop automatically when tests pass. SequentialAgent always runs every child in sequence, and LoopAgent always runs all max_iterations unless a tool or callback sets escalate = True.

Writing instructions like "Call transfer_to_billing()" in mode="chat". ADK does not create per-agent transfer functions in chat mode—it exposes a single transfer_to_agent(agent_name="billing") tool (per-specialist tools are generated only in ADK 2.0 mode="single_turn" / "task" or via AgentTool).

5. Graph Workflows (ADK 2.0), Planners and Gemini 4 Argon Thinking Levels

ADK 2.0 Graph Engine (`Workflow`)

Available across Python, TypeScript, and Go, Workflow(edges=[...]) unifies sequential pipelines, parallel fan-out/fan-in, cyclic loops, and conditional routing into one directed graph combining LlmAgents, plain code nodes (FunctionNode), ManagedAgents, and nested Workflows. Return values pass as typed node_input, and function parameters matching session.state keys are dependency-injected automatically.

def classify_severity(node_input: str) -> Event:
    target = "deep_architect" if "architecture" in node_input.lower() else "fast_responder"
    return Event(output=node_input, route=target)  # Route key for conditional edge

deep_architect = LlmAgent(name="deep_architect", model="gemini-4-argon",
    planner=BuiltInPlanner(thinking_config=types.ThinkingConfig(thinking_level="high")))
fast_responder = LlmAgent(name="fast_responder", model="gemini-3.8-flash",
    planner=BuiltInPlanner(thinking_config=types.ThinkingConfig(thinking_level="low")))

root_agent = Workflow(name="support_graph", edges=[
    (START, classify_severity),
    (classify_severity, {"deep_architect": "deep_architect", "fast_responder": "fast_responder"}),
    (("deep_architect", "fast_responder"), END),
])

Passing thinking_level="minimal" on **gemini-4-argon or gemini-3.8-flash**, OR passing legacy integer thinking_budget=... on **gemini-4-argon, fails immediately with HTTP 400 INVALID_ARGUMENT**.   • **Memory Bank vs. RAG Memory vs. Enterprise Grounding (PAA 3.1 / 3.2):**
    • **VertexAiMemoryBankService (Managed Memory Bank): Runs LLM fact extraction and contradiction consolidation** (await memory_service.add_session_to_memory(session) → GenerateMemories, typically triggered in after_agent_callback). Common trap

Mutating session.state["user:plan"] = "pro" directly on the object returned by await session_service.get_session(...). That mutates a detached snapshot, skips append_event(), leaves zero audit trail, and drops the write in PostgreSQL / Agent Runtime. Always mutate state through tool_context.state, callback_context.state, output_key, or EventActions(state_delta={...}).

8. MCP, A2A and Agent Registry Integration

**MCP is vertical (Agent → Tools/Resources); A2A is horizontal (Agent → Peer Agent). Enterprise architectures combine both under Agent Registry** governance (PAA 3.2 / 3.3).

    tool_name_prefix="erp",

# Horizontal: cross-org or cross-language specialist discovered via A2A Agent Card

Scrubbing PII exclusively in after_model_callback. Self-Assessment Questions (Click to Reveal)

Q1. Why does storing conversation state on an Agent instance cause cross-user data leaks under concurrent traffic, and how does ADK solve this?

An Agent instance is a stateless specification shared across requests. Conversation history and working state belong in the SessionService, isolated by the 3-tier key hierarchy app_name → user_id → session_id and mutated exclusively via committed Event deltas.

Q2. What happens when you pass thinking_level="minimal" or legacy integer thinking_budget to BuiltInPlanner on gemini-4-argon, and which model tier supports "minimal"?

Both fail immediately with HTTP 400 INVALID_ARGUMENT on gemini-4-argon (and "minimal" also fails on gemini-3.8-flash). Use thinking_level in ('low', 'medium', 'high') on gemini-4-argon and gemini-3.8-flash, and use gemini-3.5-flash-lite when you want thinking_level="minimal" (its default) for sub-200ms routing.

Q3. How does ManagedAgent manage conversation history and sandbox continuity over the Interactions API compared to a standard LlmAgent?

ManagedAgent never re-sends prior transcript turns. It persists only previous_interaction_id and environment_id on local ADK session events while full interaction history and remote sandbox state live server-side (pinned to the global location on Agent Platform and restricted to server-side tools).

Q4. What happens when a LoopAgent(max_iterations=3) reaches its iteration ceiling without any tool setting escalate = True, and how do you gate the next step in an outer SequentialAgent?

LoopAgent exits silently when max_iterations trips—it raises no exception—so downstream steps still run. Have the exit tool set tool_context.state["temp:approved"] = True alongside tool_context.actions.escalate = True, and verify temp:approved in the downstream agent's before_agent_callback.

Q5. When delegating to a specialist, how does sub_agents=[specialist] differ from wrapping the specialist in AgentTool(agent=specialist)?

With sub_agents (LLM transfer via transfer_to_agent), the child takes over the conversation and answers the user directly on the shared session history. With AgentTool, the parent calls the child like a function in an isolated child session, merges the child's state/artifact deltas back, and retains control.

Q6. Why is scrubbing PII only inside after_model_callback insufficient when an agent queries external customer APIs or support tickets?

By the time after_model_callback runs, raw tool outputs containing PII have already been sent to the model context and committed to session.events. Scrub PII at the tool boundary (after_tool_callback and before_tool_callback) and keep after_model_callback as the final output backstop.

Q7. When should you use adk conformance test --mode=replay vs. adk eval vs. the Agent Platform Gen AI Evaluation Service?

Use adk conformance test --mode=replay on every commit for sub-5s deterministic callback/routing checks with zero LLM calls; use adk eval (*.test.json / *.evalset.json) for in-repo CI golden trajectory gates; and use the managed Gen AI Evaluation Service for Adaptive Rubrics, custom Autoraters, 2-Step Agent Simulation from Agent Registry snapshots, Environment Simulation (503/429 fault injection), and Online Evaluation Monitors across any language or framework.

Q8. Why does returning on the first if event.is_final_response(): inside a runner.run_async(...) loop return an incomplete answer in a multi-agent pipeline?

In multi-agent workflows, every sub-agent emits its own is_final_response() event when its turn finishes. Always drain the entire run_async generator (filtering out internal thinking parts where p.thought == True) so you capture the final agent's response.
