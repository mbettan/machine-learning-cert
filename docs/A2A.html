Definition & Scope

What is A2A?

The Agent2Agent (A2A) protocol is an open, vendor-neutral standard initiated by Google with 50+ enterprise partners and governed by the Linux Foundation. It defines how autonomous agents discover capabilities, negotiate modalities, delegate stateful tasks, stream incremental artifacts, and enforce enterprise security across organizational and framework boundaries.

A2A solves the Multi-Agent Silo problem: compliant agents built on Google ADK, LangGraph, CrewAI, or SaaS platforms (Workday, Salesforce, ServiceNow, SAP) collaborate as opaque peers without exposing internal prompts, session databases, tool credentials, or model weights.

Dimension Model Context Protocol (MCP) Agent2Agent Protocol (A2A)
Topology Vertical integration (Agent ↔ Tool / Database / Resource). Horizontal peer orchestration (Client Agent ↔ Remote Specialist Agent).
Execution Model Primarily stateless, schema-bound RPCs (tools/call) for deterministic actions and lookups. Stateful cognitive reasoning, multi-turn clarification (input-required), and asynchronous workflows spanning seconds to days.
Discovery Artifact tools/list JSON Schema over stdio or Streamable HTTP. AgentCard at /.well-known/agent-card.json (plus authenticated extended cards & Agent Registry).

Canonical Production Pattern

A front-door orchestrator in Gemini Enterprise distributes domain sub-goals over A2A to specialized departmental agents, and each specialist agent invokes its own private databases and APIs over MCP.

Core & Wire Protocol Architecture (v0.3 → v1.0)

User
Initiates the high-level goal and supplies primary identity/consent context.
A2A Client (Host / Client Agent)
Discovers remote AgentCard skills, decomposes goals, dispatches tasks, handles interruptions, and synthesizes returned artifacts.
A2A Server (Opaque Remote Agent)
Exposes an A2A endpoint and executes tasks autonomously — keeping internal prompts, memory, framework, and downstream MCP credentials completely opaque.

Three-Layer Wire Stack (a2a.proto)

  • 1. Canonical Data Model: Protobuf-defined structures (AgentCard, Task, Message, Part [TextPart, DataPart, FilePart], Artifact, TaskStatusUpdateEvent, TaskArtifactUpdateEvent).
  • 2. Abstract Operations (v1.0 PascalCase vs. v0.3 names): SendMessage (v0.3: message/send), SendStreamingMessage (message/stream), GetTask (tasks/get), CancelTask (tasks/cancel), SubscribeToTask (v0.3: tasks/resubscribe — reconnects SSE to an active in-flight task after network drop), and GetExtendedAgentCard (REST: GET /extendedAgentCard).
  • 3. Protocol Bindings (supportedInterfaces): Each interface declares a url and protocolBinding supporting JSONRPC (JSON-RPC 2.0 over HTTPS), HTTP+JSON (REST), or GRPC.

Task Lifecycle & State Machine

A2A tracks work via taskId (one stateful execution unit) grouped across multi-turn threads by contextId. Know the exact difference between active, interrupted, and terminal states:

CategoryStatesStream & Client Behavior
Activesubmitted, workingQueued or actively running; SSE streams stay open and emit status/artifact events
Interruptedinput-required, auth-requiredSSE stream closes cleanly; client gathers missing user input (input-required, natural HITL pause) or completes OAuth step-up (auth-required) and resumes using the same taskId + contextId
Terminalcompleted, failed, canceled, rejectedExecution permanently finished (rejected means the remote agent declined the request); follow-ups create a new taskId under the shared contextId

Transports, Discovery & Agent Cards

Four Interaction Transports

  • 1. Synchronous Request/Response (SendMessage): Single blocking HTTP exchange for fast sub-second to ~10s lookups.
  • 2. Streaming Updates (SendStreamingMessage + SSE): Server pushes real-time TaskStatusUpdateEvent and chunked TaskArtifactUpdateEvent payloads (append: false/true, lastChunk: true); reconnect dropped streams with SubscribeToTask.
  • 3. Asynchronous Polling (SendMessage → GetTask): Server returns submitted/working + taskId immediately; client polls GetTask when persistent SSE or inbound webhooks are blocked by firewalls.
  • 4. Push Notifications (Webhooks): Client supplies a pushNotificationConfig callback URL; server posts signed async state notifications across multi-hour or multi-day workflows without holding open connections (verify HMAC/JWT webhook signatures + replay nonces!).

Transport Selection Rule

Match transport to duration: using synchronous SendMessage or even long-lived SSE for a 4-hour research job hits proxy/Cloud Run (60-minute max) timeouts. Switch to Push Notifications (Webhooks) or Polling for multi-hour tasks.

Agent Cards & Four Discovery Mechanisms

  • Well-Known URI (RFC 8615): /.well-known/agent-card.json for open discovery. Version trap: early drafts showed agent.json / tasks/send; v0.3 used agent-card.json + message/send; v1.0 keeps agent-card.json with PascalCase SendMessage.
  • Curated Enterprise Registry (Google Cloud Agent Registry): Governed enterprise catalog with IAM access controls — prevents shadow/rogue agent sprawl.
  • Authenticated Extended Agent Card: Public card sets capabilities.extendedAgentCard: true (v0.3: supportsAuthenticatedExtendedCard); authenticated callers invoke GetExtendedAgentCard to retrieve sensitive internal skills.
  • Direct Configuration: Static pinned card URLs injected via Terraform/config for tightly coupled private services.

Intra-App AgentTool vs. Inter-App A2A

A core Professional Agentic Architect design decision is choosing between in-process composition (ADK sub_agents transfer or AgentTool) and network-isolated A2A delegation:

DimensionIntra-App (sub_agents / AgentTool)Inter-App (A2A Protocol)
Team & Repo BoundarySingle repo, unified CI/CD release, homogeneous runtime stack (e.g., all Python ADK)Independent teams/repos, separate release cycles, polyglot frameworks (ADK ↔ LangGraph ↔ SaaS vendor)
Session & Memory ScopeShared in-process InvocationContext & session.stateStrict opacity: remote agent maintains its own private store; sees only explicit Part payloads sent per contextId
IAM & Blast RadiusShares one container & service identity — wide blast radius if compromisedHard security boundary: separate SPIFFE Agent Identity, VPC-SC perimeter, least-privilege IAM, and scoped OAuth token exchange
Latency & OverheadZero network serialization (in-memory call); lowest TTFTHTTPS/gRPC hop + auth validation + independent remote reasoning loop
Live Voice / Modality BoundaryNative in-memory context sharingModality normalization: live voice front-doors (CX Agent Studio / Gemini 3.8 Live) terminate audio streams locally and delegate normalized TextPart / DataPart / FilePart tasks over A2A

Generative UI: A2UI vs. AG-UI vs. MCP UI

  • A2UI (Agent-to-UI, v0.8/v0.9 — Native in Gemini Enterprise): Remote A2A agents stream flat, declarative JSON widget trees + data bindings inside A2A DataPart payloads against a client-approved Component Catalog (basic, Material, or custom widgets). The host client renders native, brand-consistent UI with zero arbitrary JS/iframe XSS risk.
  • AG-UI: Bidirectional frontend-to-agent event stream synchronizing live text tokens, tool indicators, shared state diffs, and HITL interrupts.
  • MCP UI: Tool-level embedded UI views returned directly by an individual MCP tool call.

Agentic Commerce: AP2 & x402

  • AP2 (Agent Payments Protocol): Extends A2A & MCP with verifiable cryptographic credentials (Mandates) for non-repudiable delegated commerce: (1) Intent Mandate (signed upfront rules/caps for human-not-present buying, e.g., "tickets < $300") and (2) Cart Mandate (cryptographically signs exact final items & price).
  • x402 Protocol: Uses HTTP 402 Payment Required headers so agents can autonomously pay per API call, dataset query, or compute unit via programmatic M2M micropayments without pre-provisioned subscriptions.

Collaborative Multi-Agent Topologies

Production Workflow Patterns

  • Hierarchical Supervisor / Router: Front-door orchestrator dynamically matches sub-goals to specialist AgentCard skills and synthesizes their artifacts.
  • Debate & Consensus: Multiple peers with distinct models or domain corpora critique high-stakes proposals (e.g., medical triage, financial risk, architecture review) to eliminate single-model blind spots.
  • Critic-Reviewer (Generator-Verifier): Producer agent drafts an artifact; an independent A2A reviewer agent validates policy, security, and factual grounding before external release.
08

Google Cloud Implementation & Security

ADK, Agent Runtime & Gemini Enterprise

  • ADK Server (to_a2a() & A2aAgentExecutor): Define AgentCard + AgentSkills, bridge the task loop with A2aAgentExecutor (automated by to_a2a(root_agent)), and deploy to Cloud Run, GKE, or Agent Runtime (A2aAgent).
  • ADK Client (RemoteA2aAgent): Consume any remote A2A peer inside an ADK orchestrator by pointing at its AgentCard or Agent Registry URI.
  • Gemini Enterprise & CX Agent Studio: Register third-party or ADK A2A agents directly into Gemini Enterprise (with OAuth brokering + A2UI rendering) or delegate backend workflows from CX Agent Studio over A2A.

Zero-Trust A2A Security & A2AOps

  • Header-Only Credentials: Pass OAuth 2.0 / OIDC tokens and API keys exclusively via HTTP headers — never in URLs (proxy logs) or message/task bodies (persisted in task history & forwarded to LLMs).
  • mTLS & Scoped Token Exchange: Enforce Mutual TLS (mTLS), cryptographic SPIFFE Agent Identity, and OAuth Token Exchange (RFC 8693) via Agent Gateway so downstream peers receive audience-scoped tokens rather than broad user uber-tokens.
  • Cross-Agent Guardrails & Tracing: Screen inbound/outbound A2A payloads with Model Armor against task injection, enforce Task Depth Limits, and propagate W3C traceparent headers into Cloud Trace.

Self-Assessment Questions

Q1. When should you choose A2A over ADK's in-process AgentTool?

When crossing team, repository, framework, vendor, or IAM/VPC security boundaries where opaque state and independent scaling/blast-radius isolation outweigh a network hop.

Q2. How does A2UI prevent Cross-Site Scripting (XSS) when rendering UI from a remote third-party A2A agent?

Instead of executing remote HTML/JS iframes, the agent sends declarative JSON referencing widgets from a client-approved Component Catalog rendered natively by the host app.

Q3. How do AP2 Intent Mandates and x402 solve different commerce problems?

AP2 uses user-signed cryptographic Intent and Cart Mandates for verifiable, non-repudiable delegated purchases, whereas x402 uses HTTP 402 headers for autonomous machine-to-machine API micropayments.
