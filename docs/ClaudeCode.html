Overview, Agent Loop & Surfaces

Definition

Claude Code is Anthropic's agentic coding tool. It reads your codebase, edits files, runs commands, and verifies its own work through a tool-using loop. The same harness ships as a library, the Claude Agent SDK, so you can embed that loop in your own process. Claude Managed Agents runs a comparable stateful loop on Anthropic's infrastructure.

The agentic loop

Every task cycles through three blended phases: gather context (search, read) → take action (edit, run) → verify results (tests, diffs), repeating until done. Each tool result informs the next step, and you can interrupt at any point. Hooks, skills, subagents, and MCP all plug into specific phases of this loop.

01

Gather context

CLAUDE.md, .claude/rules/, and auto-memory MEMORY.md load; Claude searches and reads files, or delegates noisy exploration to a subagent.

02

Permission check

PreToolUse hooks run first → deny → ask → protected/critical-path checks → allow → active permission mode → PermissionRequest hooks → prompt or SDK canUseTool.

03

Take action

Edits, shell commands, MCP tool calls, or skill invocations execute (optionally inside OS-level /sandbox isolation).

04

Verify

PostToolUse / FileChanged hooks format or audit; Claude runs tests and reads results before Stop hooks evaluate completion.

Surfaces: CLI, Worktrees, Cloud/Web & Teleport, Cowork, and Agent SDK

Claude Code (CLI, IDE & Worktrees)
Available in the terminal CLI, Desktop Code tab, VS Code / JetBrains extensions, Slack, and CI/CD. Local Worktrees (--worktree / -w): creates an isolated checkout under .claude/worktrees/<name> sharing git history on your machine; does not copy gitignored files (node_modules, .env, venv), requiring dependency setup or a SessionStart hook.
Cloud/Web (claude.ai/code) & Teleport
Runs in an Anthropic-managed cloud VM cloned from GitHub (survives laptop sleep; Mobile is 100% cloud-only). Prefix a CLI prompt with & <prompt> to dispatch a background cloud session. Use /teleport (/tp or claude --teleport <id>) for one-way Cloud → Local terminal handoff (requires clean local git state; local sessions cannot be pushed to web).
Cowork, Dispatch & Agent SDK
Cowork runs desktop knowledge work in an app-hosted VM; Dispatch hands off tasks from mobile/web to desktop. The Claude Agent SDK embeds the same loop, tools, permissions, hooks, and subagents as a TypeScript or Python library in your own process.

Deep Agent 4-Pillar Architecture & the 4 Context Strategies

Claude Code goes beyond a shallow single-loop ReAct agent by combining four architectural pillars mapped to the four context engineering strategies (Write, Select, Compress, Isolate):

  • 1. Explicit Planning Tool (TodoWrite / TodoRead) [Write]: Externalizes a live checklist in agent state so multi-step plans survive context window pressure and tool failures without goal drift.
  • 2. Hierarchical Sub-Agents (Task / Agent) [Isolate]: Spawns child agents in fresh context windows for noisy search or independent checks, returning only a distilled summary to the parent.
  • 3. Filesystem as External Context Engine [Write & Select]: Avoids static RAG chunking failures (under-retrieval, over-retrieval, and misaligned retrieval across imports) by navigating live code via Glob (paths), Grep (ripgrep regex), and paginated Read(file_path, offset, limit), plus writing durable state to disk (CLAUDE.md, SPEC.md, MEMORY.md).
  • 4. Detailed System Prompt Heuristics + Compaction [Compress]: Built-in tool-selection heuristics and /compact (or /clear) keep active context inside the high-recall attention budget.

Mental model

The model proposes; the harness disposes. Anything written in CLAUDE.md or .claude/rules/ is advisory guidance the model weighs. Anything in settings.json permission rules, hooks, or managed policy is enforced deterministically by the client regardless of what the model decides.

1. Permission Modes & Allow / Ask / Deny Rules

A permission mode sets the session's baseline for what runs without prompting. Rules then carve specific tools, paths, or commands in or out. Set the starting mode with --permission-mode or permissions.defaultMode (interactive CLI defaults to auto on supported plans in v2.1.283+; project .claude/settings.json and .claude/settings.local.json ignore defaultMode: "auto" and "bypassPermissions").

Common trap: acceptEdits + protected paths

acceptEdits also pre-approves CWD shell file utilities (sed, cp, mv, rm) — pair it with deny: ["Bash(rm *)"] when deletions must stay gated. Conversely, writes to protected repo paths (.git, .claude, .vscode, .idea, .husky, .mcp.json, shell profiles) are checked before permissions.allow, so putting Edit(.claude/**) in allow never pre-approves writes there, and even bypassPermissions still prompts on them.

Rule evaluation & path anchors

  • Order: PreToolUse hooks → deny → ask → protected/critical-path checks → allow → active mode → PermissionRequest hooks → prompt / canUseTool. First match in deny → ask → allow wins regardless of specificity.
  • Bare vs scoped deny: Bare tool names in deny ("Bash", "WebFetch", "mcp__*", "Agent(Explore)") remove the tool from context entirely; scoped rules ("Bash(rm *)") keep the tool in context and block matching calls.
  • Read & Edit only: Only Read(...) and Edit(...) accept path globs. Edit(...) governs Edit, Write, and NotebookEdit — Write(path) and Glob(path) rules never match!
  • Path prefix anchors: //path = absolute filesystem root (Read(//etc/**)); ~/path = $HOME; single /path = relative to <cwd> in project/local settings or ~/.claude/ in ~/.claude/settings.json (not root!); ./path or path = CWD.
  • Cross-tool coupling: Read(path) in deny also blocks Edit/Write and @file prompt mentions; Edit(path) in allow also grants Read. WebFetch(domain:*) in allow also opens all network hosts to sandboxed Bash!

MCP rules & OS sandboxing (/sandbox)

  • mcp__<server>__<tool> targets one tool; mcp__<server> or mcp__<server>__* targets all tools on that server; mcp__github__get_* wildcards the tool suffix.
  • Never use (...) on mcp__ rules in settings files (skipped with a startup warning), and unanchored "*" or "mcp__*" in allow is skipped.
  • Permission rules vs OS sandboxing: Permission rules gate which tool calls Claude invokes; OS sandboxing (sandbox.enabled: true; Seatbelt on macOS, bubblewrap on Linux/WSL2) restricts child process filesystem and network access.
  • With sandbox.autoAllowBashIfSandboxed: true, sandboxed Bash commands run without prompting. Failed sandbox commands may retry with dangerouslyDisableSandbox: true (prompting the user) unless "allowUnsandboxedCommands": false enforces strict sandboxing.
JSON — .claude/settings.json (team-shared; requires workspace trust dialog for allow rules) 
{
  "permissions": {
    "defaultMode": "acceptEdits",
    "allow": ["Bash(npm run *)", "Edit(/src/**)", "mcp__github__get_*"],
    "ask":   ["Bash(git push *)"],
    "deny":  ["Read(./.env)", "Read(//etc/**)", "Bash(rm *)", "mcp__github__delete_repo"]
  }
}

Common trap: Bash prefix matching vs hard boundaries

Bash patterns match command prefixes, so deny: ["Bash(git push *)"] does not match git -C . push. For a hard boundary, combine deny rules with a PreToolUse hook and OS-level sandboxing (sandbox.enabled: true).

Loading, imports, /init & monorepo rules

  • Target under 200 lines per CLAUDE.md: longer files cost context and reduce adherence.
  • /init & # <rule> shortcut: /init scans the repo to bootstrap a starter CLAUDE.md (treat as a draft to prune); starting a prompt with # <rule> appends an instruction to your chosen CLAUDE.md tier.
  • @path/to/file imports expand at launch (max 5 hops) and do not save context tokens.
  • Skip noisy ancestor files in monorepos via "claudeMdExcludes": ["**/monorepo/CLAUDE.md"].
  • --add-dir loads skills/commands/agents from extra directories, but not CLAUDE.md or .claude/rules/ unless CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1.
  • Audit instruction bloat/conflicts with /doctor prompt-audit and inspect token usage with /context. (Note: .claudeignore does not exist — use permissions.deny: ["Read(...)"].)

Subdir lazy-load trap, AGENTS.md & .claude/rules/

  • Subdirectory CLAUDE.md lazy-load trap: When launched at repo root, frontend/CLAUDE.md does not load at startup — it loads lazily only when Claude reads/edits inside frontend/. Use .claude/rules/frontend.md with paths: ["frontend/**"] for deterministic glob-triggered rules.
  • AGENTS.md + CLAUDE.local.md trap: Under default auto project instructions, creating CLAUDE.local.md switches detection to claude-md only and silently stops loading AGENTS.md unless /config → Project instructions is set to claude-md-and-agents-md.
  • .claude/rules/*.md files are discovered recursively; scope comes only from paths: YAML frontmatter. A file in .claude/rules/db/ without paths: loads at launch for every task.

Context Rot Taxonomy & /clear vs /compact

  • Context poisoning: A hallucination, wrong file path, or failed assumption enters the conversation history and gets repeatedly referenced on later turns. Exam trap: /compact summarizes the current conversation — which preserves poisoned assumptions inside the summary! When a session suffers from context poisoning or switches to an unrelated task, run /clear (or /rewind prior to the bad turn).
  • Context confusion: Unrelated file dumps and verbose Bash outputs crowd the attention window; fix by delegating exploration to subagents and using /compact <focus> when switching phases.
  • Context clash: Contradictory instructions across CLAUDE.md files or multi-turn requirements cause unpredictable adherence; audit with /doctor prompt-audit.

Output Styles (/output-style) & Status Line (/statusline)

  • /output-style (modifies system prompt): Unlike CLAUDE.md (appended as a user message after the system prompt), /output-style directly replaces or swaps Claude Code's system prompt. Built-ins: Default (standard SWE), Explanatory (educational "Insights" callouts), and Learning (collaborative mode that leaves TODO(human) markers). Custom styles in ~/.claude/output-styles/*.md or .claude/output-styles/*.md strip default SWE instructions unless frontmatter sets keep-coding-instructions: true (saved to .claude/settings.local.json as outputStyle).
  • /statusline (zero-token UI telemetry): Configures a shell command in settings.json ("statusLine": {"type": "command", "command": "..."}) that receives live session JSON on stdin (model, workspace, cost, and transcript_path pointing to ~/.claude/projects/<encoded-cwd>/<uuid>.jsonl) and renders a terminal footer at zero LLM token cost.

Common trap

MCP "local scope" ≠ local settings. A local-scoped MCP server lives in ~/.claude.json under the project entry, while local settings live in .claude/settings.local.json at the git repository root.

How mechanisms combine across scopes

  • CLAUDE.md & .claude/rules/ — Additive: Every matching file across all layers loads into context simultaneously.
  • Permissions & Hooks — Merge & most-restrictive wins: Permission rules merge across all settings files (deny > ask > allow). Hooks from every active layer register and execute in parallel on matching events; PreToolUse decisions resolve by deny > defer > ask > allow.
  • Subagents, Skills, & MCP servers — Override by name: Only one definition wins when names collide (plugins use plugin:name namespaces). Precedence trap: Subagents resolve managed > --agents > project > user > plugin (project beats user), whereas Skills resolve managed > user > project > nested > plugin > synced (user beats project), and MCP servers resolve local > project > user.

Spec-Driven Development (SDD) & Two-Phase Model Switching

  • Phase 1 — Architect (Opus + plan mode): Start in plan mode (Shift+Tab) on Opus to explore the repo, resolve ambiguities via clarifying questions, and write a comprehensive specification to disk (SPEC.md).
  • Phase 2 — Builder (/clear + Sonnet + @SPEC.md): Run /clear to wipe exploration noise, switch to Sonnet (/model sonnet) for fast, cost-effective execution, and pass @SPEC.md as the clean source of truth (pairing UI tasks with Playwright MCP for visual self-verification).

4. Hooks & Exit-Code Semantics

What a hook is, wildcard matchers & the 5 handler types

A lifecycle handler configured in settings.json (user, project, local, or managed policy), a plugin's hooks/hooks.json, or a skill/subagent YAML frontmatter (hooks:). Hooks receive event JSON on stdin (session_id, cwd, hook_event_name, plus tool fields tool_name, tool_input).

  • 5 handler types: "command" (shell/exec script; supports "async": true for background side effects), "http" (POSTs event JSON to a URL), "mcp_tool" (invokes a configured MCP server tool), "prompt" (single-turn fast LLM check returning {"ok": true|false, "reason": "..."}), and "agent" (multi-turn verifier subagent with Read/Grep/Glob, up to 50 turns).
  • Wildcard matcher & synchronous latency: Omitting matcher, or setting "matcher": "" or "*", acts as a wildcard matching every tool call. Because synchronous hooks block the agentic loop on every match, scope matchers tightly ("Edit|Write") or set "async": true on non-blocking telemetry/logging commands.

JSON — fail-closed PreToolUse hook registration 
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{
        "type": "command",
        "if": "Bash(rm *)",
        "onFailure": "block",
        "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/no-rm.sh"
      }]
    }]
  }
}
Bash — no-rm.sh 
#!/bin/bash
cmd=$(jq -r '.tool_input.command')
if [[ "$cmd" == rm* ]]; then
  echo "Blocked: rm is not allowed" >&2
  exit 2   # block; stderr goes to Claude
fi
exit 0     # no decision; normal flow

Structured JSON on stdout (exit 0)

  • PreToolUse (hookSpecificOutput): permissionDecision resolves across parallel hooks by "deny" > "defer" > "ask" > "allow". "deny" blocks in every mode including bypassPermissions; "defer" pauses headless -p/SDK runs with stop_reason: "tool_deferred" for later --resume; "allow" bypasses normal prompts (unless matched by permissions.deny/ask or blocked by plan mode).
  • updatedInput & additionalContext: updatedInput replaces the entire tool_input object (omitted keys are dropped; permission rules re-evaluate against the rewritten input). additionalContext must be nested inside hookSpecificOutput alongside hookEventName.
  • PermissionRequest vs PostToolUse/Stop: PermissionRequest uses hookSpecificOutput.decision.behavior ("allow"|"deny"); PostToolUse, Stop, UserPromptSubmit, PreCompact, and ConfigChange use top-level {"decision": "block", "reason": "..."} (plus updatedToolOutput on PostToolUse).

@file bypass, portable paths & $CLAUDE_ENV_FILE

  • @file mention bypass trap: PreToolUse on Read does not fire when a user types @.env in their prompt (Claude Code inlines @file directly without calling Read). Block both with permissions.deny: ["Read(./.env)"] (or CLAUDE_CODE_DISABLE_FILE_MENTIONS=1).
  • Portable paths: Use ${CLAUDE_PROJECT_DIR} in repo hooks and ${CLAUDE_PLUGIN_ROOT} (code) / ${CLAUDE_PLUGIN_DATA} (persistent state) in plugin hooks.
  • Environment persistence ($CLAUDE_ENV_FILE): Append export KEY=VAL to $CLAUDE_ENV_FILE inside SessionStart, Setup, CwdChanged, or FileChanged hooks to persist env vars across subsequent Bash calls.

5. Subagents

5-level scope precedence & plugin restrictions

Specialized assistants with their own context window, system prompt, tool set, and optional model/permission mode.

  • Precedence (highest → lowest): 1. Managed (.claude/agents/) → 2. --agents '{...}' CLI flag → 3. Project (.claude/agents/<name>.md) → 4. User (~/.claude/agents/<name>.md) → 5. Plugin (agents/<name>.md, invoked as plugin:agent).
  • Contrast with Skills: For subagents, Project overrides User; for skills, User overrides Project.
  • Plugin security restriction: Plugin subagents ignore hooks, mcpServers, and permissionMode in frontmatter.

Built-in vs Custom vs Fork (/subtask)

  • Explore (Haiku) & Plan: Read-only, skip root CLAUDE.md and git status, and are one-shot (return no agentId, cannot be resumed).
  • general-purpose & Custom subagents: Load CLAUDE.md (unless omitClaudeMd: true), start in a fresh context window (no parent conversation history), and return an agentId that can be resumed via SendMessage.
  • Fork subagent (/subtask): Unlike standard subagents, a fork inherits the parent's full conversation history, system prompt, tools, and model, and shares the parent's prompt cache (up to depth 2).
YAML — .claude/agents/security-auditor.md frontmatter

Context contracts: description vector & raw artifacts

  • Dual role of description (prompt-injection vector): A subagent's description is loaded into the main agent's system prompt so the parent knows when to delegate, whereas the markdown body is seen only by the subagent. Untrusted .claude/agents/*.md files can inject instructions into the parent via description before the subagent is ever invoked!
  • Summary-only return / missing raw artifact trap: A subagent's intermediate tool calls stay inside its isolated window; only its final text response returns to the parent. If the parent needs generated code or structured data, the subagent must either write it to disk (Write/Edit) or include the verbatim artifact/diff in its final response.

Wave scaling (3–5), Builder–Reviewer & when NOT to parallelize

  • Wave-based scaling ("Infinite Agentic Loop"): Orchestrate large parallel generation in waves of 3–5 concurrent subagents (each writing to distinct output paths) so the parent's context doesn't overflow when collecting results.
  • Builder–Reviewer separation: An agent reviewing code it just wrote in the same context suffers from confirmation bias; spawn a separate read-only subagent (security-auditor) to review the diff cold.
  • 5 anti-patterns where parallel agents/worktrees fail: (1) overlapping edits to the same files, (2) sequential data dependencies (Step B needs Step A's schema), (3) small single-file tasks where worktree/spawn overhead exceeds work, (4) ambiguous/unverified specs (multiplies rework by N), and (5) tight shared stateful resources (single local DB port).

Common traps: disallowedTools specifiers & permissionMode

1. Putting a specifier in subagent disallowedTools — such as disallowedTools: Bash(git push *) — removes the entire Bash tool from the subagent. Keep Bash in tools and block specific commands via permissions.deny or a PreToolUse hook.
2. If the parent session runs in bypassPermissions, acceptEdits, auto, or plan, the parent mode overrides the subagent's permissionMode; a subagent setting permissionMode: bypassPermissions is ignored unless the parent session is already in bypassPermissions.
3. Under claude --agent, tools: Agent(worker, researcher) allowlists which subagents can be spawned; session-wide, block specific subagents via permissions.deny: ["Agent(Explore)"].

6. Skills & Progressive Disclosure

3-Level Progressive Disclosure & Token Budgets

  • Level 1 — Metadata (~100 tokens/skill at startup): Only YAML frontmatter name and description (+ when_to_use, max 1,536 chars combined; total listing cap = 1% of context window via SLASH_COMMAND_TOOL_CHAR_BUDGET) load at startup. YAML boundary trap: Trigger phrases placed in a ## When to Use section inside the markdown body (below the closing ---) are invisible to Claude before activation!
  • Level 2 — SKILL.md body (< 5,000 tokens on activation): Loaded only when invoked; after /compact, active skills re-attach up to 5,000 tokens/skill (25,000 total).
  • Level 3 — Bundled scripts/, references/, assets/ (0 token cost for script code): Claude reads reference docs on demand and executes helper scripts via Bash (only script stdout/stderr enters context). Silent fallback trap: If a bundled script exits non-zero, Claude may silently fall back to guessing in-context unless SKILL.md instructs it to halt/fix and surface stderr.

7. Plugins & Marketplaces

Plugin anatomy & cache vs data dirs

  • Manifest at .claude-plugin/plugin.json (name, version, description); component folders (skills/, commands/, agents/, hooks/hooks.json, .mcp.json, .lsp.json, settings.json) live at the plugin root, never inside .claude-plugin/. (Plugin settings.json only supports the agent key.)
  • ${CLAUDE_PLUGIN_ROOT} vs ${CLAUDE_PLUGIN_DATA}: Installed plugins are copied into a read-only versioned cache (~/.claude/plugins/cache/...) that ${CLAUDE_PLUGIN_ROOT} points to — anything written inside ${CLAUDE_PLUGIN_ROOT} is wiped on update. Store persistent state, SQLite DBs, or node_modules in ${CLAUDE_PLUGIN_DATA} (~/.claude/plugins/data/<id>/), which survives updates.
  • Version bump rule: version in plugin.json overrides marketplace.json version and git SHAs. Pushing commits without bumping plugin.json version causes claude plugin update to skip fetching.
  • Declare install-time secrets in userConfig with "sensitive": true (stored in OS keychain, exposed as ${CLAUDE_PLUGIN_OPTION_<KEY>}).

Marketplace governance & granular install

  • Granular catalog (.claude-plugin/marketplace.json): Maps multiple named plugins inside a single repository so developers can install individual skills, subagents, or MCP servers via /plugin without loading the entire repo's context overhead.
  • extraKnownMarketplaces: pre-registers org catalogs (github, git, url, npm, file).
  • enabledPlugins: "plugin@marketplace": true force-enables a plugin in managed settings (users cannot disable it); false blocks it.
  • strictKnownMarketplaces: allowlist of marketplace sources ([] blocks every marketplace, including the official directory); blockedMarketplaces blocklists specific sources.
  • disableSideloadFlags: true: blocks --plugin-dir CLI sideloading (which bypasses marketplace allowlists).
  • strictPluginOnlyCustomization: true (or selective strictCategories: ["hooks", "mcp"]): blocks non-managed local/user/project customizations so only managed settings and approved plugins can define hooks, skills, agents, or MCP servers.
JSON — managed-settings.json (curated plugin rollout) 
{

  "extraKnownMarketplaces": {
    "acme-tools": { "source": { "source": "github", "repo": "acme-corp/plugins" } }
  },
  "enabledPlugins": { "secure-review@acme-tools": true },

Managed MCP: Provisioning vs Filtering

  • 1. Exclusive file provisioning (managed-mcp.json): Deploying managed-mcp.json at the OS system path gives IT exclusive control — users cannot add, modify, or use any MCP servers from .mcp.json, ~/.claude.json, or plugins.   • 2. Policy filtering (allowedMcpServers / deniedMcpServers): In managed-settings.json, entries match by {"serverName": "..."}, {"serverCommand": [...]} (exact stdio array), or {"serverUrl": "https://*.corp.com/*"}. Denylist always wins.
  • serverUrl trap: Once any serverUrl entry appears in allowedMcpServers, remote HTTP/SSE servers must match a serverUrl pattern (serverName entries stop matching remote servers!).

${VAR} expansion & Tool Search

  • ${VAR} and ${VAR:-default} expand in command, args, env, url, and headers. Unset variables without defaults send the literal ${VAR} string.
  • Credential variable strip: ANTHROPIC_API_KEY and CLAUDE_CODE_* auth vars resolve to empty string in remote HTTP/SSE url/headers (causing 401). Use a custom env var name like ${SEARCH_MCP_TOKEN}.
  • MCP Tool Search (ENABLE_TOOL_SEARCH): By default (true/unset), all MCP tool schemas are deferred behind ToolSearch (set "alwaysLoad": true on a server in .mcp.json to preload its schemas). auto defers at 10% context (auto:<N> for custom %); false preloads all schemas up front.

GitHub Actions Integration (/install-github-app)

  • Setup & prerequisites: Run /install-github-app interactively in the CLI (requires authenticated gh CLI and repository admin permissions) to install the Claude GitHub App, configure repo secrets (CLAUDE_CODE_OAUTH_TOKEN or ANTHROPIC_API_KEY), and open a PR adding .github/workflows/claude.yml (@claude mentions on issues/PRs create isolated claude/issue/<N> branches — never pushing directly to main) and claude-code-review.yml (automated PR diff reviews).
  • Ephemeral CI runner trap: GitHub Actions runners are fresh checkouts — gitignored CLAUDE.local.md, .claude/settings.local.json, and ~/.claude/projects/.../memory/MEMORY.md do not exist in CI. Any rule or skill that PR review agents must follow must be committed to CLAUDE.md, .claude/rules/, or .claude/skills/.

Checkpointing & /rewind (Esc+Esc)

  • 3 restore modes (30-day retention): Claude Code automatically snapshots tracked files before every user prompt and file-editing tool call. Press Esc twice (Esc+Esc) or run /rewind to pick a prior turn and restore: (1) Conversation and code, (2) Conversation only (keep disk edits, rewind context), or (3) Code only (revert disk edits, keep error lessons in context).
  • Critical Bash side-effect trap: Checkpointing and /rewind (as well as SDK rewind_files()) track only changes made through file-editing tools (Edit, Write, NotebookEdit). They never undo Bash side-effects (such as rm, mv, sed -i, git commit, package installs, or DB migrations) — use git or backups to recover from destructive shell commands.

Critical CI security trap: -p without --bare on untrusted PRs

When running claude -p on an untrusted PR checkout without --bare, project permissions.allow rules and subagent frontmatter hooks are skipped, but repository .claude/settings.json hooks and .mcp.json stdio servers execute automatically without a workspace trust dialog! Always pass --bare (or --settings '{"disableAllHooks": true}' + --strict-mcp-config) when running -p against untrusted code.

query() vs ClaudeSDKClient & sessions

  • Packages: TypeScript @anthropic-ai/claude-agent-sdk · Python claude-agent-sdk (replaces claude-code-sdk).
  • query(prompt, options): Starts a fresh session per call unless you pass continue_conversation=True (continue: true), resume=session_id (from ResultMessage.session_id), or resume=session_id, fork_session=True (forkSession: true). 12. Managed Agents & Agent Wiring Paths

All Managed Agents endpoints require the beta header managed-agents-2026-04-01 (set automatically by client.beta.agents / environments / sessions).

1. Agent (POST /v1/agents)
Versioned server-side definition (model, system string — no CLAUDE.md hierarchy, tools, mcp_servers, skills). Built-in sandbox tools use {"type": "agent_toolset_20260401"} (in /workspace); custom tools ({"type": "custom", ...}) pause the session and emit agent.custom_tool_use over SSE until your backend runs the logic and posts user.custom_tool_result. Per-tool permission_policy (always_allow, always_ask, auto) gates execution via user.tool_confirmation.
2. Environment (POST /v1/environments)
Anthropic-managed cloud container (type: "cloud", configurable networking: {"type": "limited"} domain allowlists) or self-hosted runner on your infrastructure.
3. Session (POST /v1/sessions)
Binds a pinned agent version + environment_id, mounted resources (file, github_repository, memory_store), vault_ids (Vaults inject MCP/API credentials into outbound headers outside the container so raw secrets never enter the sandbox), and spend budget.
4. Events (POST /v1/sessions/{id}/events)
Bidirectional SSE stream (user.message, agent.message, agent.custom_tool_use → user.custom_tool_result, user.tool_confirmation, and session.status_idle with stop_reason.type == "end_turn").

Compliance trap: ZDR & HIPAA BAA

Managed Agents is stateful by design (storing conversation history, container state, and outputs server-side) and cannot be used under a HIPAA BAA or Zero Data Retention (ZDR) agreement. Find the defect: a team's "secure" setup

A team commits the following and believes .env is completely blocked, warehouse MCP tools are auto-approved, and their CI JSON schema script is safe. Find four defects before revealing.

.claude/settings.json + .claude/hooks/block-env.sh + .mcp.json + CI script 
// .claude/settings.json
{
  "permissions": { "allow": ["mcp__*", "Edit(.claude/**)"], "deny": ["Write(/.env*)"] },
  "hooks": { "PreToolUse": [{ "matcher": "Read",
    "hooks": [{ "type": "command", "command": "/Users/alex/repo/.claude/hooks/block-env.sh" }] }] }
}
# .claude/hooks/block-env.sh
f=$(jq -r '.tool_input.file_path')
if [[ "$f" == *.env* ]]; then echo "blocked" >&2; exit 1; fi
// .mcp.json
{ "mcpServers": { "warehouse": { "type": "http", "url": "https://wh.internal.example.com/mcp",
    "headers": { "Authorization": "Bearer ${ANTHROPIC_API_KEY}" } } } }
# CI script
claude -p "Extract release notes" --json-schema '{"type":"object","properties":{"tag":{"type":"string"}}}' --output-format json | jq -r '.result.tag'

Reveal the Four Fixes (Click to Reveal)

Fix 1. Why are all three permission rules broken?

"mcp__*" in allow is unanchored and skipped (use "mcp__warehouse__query"); "Edit(.claude/**)" in allow never bypasses protected-path prompts on .claude/; and "Write(/.env*)" in deny never matches because file-write rules must use Edit(...) (and Read(./.env*) in deny is needed to block both Read/Edit/Write and @.env prompt mentions).

Fix 2. Why do .env reads still succeed and why does the hook break on other machines?

block-env.sh exits 1 (non-blocking fail-open) instead of 2, lacks "onFailure": "block", misses @.env prompt mentions, and hardcodes /Users/alex/... instead of ${CLAUDE_PROJECT_DIR}.

Fix 3. Why does the warehouse MCP server return 401 Unauthorized?

Built-in credential variables like ANTHROPIC_API_KEY resolve to an empty string in remote MCP url/headers. Reference a custom variable name ("Bearer ${WAREHOUSE_MCP_TOKEN}").

Fix 4. Why does the CI pipeline print null for the schema output?

--json-schema places the validated JSON object in .structured_output.tag, not .result.tag (and untrusted PR runs should also pass --bare + --permission-mode dontAsk).

Self-Assessment Questions (Click to Reveal)

Q1. Why does deny: ["Write(/etc/**)"] fail to block Write("/etc/hosts"), and what is the exact rule that blocks it?

Two reasons: (1) only Read(...) and Edit(...) accept file-path patterns (Edit governs Edit, Write, and NotebookEdit; Write(...) never matches), and (2) a single leading slash / anchors to <cwd> or ~/.claude/, not the filesystem root. Use deny: ["Edit(//etc/**)"] with a double slash //.

Q2. Why does a PreToolUse hook matching Read fail to stop a user who types Summarize @.env, and how do you block both?

Claude Code inlines @file prompt mentions directly while building the prompt without invoking the Read tool, so PreToolUse never fires. Add Read(./.env) to permissions.deny (which blocks Read, Edit/Write, and @file mentions) or set CLAUDE_CODE_DISABLE_FILE_MENTIONS=1.

Q3. What happens when a subagent frontmatter includes disallowedTools: Bash(git push *)?

The subagent loses the entire Bash tool, because any specifier in subagent disallowedTools strips the whole underlying tool. Keep Bash in tools and block git push via permissions.deny or a PreToolUse hook.

Q4. How does scope precedence differ between Subagents and Skills when a user-level and project-level definition share the same name?

For Subagents, project beats user (managed > --agents > project > user > plugin). For Skills, user beats project (managed > user > project > nested > plugin > synced).

Q5. In a plugin, why shouldn't a hook write a SQLite database inside ${CLAUDE_PLUGIN_ROOT}?

${CLAUDE_PLUGIN_ROOT} points to the read-only versioned plugin cache, which is wiped and replaced whenever the plugin updates. Store persistent state in ${CLAUDE_PLUGIN_DATA} (~/.claude/plugins/data/<id>/).

Q6. What is the security risk of running claude -p on an untrusted PR branch without --bare, and where does --json-schema output appear?

Without --bare, claude -p executes repository .claude/settings.json hooks and .mcp.json stdio servers automatically without a workspace trust dialog. When using --json-schema with --output-format json, the validated payload is in .structured_output, not .result.

Q7. In the Agent SDK, what four things can still load even when you pass setting_sources=[]?

(1) Managed policy settings, (2) ~/.claude.json global state (isolate via CLAUDE_CONFIG_DIR), (3) auto-memory at ~/.claude/projects/<project>/memory/MEMORY.md (disable via CLAUDE_CODE_DISABLE_AUTO_MEMORY="1"), and (4) claude.ai MCP connectors (suppress via strict_mcp_config=True).

Q8. In Claude Managed Agents, how do you run a proprietary tool inside your own VPC while keeping third-party MCP credentials out of the cloud container?

Declare the VPC tool as {"type": "custom", ...} on the Agent so the session pauses and emits agent.custom_tool_use over SSE (your VPC executes it and posts user.custom_tool_result), and attach a Vault via vault_ids on the Session so MCP auth headers are injected server-side outside the sandbox.
